拖放改走原生 WM_DROPFILES —— 前两条路都是错的

用户试了三次都不行。把三条路都试过一遍之后才找对：

① HTML5 dataTransfer.files
   QtWebEngine 里能拿到 File 对象，但没有 path 属性 ——
   那是 Electron 扩展，Chromium 标准没有。没路径就没法转 GIF。

② QWidget eventFilter + OLE drag-drop
   直接构造 QDropEvent 塞给控件时 eventFilter 是正常的（日志有、
   accepted 为 True），但真实拖动时鼠标显示禁止图标、事件根本没产生。
   后来查出来是 UIPI：程序要 UIA 所以是管理员权限（高完整性），
   资源管理器是中完整性，Windows 拦住跨完整性的 OLE 拖放。
   加了 ChangeWindowMessageFilterEx 放行三条消息（API 都返回 True），
   事件还是没到。

③ 现在：Windows 原生 WM_DROPFILES
   DragAcceptFiles(hwnd, TRUE) 让系统知道这个窗口收文件，
   之后系统直接发 WM_DROPFILES，不经过 OLE，绕开跨进程那套。
   配合 QAbstractNativeEventFilter 全局拦消息 —— 比装 eventFilter
   到某个子控件可靠，不管落在哪一层都会经过。

我自己构造了一个 WM_DROPFILES（GlobalAlloc + DROPFILES + PostMessage）
验证整条链路：
    WM_DROPFILES hdrop=... 文件数=2
    已交给页面：2 个
    页面 pending: {"n":2,"p":["动图_512.gif","动图_240.gif"]}

批量拖拽本来就是支持的（DragQueryFileW 逐条读）。

拖放出问题很难查（界面在管理员权限下跑，看不到控制台），
所以加了 <程序目录>/data/_drop.log，记录 install / 收到消息 /
解析出几个文件 / 有没有交给页面。下次再坏能一眼看出卡在哪。

DragFinish 必须调 —— 否则系统侧资源不释放，第二次拖放会失败。
