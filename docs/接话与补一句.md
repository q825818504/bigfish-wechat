# 接话与补一句

> v0.9.4。这一层解决的问题：**她会不会看眼色。**

---

## 一句话

以前她对每一条消息都必回，而且回完就完。

现在多了两件事：

- **该不接的时候可以不接**（你回「嗯」，她不一定接）
- **说完还能补一句**（「哦」之后过十几秒，「吃了吗」）

两件事共用一套判据：**这一句话够不够。**

---

## 一、不接：`-`

模型输出一个 `-`，这一轮不说话。

日志里会写：

```
[接话] 不接（连着第 1 次）：对方这句没内容可接
```

### 为什么需要一个符号，而不是"输出空"

模型输出空串和生成失败长得一样，分不清是"她想好了不说话"还是
"这次生成坏了"。给一个明确的标记，日志才写得清。

### 连着不接的兜底

连着 2 次不接之后，第 3 次**强制回**：

- prompt 里加一句「这一次一定要回一句，不要用 `-`」
- 万一模型还是给了 `-`，发一个「嗯」

不这么做的话，你连着说三句她一声不吭 —— 和程序坏了没有区别。

### 群聊不参与

@ 你的话不接，等于没听见，看起来像挂了。所以 `-` 只在私聊生效。

---

## 二、补一句：`补：`

模型可以在主回复之后另起一行写：

```
哦

补：吃了吗
```

第一段立刻发，第二段**8–25 秒后**再发。

---

## 三、关键设计：生成宽松，发送严格

让模型写「补：」本来就会滥用 —— 它不知道什么时候该补，只知道格式上可以补。
只靠 prompt 约束的结果是「每条回复后面都跟一句」，那比不补还假。

所以规则是：

> 模型想补就让它写，但只有**主回复本身不完整**的时候才真的发。

六道筛，前四道问"这句话说完了没有"，后两道问"最近是不是补太多了"：

| # | 条件 | 不补的理由 |
|---|---|---|
| 1 | 主回复是空的 | 没东西可补 |
| 2 | 已经分了 ≥2 条 | 再说就多了 |
| 3 | 主回复 ≥12 字 | 说完了 |
| 4 | 以问句结尾 | 球已经踢出去了 |
| 5 | 6 小时内补过 | 太密 |
| 6 | 最近 3 条回复内补过 | 太密 |

全过还要**掷骰 50%**，留一点不确定，免得变成"短句必补"的机械规则。

### 效果

一天 30 条回复里：

```
回复本来就长（≥12 字）  ~65%   不补
分了 2 条以上          ~10%   不补
以问句结尾             ~10%   不补
最近刚补过              ~5%   不补
过完所有门槛           ~10%   掷骰 → 一天补 1–2 次
```

补的都是「哦」「行吧」「那你忙」后面 —— 这才像话。

---

## 四、四条取消条件（这一节最重要）

第二段是延迟发的，这中间世界会变。四条任何一条漏了，都会出现
"她说了句莫名其妙的话"，而且事后查不出来：

| # | 情况 | 为什么必须取消 |
|---|---|---|
| 1 | **这期间对方说话了** | 她补的那句会和新消息撞车 |
| 2 | 她睡着了 | 睡着的消息不该发（和 sleep-gate 的规则一致） |
| 3 | 超过 90 秒还没发 | 语境已经过去，这时补更像自言自语 |
| 4 | UIA 没就绪 | 发不出去就丢，不重试（重试会延迟错位） |

第 1 条怎么判断：用**收到消息的序号**（`recv_count`），不用时间戳 ——
序号不会被她自己的发送干扰，也不受时钟影响。

预演模式（`dry_run`）只写日志不发：

```
[接话·预演] 本来会补一句：吃了吗
```

---

## 五、日志怎么读

```
[接话] 不接（连着第 1 次）：对方这句没内容可接
[接话] 有半句没说出口，但不补（主回复 14 字，说完了）
[接话] 待补一句：吃了吗（13 秒后）
[接话] 补一句：吃了吗
[接话] 补的那句取消：对方已经说话了
```

**被筛掉的每一条都记**。这样你能直接看到"它想补但被拦了几次" ——
如果一天拦了 40 次、只放 2 次，说明分寸对了。

## 六、代码位置

| 文件 | 职责 |
|---|---|
| `bigfish/say.py` | `is_silent` / `split_afterthought` / `allow_afterthought`（纯函数，可离线测） |
| `bigfish/desktop.py` | `_maybe_queue_after`（排进延迟队列）/ `_flush_after`（到点发或取消） |
| `tools/selftest_afterthought.py` | 45 条断言，重点是那四条取消条件 |

### 为什么判据放在 say.py

它本来就是「怎么把话说出口」那一层（分条、节奏）。"接不接"和"补不补"
是同一层的判断 —— 都是关于**说多少**，不关于**说什么**。

而且两件事用的是同一套判据（这句话够不够），分开写等于把长度门槛写两遍。

---

## 七、攒批判定：到点问一句「他说完了吗」（0.11.1）

### 为什么需要

固定窗口只能猜：

- 窗口短了 → **插话**。用户实测：「我稍微犹豫一点发，她就已经回复了」。
- 窗口长了 → **呆**。对方明明说完了，她还在数秒。

真正决定"要不要再等"的，是**这句话有没有说完**——
这是模型最擅长、规则最难写准的东西。所以到点之后问一次模型。

### 流程

```
消息到达
   ↓
安静窗口 = max(自适应, batch_min_wait)      ← 默认 6 秒
   ↓ 到点
问模型：他还有下一句吗？                     ← 0.5~2 秒
   ├─ more=true  → 再等 batch_judge_extra（默认 8 秒）
   │                最多问 batch_judge_rounds 次（默认 3）
   └─ more=false → 立刻封批
   ↓
硬上限 batch_max_wait（默认 30 秒）：越不过它，模型说多少次「还有」也一样
```

也就是说：**6 秒起步，正常 6~14 秒就回；极端情况最多 30 秒。**

### 两条硬约定

1. **判定失败一律倒向「说完了」。**
   模型超时、报错、输出看不懂 → 立刻封批。
   让一次网络抖动把回复拖到 30 秒上限，比早回一句糟得多。

2. **对方在判定期间又说话了 → 旧结论作废。**
   `feed()` 会清掉 `awaiting` 并把 `judged` 归零；
   之前那次判定的结果回来时直接丢掉，`verdict()` 返回 `None`。
   否则「他说完了」的旧结论会按住后面新来的消息。

### 参数在哪调

**「说法」插件面板**（不是设置页）。这几项决定「她什么时候开始想」，
和分条、节奏是同一类东西，所以放在一起。

| 参数 | 默认 | 说明 |
|---|---|---|
| 最少等几秒再回 | 6.0 | 攒批底线。任何消息都不会早于这个时间封批 |
| 到点问一次模型 | 开 | 关掉 = 只按固定时间回（老行为） |
| 判「还有」后再等 | 8.0 | 每次判定说「还有」后的追加等待 |
| 最多问几次 | 3 | 防止对方一直分条发、模型一直说「还有」 |
| 判定超时（秒） | 6.0 | 超时按「说完了」处理 |
| 最多等几秒（硬上限） | 30.0 | 从对方第一句算起 |

改完 **5 秒内生效**（`_batch_loop` 每 5 秒重读一次插件配置），不用重启。

### 日志

```
[倾听] 判定：他还有下一句（只是开场，逗号收尾）
[倾听] 判定他还有下一句，再等 8 秒（第 1 次，上限 30 秒）
[倾听] 判定：说完了（句号收尾）
[倾听] 判定失败（按说完了处理）：判定超时
```
