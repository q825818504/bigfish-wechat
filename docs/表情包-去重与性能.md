> 一次性把三件事讲清楚：**为什么卡**、**关插件会不会丢图**、**批量导入怎么判重复**。

## 一、卡在哪，改了什么

### 翻页（改成真翻页，不用划到底自动加载）

一页 **60 张**，底下有「‹ 上一页 / 第 N / 37 页 · 61–120 / 2173 / 下一页 ›」。
最后一页时"下一页"灰掉，一眼能看到底在哪。

为什么不自动加载：问题不在性能，在手感 —— 越划越多、不知道还有多少、
永远摸不到底。翻页把"还剩多少"直接写在页脚。

实测（Chromium 1440×900，真界面、精简数据、2173 条）：

| 指标 | 数值 |
| --- | --- |
| 首屏渲染（60 格 + 强制布局） | 37 ms |
| 翻一页（整页替换） | 8~12 ms |
| 页内节点数 | 恒定 60（不会越翻越多） |
| 翻页后滚动位置 | 回到顶部 |

### 进页面的顿挫：这次真正掐掉了两处

**① 每 2 秒一次的微信进程探测（主因）**

`get_status` 每 2 秒跑一次，里面调 `_find_weixin_pids()` ——
它要 EnumWindows + NtQuerySystemInformation + tasklist 三路合一：

```
实测 173 ms / 次，全在 GUI 线程上 → 每 2 秒卡 173 ms
改成 30 秒缓存后 ≈ 11.6 ms / 次
```

这一条才是"点任何按钮都慢半拍"的根源：你点「表情包」的那一刻，
有一半概率正撞上这次探测。

顺带把 `IsUserAnAdmin()` 也缓存了（5.08 ms → 0.0001 ms）。

**② 列表数据瘦身**

以前每次进页都传 1048 KB 的 JSON（2181 条 × 494 字节），其中：

```
detail   220 KB   只有双击看详情才用
thumb    115 KB   路径可以前端拼
path      85 KB   同上
tags      65 KB   同上
```

现在 `sticker_list(slim=true)` 只给翻页要用的字段：**1048 KB → 495 KB**。
双击看详情时再单独 `sticker_get(code)` 取那一条（约 300 字节）。

**③ index.json 解析提速**：`json.load(文本)` → `json.loads(字节)`，
走 C 加速的编码检测，**26 ms → 19 ms**。

### 还剩的已知代价

`list_stickers` 本身仍是 ~130 ms（2173 次 `os.stat` + `os.path.isfile`
+ 组装字典），跑在 GUI 线程上。进页时会顿一下，量级已经比之前小。
要彻底消除只能挪线程，这一步没做。

## 二、关掉插件会不会丢表情？不会

源码层面：`plugins.set_enabled()` 只写 `plugins.json` 里的一个布尔值，
表情插件的代码里没有任何 `os.remove` / `rmtree` / `unlink`。

实测（临时数据根，导入 1 张后关→开）：

```
关前 ['_thumbs', 'index.json', 'stk_0001.gif', 'x.png']
关时 ['_thumbs', 'index.json', 'stk_0001.gif', 'x.png']
开后 ['_thumbs', 'index.json', 'stk_0001.gif', 'x.png']
文件完全一致: True | 条目保留: True
```

插件关掉只是「她不会发」，不是「她的表情没了」。

## 三、批量导入怎么判重复

三层，前两层会**跳过**，第三层只提示。

### 第 1 层：字节相同

`sha256(整个文件)` 相等 → 跳过。

- 改名、拷贝、跨盘复制 → 必中
- 零误判

### 第 2 层：配色 + 构图几乎一致

把首帧压成 8×8 色格，比两个数：

| 数 | 含义 |
| --- | --- |
| 色差 | 8×8 里逐通道最大差值 |
| 格数 | 色差超过 40 的格子有几个 |

判据：**格数 ≤ 2 且 色差 ≤ 40 → 跳过**（个别格子变了、色差也大 → 「同一张图加了东西」）。

### 第 3 层：只提示不跳过

「格数少、色差中等」的组合 → 记一条「很像」，照收。

### 阈值是量出来的

400 张随机样本、79800 对两两比较（真库 `D:\大肥鱼`）：

```
色差  格数  结构   这是什么
  1     0     0    同一张图重新导出          ← 跳过
  5     0     0    同一张图加了不同水印       ← 跳过
 29     0    18    同一张图换了配色           ← 只提示
 31     0    22    同角色不同表情（配色一致） ← 只提示
 42     1    34    同角色，构图几乎不变       ← 只提示
 70     3     4    同角色，换表情             ← 收
255    19     0    同角色，姿态完全不同       ← 收
```

**关键发现：不能只靠结构相似判重。**
2181 张全是同一个角色的换装表情，dHash（结构）把「开心挥手」和「按按钮冒汗」
判成距离 0 —— 64 位全一样。pHash 也不行：真正的重复对反而有 16。
所以判据必须是「**配色也几乎一致**」，不能是「结构像」。

### 你会看到什么

导入完成后：

- 提示：`新增 1620 张，跳过重复 380 张`
- 日志区：跳过的具体文件 + 撞上了库里哪个编号 + 理由
- 相似的会单独列一行「很像库里已有的图，仍然收进来了」——你可以自己删

## 四、已知边界

- **整块加字幕的图认不出来**：底部 1/4 全换成字的版本，和「换了个表情」在 8×8 上分不开。
  这种只能进库后人工删。
- **同系列不会被跳过**：换装、换姿势、换表情一律收 —— 这是刻意的，
  因为库本身就是一个角色的全套表情。
- **老库第一次导入会慢一点**：要先给 2181 条补指纹（实测 18.8 ms/条，
  全库约 41 秒）。这一段跑在导入那一次的调用里，会明显停顿 ——
  分批补的版本还没接进界面，需要的话下一步做。
