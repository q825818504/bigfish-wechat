# 自环防护：她为什么会自己跟自己聊

> 2026-11-04 线上事故复盘。如果你以后发现"日志里她刚发的话变成了「收」"，
> 从这份文档开始看。

## 现象

20:27 到 20:29，两分钟里她跟「老爸」说了十几条，中间老爸一句没说。

日志长这样：

```
20:29:06 [发] 拔剑四顾心茫然……这句我背得还行吧
20:29:06 [收] 老爸：拔剑四顾心茫然……
20:29:08 [想] 1.3s 9字
20:29:10 [发] 背吧背吧，我听着呢
```

`[发]` 和 `[收]` 是同一条消息。她把自己刚发出去的那条，当成老爸说的话，
又回了一遍。

## 先说清楚：[收] 不是"老爸发的"

日志的 `[收]` 标签意思是「**这条消息进入了回复流程**」，不是「这是对方说的」。

监听器（`bigfish/watcher.py`）对所有新消息一视同仁 —— 数据库里冒出新行就
交给 `handle()`，`is_self` 只是消息的一个字段，由后续闸门判断。

所以看到 `[收] 老爸：<她自己刚说的话>`，说明的是：
**这条被读回来了，而且所有闸门都没拦住它。** 不是"发信人被认成了老爸"。

## 根因：四个问题叠在一起

### ① `allow_self = True` 泄漏到了生产会话

这个开关是给文件传输助手自测用的，语义是「允许回应我自己发的消息」。
它当时是**全局**的，于是老爸的私聊也变成了"我自己发的也算数"。

线上那份 `_internal/config.json` 里就是 `True`。

### ② 记账晚于写库（竞态）

发送路径：

```python
r = sender.send(chat, part)   # UIA 按回车就返回
remember_sent(part)           # 之后再记账
```

而微信是**异步写数据库**的。数据库先落地、watcher（1.2 秒一轮）恰好在这
一刻轮询到，这条就"没有账可对" —— 被当成对方说的。

窗口很窄，但聊一晚上必然撞上。撞上一次就进入正反馈：

```
她发 → 被读回 → 她又回 → 新的回复又被读回 → 又回 → ...
```

**这是"停不下来"的机制。** 不是死循环，是概率雪崩。

### ③ 没有轮级熔断

前面两层（`is_self` + 内容比对）都是**精确识别**。识别对了没事，
识别漏了就没有任何机制兜底。

### ④ 防护埋在闭包里，写不了测试

`recently_sent`、`text_is_echo`、`loop_streak` 全是 `_run()` 里的局部变量。
`_run()` 四千多行。**一行测试都写不了** —— 所以这次事故没有任何用例
能提前发现，复发也发现不了。

## 修复：抽成 `bigfish/loopguard.py`，四层闸门

任何一层单独失手，都不会成环。

| 层 | 机制 | 挡住什么 |
|---|---|---|
| **L0** | 静音 | 熔断后该会话完全不处理，连日志都不刷 |
| **L1** | 白名单 | `allow_self` 只对 `filehelper` 生效；私聊/群聊就算开着也拦 |
| **L2** | 乐观记账 | 发送**之前**记账，失败回滚 —— 消灭②的竞态窗口 |
| **L3** | 轮级熔断 | 连续 4 轮自动回复、中间无对方消息 → 静音 120 秒 |

### L3 的判据为什么不会误伤

一次回复分 2~4 条发出去，那是**一轮**。人类聊天不可能连续四轮回复之间
一句对方的话都没有。

```python
if guard.note_reply(msg.chat_id):     # 一轮回复记一次
    log("自环熔断")                   # 第 4 轮 → 静音
```

### 对方永远不会被误杀

`is_self` 为 `False`（对方发的）时，`admit()` 直接放行并清零计数，
**不做任何内容比对**。这一条踩过坑：早期版本靠"文字相同"判回环，
结果老爸原样复述她的话（聊天里极常见的调侃）被拦了两次。

## 怎么验证

```bash
python tools/selftest_loopguard.py
```

35 个断言，包含**事故复现**：

- 场景一：`allow_self=True`，私聊，她发完被读回 → L1 拦住，回 0 轮
- 场景二：连 L1 都人为放开、L2 全部失手 → L3 在第 4 轮掐住

不需要微信、不需要桌面、不需要网络。假时钟直接跳，不 sleep。

## 排查同类问题的动作清单

发现"她自己回自己"时，按顺序：

1. **先杀进程**。它会一直发，别等它自己停。
2. 看配置：`<安装目录>/_internal/config.json` 里 `allow_self` 是不是 `true`。
   （注意是 `_internal` 那份。外层那份是死文件，改了不生效。）
3. 看日志有没有 `[回环]` 行。有 → 闸门在工作；一条都没有 → 闸门根本没进去，
   八成是 `is_self` 判定失效（账号连错、或 `sender_username` 解析不出来）。
4. 查账号：两个微信号同时登录时，读的库和发的窗口可能不是同一个号。
   `python tools/diag_self.py <会话名>` 会打出最近的 sender 解析结果，
   `self` 那一列该是 `True` 才是自己发的。
5. 看有没有 `[自环熔断]`。有 → L3 兜住了，翻它前面 4 轮找第一次漏拦。

## 配置文件只有一个位置

```
<安装目录>/_internal/config.json
```

`bigfish/desktop.py` 里以前有两处 `CONFIG_PATH` 定义，后一处静默覆盖前一处。
照着第一处去改外层 `config.json` 改了也不会生效 —— 已经删掉。

`tools/deploy.py` 覆盖 `_internal` 时会显式保住这个文件。
以前它写「config.json 未动」，其实只是恰好新包里没带 config.json；
一旦带了，账号 / 监听名单 / 主人会一起没，而且没有任何提示。
