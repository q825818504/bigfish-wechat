# 多会话并发与投递

> 2026-11-08。起因：用户问「多个会话同时说话，她顾得过来吗」。
>
> **当天已按 P1+P2 落地**：`bigfish/desktop.py` 的 `_deliver` / `_gen_worker` /
> `_send_worker`，以及 `wechat_sender.UiaSender` 的 `@_serialized_send`。
> 第 5 节的 P3（优先级、超时、结构化观测）仍然待做。

---

## 1. 现状：能听到，但排队

```
watcher（1.2s 轮询）
  └─ enqueue（立刻返回，不阻塞轮询）
       └─ MessageBatcher（按会话分桶、防抖封批）
            └─ bigfish-batch（**唯一线程**）
                 └─ for batch in tick(): handle_batch(batch)   ← 串行
                      ├─ 模型 2~16s
                      ├─ UIA 发送 4~8s
                      └─ 后置挑图（模型）0~40s
```

`handle_batch` 是同步阻塞的，所以：

| 场景 | 用户感知 |
|---|---|
| 1 个会话 | 正常，5~10 秒回一条 |
| 2 个会话同时说 | 第二个等第一个处理完，10~20 秒 |
| 3 个会话同时说 | 最坏 30~50 秒 |
| 任一轮触发后置挑图 | 全队列再 +10~40 秒 |

代码里自己写着这句：

> ⚠ 这一段是**串行**的：挑图要调一次模型，跑完引擎才回去收下一条消息。
> 花 40 秒的话，用户看到的就是"聊几句之后突然安静"。

## 2. 参考：MaiBot 与 AstrBot 怎么做的

| | MaiBot | AstrBot companion_v2 | 大肥鱼（现在） |
|---|---|---|---|
| 运行时 | asyncio 事件循环 | 宿主事件循环 + durable task | Qt 线程 + 同步 requests |
| 每会话隔离 | `BotChatSession` / `SessionContext` | `conversation_flows`，每会话一条 flow | `convs` dict（仅数据隔离） |
| 防抖 | `chat/debounce/controller.py` | `ConversationPolicy.quiet_seconds` | `MessageBatcher` |
| 状态机 | 无显式三态 | **collecting → generating → delivering** | 无（一把梭） |
| 执行层 | `create_task` 并发 | SQLite 任务表 + lane + fence（`execution/service.py`） | 单线程 |
| 发送 | `uni_message_sender` 统一出口 | `delivery` 单独一层 | `handle` 内联 |
| 延迟/忙碌 | 无 | `busy_gate`：把 `due_at` 往后推，不 sleep | 无 |

**可以直接借的三条**：

1. **AstrBot 的三态**：收集、生成、投递是三个阶段，各自有独立的超时与重试。
   一个阶段的慢不该拖死另一个阶段。
2. **AstrBot 的 defer 而不是 sleep**：忙碌/冷却把 `due_at` 往后推，
   已经入批的消息不丢、不打断，只是晚一点封批。
   这比"在任务里 sleep 然后取消"干净得多 —— 后者会留下半截状态。
3. **MaiBot 的统一发送出口**：平台写入只有一个地方，业务层只产出"要发什么"。

**不该照搬的**：AstrBot 的 SQLite 任务表 + fencing（为了跨进程重启恢复）；
它在单人桌面场景是纯负担。我们只要内存队列 + 线程。

## 3. 硬约束（决定架构的三件事）

1. **UIA 只能串行**。一个微信窗口、一个输入框、一个剪贴板。
   两个线程同时 `send()` 会互相踩，发错人。
2. **模型调用是同步 requests**，会阻塞所在线程 2~16 秒。
3. **Qt 主线程不能阻塞**，引擎线程也不该被长任务占死（现在是 batch 线程被占）。

推论：
- 生成可以并行（每线程一次 HTTP）。
- 发送必须单点（唯一 worker），且热激活、窗口检查、表情包也归这条线。
- 同会话必须串行（否则上下文错位、记错账）。

## 4. 目标架构

```
watcher ──enqueue──► batcher（按会话防抖，带 post_reply_grace）
                         │  封批
                         ▼
                    gen_queue  (有界，默认 32；满则丢弃最旧并记日志)
                    ┌────┴────┐
              gen_worker   gen_worker        ← 2 个（可配 1~3）
                    │            │
         per-chat lock：同一会话同时只有一轮在生成
                    │            │
                    └────┬───────┘
                         ▼
                     outbox  (FIFO；按 chat 保序)
                         │
                    send_worker（唯一）
                    ├─ 窗口检查 / 热激活
                    ├─ open_chat → 逐条发送（条间停顿）
                    ├─ 记账（remember_sent / guard）
                    ├─ 后置表情（挑图已在 gen 阶段完成，这里只发）
                    └─ [发] / [记] 日志
```

### 4.1 三个阶段各自做什么

| 阶段 | 线程 | 职责 | 超时 |
|---|---|---|---|
| collecting | batcher（已有） | 防抖、合并、@ 优先、回复后冷却 | `max_wait` |
| generating | gen_worker × N | 记忆检索、prompt 拼装、调模型、分条、**挑图** | `turn_timeout` 90s |
| delivering | send_worker × 1 | 窗口检查、开会话、发送、记账、表情 | 单条 30s |

### 4.2 每会话串行，跨会话并行

- `chat_locks: dict[str, threading.Lock]`，gen_worker 拿到批次先 `acquire`。
- 同一会话的第二批会等第一批生成完 —— 保证"她记得自己刚说了什么"。
- 不同会话互不影响，2 个 worker 就能让"两个人同时找她"都得到秒级响应。

### 4.3 后置挑图归位

现在它在 batch 线程里串行跑（0~40 秒），是最大的单点。
归位后在 gen_worker 里跑：**只影响这一条消息什么时候进 outbox**，
不影响其他会话。并且给它单独预算（`sticker_budget = 8s`），超时就发文字。

### 4.4 发送单点

- `send_worker` 是唯一持有 UIA 的线程。
- `parts` 的条间停顿、`remember_sent` 的先后顺序（先记账再回车）都留在这里，
  **不搬到 gen 阶段** —— 那里还不知道会不会发。
- 发送失败/未知的判定（`sending.Outcome`）原样保留。

### 4.5 背压与合并

- `gen_queue` 有界：满了丢**最旧**的待生成批次，记 `[丢弃] 队列满`。
  宁可少回一句，也不要越排越久。
- 同一会话在 gen 期间又来消息：进 batcher 的新桶，等这一轮投递完再生产
  （`post_reply_grace` 已经把这种"补一句"合并过一轮）。
- 被 @ / 主人对话可以加 `priority` 字段，插到 outbox 前面（Phase 3）。

### 4.6 超时

- `turn_timeout`（默认 90 秒）：gen 阶段超时 → 丢弃这一轮，日志 `[超时] 生成超时`，
  不发送。避免"十分钟后突然冒出一句三天前的话"。
- 投递单条 30 秒（UIA 有时会卡）。

### 4.7 可观测

每轮一条结构化记录（写入 `data/prompts/` 或独立 jsonl）：

```
{chat, t_recv, t_gen_start, t_gen_end, t_send_start, t_send_end,
 wait_ms, gen_ms, send_ms, parts, sticker, outcome}
```

排查"她为什么慢"时不用再靠猜。

## 5. 落地顺序

| 阶段 | 内容 | 改动面 | 风险 | 预计 |
|---|---|---|---|---|
| **P1** | 发送抽成单 worker + `_send_lock`；后置挑图移出 batch 线程 | `desktop.py` 发送段 | 低 | 半天 |
| **P2** | gen_worker 池 + per-chat 锁；`convs` 加锁 | `_run` 的 batch/handle 拆分 | 中 | 1~2 天 |
| **P3** | 优先级、超时、结构化观测 | 新增小模块 | 低 | 半天 |

**P1 就能吃掉 80% 的体感问题**（后置挑图不再拖全队列）。
P2 才解决"两个会话同时说话"的排队。

---

## 6. 风险清单

| 风险 | 说明 | 对策 |
|---|---|---|
| `convs` 并发读写 | 两个 worker 同时改同一会话的 hist | per-chat 锁；hist 只在 gen 阶段写 |
| `_life` / `_policy` 主线程写、worker 读 | 读到撕裂的值 | 每轮开始快照一份，worker 只读快照 |
| `_sticker_sent` 冷却表 | 多 worker 同时读改写 | 加锁 |
| UIA 对象跨线程 | 现在已经是跨线程（batch 线程用引擎线程创建的对象） | 统一收进 send_worker，不再扩大 |
| 发送顺序 | 不同会话的 outbox 交错 | 允许；同一会话保序即可 |
| 表情包与文字顺序 | 先文字后表情是产品语义 | outbox 条目里带 `sticker`，send_worker 按序发 |

---

## 7. 刻意不做

- **不为并发做 asyncio 重写**：UIA 是同步的，asyncio 在这里只增加复杂度。
- **不做跨进程 durable 队列**（AstrBot 那套）：单人桌面，重启丢一轮可以接受。
- **不让多个线程同时用 UIA**：这是硬约束，任何"并行发送"的方案都直接否掉。
- **不做"批量多会话一次 prompt"**：上下文会糊，人格会串。

---

## 8. 验收

- 两个会话同时发消息：两边都在 10 秒内得到回复（现在第二个要等 10~20 秒）。
- 触发后置挑图时，另一个会话的回复不受影响（现在会被拖 10~40 秒）。
- 同一会话连发三段：只回一次，且内容覆盖三段（现在已由 batcher + grace 保证）。
- 压测：3 个会话各发 5 条（间隔 2 秒），全部有回复、无串会话、无自环。
- `[发]` 日志顺序与微信界面一致（同会话严格保序）。
