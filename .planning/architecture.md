## 自环：四道闸

11-04 那晚她自问自答十几条。复盘下来不是"某个开关忘了关"，
是**四个环节各自缺一样东西**，所以是四块结构，不是四道补丁。

```
消息进 → ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ → 发送
        │ ①判身份   │→ │ ②查账本   │→ │ ③群闸门   │→ │ ④信封     │
        │ identity │  │ ledger   │  │group_gate│  │ sending  │
        └──────────┘  └──────────┘  └──────────┘  └──────────┘
             │             │             │             │
         自己？对方？    这句我发过吗   叫了她吗？    发没发出去？
         还是拿不准？    是 → 否决     否 → 不回    不知道就别重发
```

| 闸 | 回答的问题 | 拿不准时倒向哪边 |
|---|---|---|
| `identity` | 这条是谁说的 | 私聊**不回**；群里**等闸门**判"叫没叫她" |
| `ledger` | 但我刚发过这句吗 | 命中就否决判据（留痕 `ledger_veto`） |
| `group_gate` | 群里这条冲她说的吗 | 不叫就不接（免检群不算"叫她"） |
| `sending` | 到底发出去没有 | 按**未知**处理：不重试、不撤账、告诉用户 |

四个都是"拿不准就闭嘴"，方向一致：**漏回一次的代价，远小于自环一晚。**

配置在 `scopes.py` 里定归属 —— `allow_self` 只对文件传输助手生效，
写会话层不写全局，否则等于"所有会话都能回应自己"，那正是事故的形态。

### 本轮新增的两块

`vault.py` 和 `mood_judge.py` 是补「写路径」时加的。之前只有读：
聊天记录读得出来、记忆检索得出来、心情读得出来 —— 但**一行都不写**。
所以聊一晚上，记忆页和心情页永远是 0。

### v0.4.0：说法层与倾听层

入站多了一道「攒批」，出站多了一道「分条 + 节奏 + 确认」：

```
微信库 ──▶ watcher ──▶ MessageBatcher ──▶ EngineWorker.handle ──▶ 模型
                          （倾听层）                                │
                                                                   ▼
                                                        say.split_reply（分条）
                                                                   │
                                                        say.plan_pacing（停顿）
                                                                   │
                                                    say.send_parts（逐条确认）
                                                                   │
                                                                   ▼
                                                              UIA 发送
```

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `listen.py` | 把逐条消息攒成一批 | 纯状态机 `feed`/`tick`，时间由调用方给；硬上限 8s / 8 条 |
| `say.py` | 分条 / 节奏 / 发送确认 | 纯函数 + 注入式 IO（`send` 与 `read_recent` 都是参数），假对象可测 |
| `plugins/say.py` | 面板参数 + 提示词 | 座位 890；两个入口每轮现读同一份 `plugins.json` |

**为什么拆成「核心模块 + 插件」**：分条与攒批是发送层能力，不该由 prompt 决定；
插件只提供参数与风格提示。关掉插件仍能分条（用默认值），只是不再提示模型说短句。

**为什么确认放在核心层**：它是「一条发出去没有」的事实判断，
不属于任何一个可关的功能。关掉说法层也要知道消息发没发出去。

## 为什么这样分层

### 读写分离

读取走数据库（只读、快、不需要界面、不抢焦点）。
发送走 UIA（必须操作界面，因为微信 4.x 的自绘 UI 没有别的写入接口）。

两者互不依赖，任一失败不影响另一个。

### 人格与协议分离

```
system  = 人格（灵魂）+ 这会儿的状态（情绪）
user    = 你记得的事（记忆）+ 这一轮怎么答（协议）+ 对话记录
```

人格里不放任何输出格式规则。灵魂只定义「我是谁」，不该被
「别用 Markdown」这种要求污染。

### 用 Node 而不是 Python 重写记忆检索

`dsh-bigfish` 的记忆检索有中文二元分词、半衰期衰减、FTS5 索引、
session scope 过滤。Python 重写必然产生偏差，结果是
「微信里的大肥鱼」和「DSH 里的大肥鱼」记得不一样的事。

`bridge.mjs` 直接 `import` 原版模块调用，逻辑零偏差。

## 数据流：一条消息的完整旅程

```
1. 手机发「在吗」
2. 微信写入本地 SQLCipher 数据库
3. MessageWatcher 轮询发现 sort_seq 变大
   取出消息，render.py 语义化
4. **LoopGuard.admit()** 四层闸门（见下节「自环防护」）
   放行后才继续；自己发的消息在这里被拦掉
5. GroupGate 判定（私聊直接过）
6. BigFishApp 组装 prompt：
     system = soul.render_persona() + mood.injected_text
     user   = memory.recall("在吗") + 协议 + 最近对话
7. 调模型，1-2 秒返回
8. UiaSender:
     open_chat("老爸")  → 校验 current_chat
     定位 mmui::ChatInputField → 校验 Name
     写入文本 → 回车
9. 微信把消息发出去，写回数据库
10. **发送之前**就 guard.note_sent(part)（乐观记账），
    发失败 guard.rollback_sent()。注意顺序 ——
    发完再记账有竞态窗口（见下节）
11. **发送成功之后**（这一步以前完全没有）：
      vault.record_exchange()  → 一问一答两条进记忆库
        · event_key = wx-u-<local_id>，幂等
        · 640 步长 / 800 窗口切片
        · memory_terms() 中文二元分词进 FTS
      mood_judge.judge_and_apply()  → 后台线程
        · 调模型判断 {moodDelta, dims, reason, confidence}
        · 衰减 → 缩幅 1/3 → 写 mood.json → 追加 timeline
```

**为什么写在第 11 步而不是第 6 步**：
第 6 步只是"准备要说的话"，那时还没发出去。
没发出去的一轮不算对话发生过 —— 记了会让记忆里多出她从没说过的内容。

## 自环防护：一条消息回到自己身上时

UIA 发出去的消息会立刻被自己的监听器读回来（同一个数据库）。

```
她发 → 微信写库 → watcher 读到 → 判定这条该不该回
```

如果判定错了，就进入**她自己跟自己聊**的循环。2026-11-04 真发生过一次，
两分钟十几条，只能杀进程。

`bigfish/loopguard.py` 的四层闸门：

| 层 | 机制 | 挡住什么 |
|---|---|---|
| L0 | 静音 | 熔断后该会话完全不处理 |
| L1 | 白名单 | `allow_self` 只对 `filehelper` 生效；私聊/群聊就算开着也拦 |
| L2 | 乐观记账 | 发送**之前**记账、失败回滚 |
| L3 | 轮级熔断 | 连续 4 轮自动回复且中间无对方消息 → 静音 120 秒 |

### 为什么不能只靠「精确识别」

L1（`is_self`）和 L2（内容比对）都是**精确判断**：判断对了没事，错了没兜底。

而 L2 有天然竞态：UIA 按回车就返回，微信**异步**写库。发完再记账的话，
数据库可能先落地、watcher 恰好在这一刻轮询到 —— 这条就"没有账可对"。
1.2 秒一轮窗口很窄，但聊一晚上必然撞上；撞上就是正反馈。

所以：**顺序反过来**（先记账再发），外加 L3 做症状级兜底。
L3 不看原因只看症状 —— "连续 4 轮回复之间一句对方的话都没有"，
这个判据不可能是正常聊天。

### 为什么 L3 按「轮」不按「条」

一次回复分 2~4 条发出去，那是**一轮**。按条计会把分条功能本身判成自环。

### 为什么对方不会被误杀

`is_self=False` 时 `admit()` 直接放行并清零计数，**不做任何内容比对**。
早期版本靠"文字相同"判回环，老爸原样复述她的话（聊天里极常见）被拦过两次。

## 发表情：第二条发送通道

文本和媒体走两条不同的路，因为它们的坑完全不同。

```
send()        文本
    定位 ChatInputField → 校验 Name → Ctrl+V 打字 → 回读比对 → 回车

send_media()  图片 / GIF 表情
    _materialize()          临时目录的文件搬到 <数据目录>/_outbox/
    _focus_input_hard()     三层聚焦
    _write_clipboard_files  powershell Set-Clipboard（写全五种格式）
    Ctrl+V                  keybd_event
    彩色占比 ≥ 2%          判草稿进没进
    回车
    verify_media_sent()     回读数据库，只认 type='动画表情'
```

### 为什么媒体要多这么多步

文本粘贴是控件级操作，Edit 控件自己就会处理。
文件粘贴是**富操作** —— 微信要去读剪贴板、造附件对象、塞进编辑框，
中间任何一环出问题都是"什么都没发生"，而且不给任何错误提示。

四个真机踩出来的约束：

| 约束 | 表现 | 解法 |
|---|---|---|
| 剪贴板要五种格式 | 格式检查通过，粘贴时一个像素不变 | `Set-Clipboard` 而不是手拼 `DROPFILES` |
| **不能是临时目录** | 同上，且更难查 | `_materialize()` 搬到 `_outbox` |
| 焦点要三层 | 前台是微信但按键打空 | `ensure_visible` + `SetFocus` + 真实点击 |
| 判据要看颜色 | 灰度差 5.9 卡在阈值 6 下面 | 彩色像素占比 ≥ 2% |

### 为什么成功与否只信数据库

`SendKeys("{Enter}")` 返回成功只代表"按键按下去了"。
发没发出去，只有微信自己的数据库知道。

所以 `send_media` 的最后一步永远是 `verify_media_sent()`，
10 秒内没有 `type='动画表情'` 的新消息就抛错。
**不允许出现"日志说成功、用户什么都没收到"。**

## 表情包的数据

```
<数据目录>/stickers/            她的表情库（用户攒的 / 程序生成的）
<数据目录>/stickers/index.json  每张一句话，插件靠它判断该不该用
<数据目录>/_outbox/             发送暂存（用完即删）
<数据目录>/sticker-config.json  开关、频率、冷却
<数据目录>/sticker-usage.json   发过什么（冷却和"别连着发同一张"）
```

**清空保留 `stickers/`，鲸落才删。**
清空是"她忘了"，可表情包是用户攒的，不是她的记忆 ——
把用户几十张表情一起删掉，那是删用户的文件。

**`_outbox` 不参与清空/鲸落的统计**：它是临时区，里面不该有长期文件。

## 表情挑选：先对维度，再对强度

```
挑表情前
  ↓
_current_mood() 读最新落盘的 mood.json
  ↓  {value: 72, label: "心情不错", dims: {happy: 45, sweet: 12}}
_mood_line() 压成两三行
  ↓  "她现在的心情：心情不错（72/100）"
     "情绪偏向：开心 45、甜蜜 12"
候选列表（每张带维度和强度）
  ↓  "- stk_0007 [动图·强度5·开心] 笑到打滚"
模型
  ↓  先看这句话什么情绪 → 再看她哪个维度活跃 → 挑匹配的
代码
```

### 为什么心情要重新读一次

引擎每轮开始时的 `ctx.mood` 是**这一轮开始时**的快照。
而心情判断是**上一轮发送成功后**异步写盘的 —— 慢一拍。

用快照的话，用户刚说了件开心事、她被哄好了，这一轮挑表情却还是
按旧心情挑。读一个几百字节的 JSON 成本可以忽略，而这个差异
用户能感觉到。

### 为什么强度和维度存字段而不是每次推

「这张图有多强烈」「它属于哪类情绪」是**图的固有属性**，
一次判断长期复用。让模型每次重推，同样的图这次判 3 下次判 4，
挑出来的结果就飘了。而且 detail 有 200 字，几十张塞进 prompt 会爆。

### 为什么允许「不归类」

七根维度覆盖不了「无语」「疑惑」「震惊」。硬塞进 happy 或 sad
会让匹配变差 —— 她难过的时候收到一张"无语"的表情，看着莫名其妙。
空表示"任何心情都能用"，这比强行归类准确。

## 拖放：三条路只有一条通

| | 做法 | 结果 |
|---|---|---|
| ① | HTML5 `dataTransfer.files` | QtWebEngine 里没有 `path` 属性 |
| ② | QWidget eventFilter + OLE | 管理员权限下被 UIPI 拦住 |
| ③ | **原生 `WM_DROPFILES`** | 通了 |

**真正的冲突**：窗口只要注册了 OLE drop target，系统就只走 OLE，
再也不发 `WM_DROPFILES`。而 OLE 在管理员权限下被 UIPI 卡死
（本程序要 UIA 必须是管理员，资源管理器是普通权限）。

两条路互相打架，只能选一条。选 `WM_DROPFILES`：

```
RevokeDragDrop(hwnd)        撤掉 OLE 注册
DragAcceptFiles(hwnd, TRUE) 让系统走老式路径
QAbstractNativeEventFilter  全局拦消息
DragQueryFileW              逐条取路径
DragFinish                  必须调，否则第二次拖放失败
```

代价：网页内部的拖放失效。我们不需要那个。

日志写到 `<程序目录>/data/_drop.log` —— 界面在管理员权限下跑，
看不到控制台，出问题只能靠这个。

## 引擎线程模型

```
主线程 (Qt)
  └── QWebEngineView   界面
  └── Backend          Slot 接口
        ↕ 信号
  QThread (EngineWorker)
        └── MessageWatcher（内部再起一个轮询线程）
        └── 模型调用（阻塞，但不影响界面）
        └── UIA 发送（阻塞）
        └── threading.Thread × N  心情判断（daemon，跑完就退）
```

**心情判断为什么要单起线程**：
它要调一次模型（1~2 秒）。如果同步做，两条消息紧接着来时会明显卡顿 ——
用户会觉得"她怎么突然不理我了"。而心情是**事后记录**，晚两秒完全没关系。

用最朴素的 `threading.Thread(daemon=True)` 而不是 QThread：
它不碰任何 Qt 对象，只做 HTTP + 写文件，跑完就退。
要往界面吐日志时走 `self.log.emit()`（signal，跨线程安全）。

界面每 2 秒轮询 `get_status`，日志通过信号推送 + 缓冲区补漏。

## 写层：`bigfish/vault.py`

```
            读路径                        写路径
  ┌──────────────────────┐     ┌──────────────────────────┐
  │  bridge.mjs (Node)   │     │  vault.py (Python)       │
  │  import 原版 store.js │     │  逐字段复刻 store.js 语义 │
  └──────────┬───────────┘     └────────────┬─────────────┘
             │                              │
             └──────────► 同一批文件 ◄───────┘
              soul-*.json / mood-*.json / memory-*.sqlite3
                          scope.json / root.json
```

**为什么读走 Node、写走 Python**
读要的是**分词与衰减算法**（中文二元分词、半衰期、FTS5），
在 Python 里重写必然漂移 —— 会让微信里的大肥鱼和 DSH 里的记得不一样的事。
写要的是**结构归一与原子性**，那是纯规则，逐条复刻即可，而且必须能在
没有 Node 的 exe 里跑。

**三条不能破的约束**（全部有测试钉住）

1. **原子写**：同目录 `.tmp` → `os.replace`。
   跨盘 rename 会抛；写一半断电不能留下半个灵魂文件。
2. **归一化永不抛错**：任何输入都夹成合法结构。
   未知 trait 键丢弃；`values: []` 是真实意图，**不能**偷偷补回默认值。
3. **revision 每次写盘 +1**：面板靠它检测并发。

**删除记忆的级联顺序**（踩过的坑）
`chunks.message` 是外键，`foreign_keys=ON` 时先删 messages 会抛约束错误。
正确顺序：FTS → chunks → anchor_sources/activations/groups/replays → messages。
漏掉 FTS 的表现是「检索命中了已经不存在的内容」—— 比删不掉还难查。

## 存储布局：一个数据目录 = 一份

```
<数据根>/                     ← root.json 里的 dataRoot
  ├── soul.json               她是谁
  ├── mood.json               此刻怎样
  └── memory.sqlite3          她记得什么
```

没有「范围」这个概念。换数据根 = 换一个人。

**老布局兼容**（`<数据根>/ws-<uuid>/soul-ws-xx.json` 那套）：
- `legacy_layout()` 找出"有灵魂的那一份"（带灵魂才算真正在用）；
- `existing_path()` 新布局没有就顺着老路径读；
- `migrate_legacy()` 由用户点按钮迁移，不自动做。

**为什么保留兼容而不是直接删老的**：
用户的老数据可能是几个月攒下来的。升级一次就"记忆全没了"是不可接受的，
哪怕技术上更干净。所以读要兼容，写只走新路径。

**清空的顺序**：盘点 → 备份 → 删。备份失败就中止，什么都不删。
灵魂永远保留（`keep_soul=True`）—— 清记忆不等于洗掉人格。

## 数据目录：默认在安装目录，可改

```
<安装目录>/
  ├── BigFish.exe
  ├── ui/  bridge/
  ├── _internal/           ← PyInstaller 运行时（升级会整个替换）
  ├── settings.json        ← 用户改过的位置（**不放 data/ 里**）
  └── data/                ← 默认位置，她的全部
       ├── soul.json
       ├── mood.json
       ├── mood-config.json
       └── memory.sqlite3
```

解析顺序：`BIGFISH_DATA_ROOT`（测试）→ `settings.json` → `<安装目录>/data`。

**settings.json 为什么不放 data/ 里**：改位置时它会跟着数据搬走，
程序下次启动就找不到新地址。配置必须待在一个固定位置。

**为什么不用 `_MEIPASS`**：onedir 模式下它是 `_internal/`，
用户升级时会被整个替换掉 —— 数据放那里等于每次升级清空。

**为什么默认放安装目录而不是 `%APPDATA%`**：
用户明确要求。便携版拷走就能带走她，这是实际好处。
但**不是定死** —— 装 C 盘的人可以把数据挪到 D 盘，
见「改位置」一节（D-19）。

**启动流程**（`vault.ensure_data_root()`）：
```
建 data/  → 测可写  → 有 soul.json? → 有：什么都不做
                                    → 无：DSH 有? → 有：导入一次
                                                  → 无：出厂模板
```

**与 DSH 的边界**：

| 动作 | 允许？ |
|---|---|
| 读 DSH 的 soul（首次导入） | ✅ 只做一次 |
| 读 DSH 的 sessions / workspace.json | ❌ 永不 |
| 写 DSH 的任何文件 | ❌ 永不 |
| 读 DSH 的 mood 配置作初始值 | ✅ 只读回落 |

最后一条是刻意的：插件那份 `bigfish-mood/config.json` 里有用户调过的参数
（基线 70、半衰期 12h 之类），第一次用直接沿用比从头调好。
但**写**永远写本地的 `data/mood-config.json`。

## 改位置：「改指向」和「搬数据」是两件事

界面上是两个按钮，不是一件事，因为后果完全不同：

| 操作 | 做什么 | 陷阱 |
|---|---|---|
| 只改指向 | 只写 `settings.json` | 新目录是空的话，打开是出厂人格 |
| 搬过去（连同数据） | 先 `copytree`，**成功后才**改指向 | 顺序反了会指向空文件夹 |

**`apply_move()` 的顺序不能反**：
```
1. 复制全部内容到 dst
2. 复制成功 → set_data_root(dst)
3. 源目录改名 .old-<时间戳>（不直接删）
```
任何一步失败都在**改指向之前**返回。反过来的话，复制一失败，
数据目录就指向一个空文件夹 —— 用户打开会以为"人格没了"，
那是最吓人的一种失败。

**为什么源目录不直接删**：搬家是最不可逆的操作之一。
改名留着，用户确认没问题了自己删。

| 操作 | 删什么 | 保留什么 | 护栏 |
|---|---|---|---|
| 清空 | 心情 + 记忆 | **灵魂**（她还在，只是忘了） | 自动备份 |

### 模块地图（新增部分）

```
bigfish/
  memory.py        记忆核心：原文/事实/习惯/身份 四层 + 检索 + 反思
  plugins/         插件系统：座位校验、开关落盘、分发、清单

    guard.py         末尾守卫（order 9990）
    clock.py         时间感知（order 870）
  wechat.py        多账号探测（probe_running_accounts）
```

### 记忆四层

```
原文层  messages / chunks / search_index     权威，可重建派生层
事实层  facts                                可纠正 / 可遗忘 / 可置顶
习惯层  habits                               三次 + 跨三天 + 衰减
身份层  owners / persons                     谁是谁（跨平台）
```

派生层（`search_index` / `chunk_meta` / `facts` 索引）全部可抛弃重建，
`rebuild_derived()` 一处收口。

### 注入时的一次判断

```
facts_for_prompt(owner, tier)
    → 展开 owner_persons(owner)          # 同一人的所有平台账号
    → scope_filter(owner, tier, siblings)
        WHERE owner IN (我的所有账号) OR visibility IN (shared, public)
    → 置顶走独立预算，普通走常规预算
```

**只有这一处做隔离判断。** 其他任何地方再写一遍，迟早会出现两套规则。

### 插件座位制

system 段不再按 append 顺序拼，而是按**座位号**排序：

```
850 记忆（内建）
860 灵魂（内建）
870 生活   872 日程   880 目标（空位，暂无插件）
890 说法
900 心情（内建）
930 余韵
9990 守卫
```

`SEATS`（展示给用户的身份序）只列**真实存在的段**；
`PLUGIN_SEATS`（注册校验用的空位表）保留了 880 —— 两件事分开，
否则用户会在插件页找一个不存在的「目标」插件。

插件注册时必须声明座位，占错直接抛错。
理由：多段叠加时顺序决定语气，而"排到末尾"取决于 import 顺序 ——
那是个跟内容无关的实现细节，不该影响她说话的方式。

### 账号选择的进程探测

```
probe_running_accounts()
    枚举 xwechat_files/<账号>/db_storage/message_0.db
    CreateFileW(dwShareMode=0) 试开
      失败 = ERROR_SHARING_VIOLATION = 微信正占着 = 这个号在运行
```

这是唯一与真实进程挂上钩、又不需要读加密内容的信号。
（mtime / msvcrt 锁 / sqlite BEGIN IMMEDIATE 都试过，全部无效，详见 decisions D-33）

## v0.2.1：记忆的边界

### 事实的三个新维度

```
facts
  owner       属于谁       private:wechat:<id> / group:wechat:<id>
  visibility  谁能看见     private / shared / public
  origin      在哪儿说的   private / group:<群id> / (空=不知道)
  topic       讲的哪类事   19 个值，分白/黑/灰三档
```

`origin` 必须和 `owner` 分开存。群聊双写之后，同一句话在「人池」和「群池」
各有一份 —— **owner 不同，但 origin 相同**。只有分开存，才说得清
"这句话是在群里说的"。

### 群聊双写

```
                  ┌──────────────┐
群里 A 说一句 ────┤ 反思产出事实  │
                  └──────┬───────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
      A 的私聊池              群 C 的池
      (一定写)          (只有不算私密的才写)
    origin=group:C          origin=group:C
```

判定「不算私密」：

```python
publicish = visibility in (shared, public) or topic_allowed(topic)
```

两个"公开信号"有一个就够 —— 标了 shared 已经是显式授权，不必再打标签。

### 两套判定必须分开

这是本版最容易踩错的地方：

| 函数 | 回答 | 看 tier 吗 |
|---|---|---|
| `visible_visibilities(tier)` | 谁在**界面/提示词**里看得见 | 看（主人=全部） |
| `open_facts_for(owner)` | 她**说得出**哪些 | **不看**（所有人只看开放信息） |

`facts_for_prompt` 永远只装两样东西：
**「你自己的」+「所有人的开放信息」**，主人也不例外。

因为「跟 A 说话时脑子里装着 B 的秘密」和「B 能不能看到」是两件事。

### 三道闸门

```
第一道：owner + visibility     谁能看见这条事实
第二道：topic 白名单            这条能不能说给外人
第三道：guard 插件             被追问时守住（不点头、不否认）
```

少任何一道都会漏：
- 只有第一道 → 标了 shared 的住址会被端出去
- 只有前两道 → 「你主人是不是住在朝阳区？」试一下就出来了

### 印象页的数据流

```
impression_board()
  ├── owners 表 → 谁都在这一格
  ├── impressions 表 → 你手写的评语（模型不参与）
  └── open_facts_for() → 开放信息清单（实时查，不存副本）
```

开放信息**不存副本**是刻意的：存一份就等于给"她准备说什么"开了第二个真源，
两边一定会漂。

「删除」= `revoke_open()` = visibility 退回 private + topic 清空。
**不是 `forget_fact()`** —— 事实还在，她照样拿它当结论，只是不再对外提。

## v0.3.1：记忆的四层取用

```
                        ┌─────────────────────────────┐
   对话 ─────────────►  │ messages / chunks / FTS     │  原文（只增不减）
                        └──────────┬──────────────────┘
                                   │ 检索时
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
              bm25 排序       命中权重 +0.15   MMR 去冗余
                    └──────────────┴──────────────┘
                                   │
                                   ▼
                          ## 你记得的事（2400 字）

                        ┌─────────────────────────────┐
                        │ facts（几千条）              │
                        └──────────┬──────────────────┘
                                   │ 取 24×N 条候选
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
              取用分数        相关性        置顶必进
          conf×decay+use   question 共词    你钉住的
                    └──────────────┴──────────────┘
                                   │
                                   ▼
                          ## 你认定的事（十几条）
                                   │
                                   ▼ 每轮记一次 mark_used
                          last_used_at / use_count

                        ┌─────────────────────────────┐
                        │ profiles（每人一段）         │
                        └──────────┬──────────────────┘
                                   │ 每轮必带，enabled 才注入
                                   ▼
                          ## 你印象里的他（400 字）
```

### 三个时间尺度的分工

| 层 | 更新频率 | 谁写 | 影响 |
|---|---|---|---|
| 原文 | 每条消息 | 程序 | 检索命中才有用 |
| 事实 | 攒够一批反思 | 模型 | 逐条的、可纠正的 |
| 画像 | 事实涨 40 条触发 | 模型 | 每轮都带的概述 |

**画像不是压缩**。它和事实**并存**：
- 事实一条不少，检索照样翻得到原话
- 画像只是多出来的一份"整段概述"，每轮都能进提示词

所以它不违背「硬盘多大记忆就多大」——
硬盘上是"完整 + 概述"两份，不是"完整被换成了概述"。

### 取用分数

```python
score = confidence × decay + use_count × 0.03
decay = 0.5 ** (距上次使用天数 / 90)
```

设计要点：
1. **从没用过的按 decay=1 算** —— 否则升级当天所有老条目一起沉底
2. **半衰期 90 天**，不是 MaiBot 的 24 小时（那是给闲聊调的）
3. **用得多的加分上限 0.03/次**，避免老条目霸榜

### 补搜

```
第一次检索结果 < 2 条
    ↓
用最近三轮对话当查询
    ↓
再查一次，结果合并
```

这是「让模型主动查」的穷人版：不改架构，只在明显没料时补一枪。

## 模型接入：三条路与三种协议

```
                ┌─────────────────────────────────────────┐
   设置页  ───►  │ config.json 的 llm 段                    │
   选一家/填Key  │  channel / base_url / model / api_key    │
                │  protocol / temperature / max_tokens     │
                └────────────────┬────────────────────────┘
                                 │
                    ModelConfig.load()
                                 │
              ┌──────────────────┴───────────────────┐
              │  预设兜底：bigfish/providers.py       │
              │  空字段 → 取预设的 base_url / protocol │
              │        / 模型列表第一个               │
              └──────────────────┬───────────────────┘
                                 │
                        call_model(cfg, system, user)
                                 │
        ┌────────────────┬───────┴────────┬────────────────┐
        ▼                ▼                ▼                ▼
    openai           anthropic         gemini           错误处理
    Bearer           x-api-key         ?key=            翻中文
    messages[]       system 顶层       systemInstruction 401/404/429…
    choices[0]       content[]         candidates[0]
```

### 三条路

| channel | 谁用 |
|---|---|
| 预设 id | 绝大多数人：选一家，粘 Key |
| `custom` | 中转站、公司内网、自建服务：填 base_url + 模型 ID |
| `magpie` | 本机或别人的 Magpie 网关：不用 Key |

预设是**填好的默认值**，不是白名单。地址、协议、模型三项都能改 ——
这个设计很重要：预设写错了不致命，用户改一次就好。

### 三种协议不是「换个地址」

| | OpenAI 兼容 | Anthropic | Gemini |
|---|---|---|---|
| 认证 | `Authorization: Bearer` | `x-api-key` + `anthropic-version` | `?key=` 查询串 |
| system | `messages[0]` | **顶层 `system`** | `systemInstruction` |
| 正文 | `choices[0].message.content` | `content[]` 挑 `type=="text"` | `candidates[0].content.parts[]` |
| 推理 | `message.reasoning_content` | `content[]` 挑 `type=="thinking"` | `parts[]` 挑 `thought: true` |
| token | `max_tokens` | `max_tokens` | `generationConfig.maxOutputTokens` |

三个必须记住的：Anthropic 的 system 不能塞 messages（400）；Gemini 的 key
不能放请求头（400）；Gemini 的模型名在 URL 里不在请求体里。

### 为什么不用 SDK

`openai` + `anthropic` 两个包 10MB+，而实际要的只有「发一个 POST、取一个
字符串」。这个程序打包已经 201MB，不值得再肥。urllib 够用，
而且三种协议的细节控制在自己手里 —— 用 SDK 反而要为「兼容层怎么翻译」
再查一遍文档。

### 地址归一化

用户粘 `https://api.deepseek.com/v1/chat/completions` 是最常见的事。
不剥后缀会拼成 `.../chat/completions/chat/completions`，报一句 404 ——
而用户"明明填对了"。`normalize_base()` 统一剥掉 `/chat/completions`、
`/messages`、`/models/xxx:generateContent` 这类尾巴。

### 测试连接为什么要真发请求

只检查字段填没填，验不出 Key 无效、地址不通、模型名不存在 —— 这三样
恰好是第一次配置最容易撞的。真发一次 `max_tokens=24`，0.5~3 秒出结果。

Qt 的 slot 跑在 GUI 线程，同步做会把窗口冻住（最长 25 秒）。
所以 `test_model` 开线程、立刻返回 ticket，前端 `poll_test` 每秒取一次。

## v0.8.0：她自己的时间线

到 0.7 为止，她的全部行为都发生在一个事件之后：收到消息 → 生成 → 发送。
没有消息的时候，程序里唯一的动作是 `while not self._stop: self.msleep(300)`。

0.8 把那圈空转接上了电。

```
                    ┌──────────────────────┐
       每 5 秒 ────▶ │  life.tick(now)      │  不调模型 / 不读微信库 / 不发消息
                    │  asleep / energy     │
                    │  doing / sleep_debt  │
                    └──────────┬───────────┘
                               │ 状态写 <数据根>/life.json
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
       ┌────────────┐   ┌────────────┐   ┌────────────┐
       │ 身体 871   │   │ 睡觉不回   │   │ 刚看到     │
       │ 注入面     │   │ gate       │   │ 醒来补一句 │
       │ 可关       │   │ 可关       │   │ 用掉即清   │
       └────────────┘   └────────────┘   └────────────┘
```

分层的理由和记忆/心情一致：**状态是器官，插件是它的嘴和闸**。
关掉「身体」她照样会累会睡，只是不再说出来。

### 两个时钟

```
主时钟（她的）：23:20 ± 42 分钟入睡，睡 8h20m ± 35 分钟。每天不一样。
扰动（你的）：  你深夜还在聊 → 多撑 18~38 分钟/次，一晚最多 96 分钟。
```

**不能用「你最后一条消息 + 40 分钟」推她的睡眠。** 反例很短：
你早上 9 点发一条，一整天没说话 —— 她 9:40 就睡了？晚上 11 点她"刚醒"？
那不是人，是回声。

### 「一天」由醒来推动

`day` 只在 `woke` 那一刻推进。任何固定分界线（凌晨 4 点、早上 6 点）
都会和浮动的起床时刻（最晚 09:55）打架：05:00 启动时她被判成醒着，
可她刚睡下两小时。

冷启动才猜一次，猜完立刻落盘，之后永远以 `state.asleep` 为准。

**所有睡眠窗口判断只能用 epoch。** 入睡点会跨午夜（23:20+42 = 次日 00:02），
用「一天中的分钟数」比较时次日 00:02 被折成 2，于是 23:50 被算成
「早就过了入睡点」。第一版就是这么错的，`selftest_life` 里留了用例。

### 手头的事：能讲，但不能编

`doing` 按时段取样，种子是 `day + 时段` —— 同一天同一段永远同一个答案。
问三次「你在干嘛」三次一样；换时段才换事。

**只有 `doing` 里写着的才能说出口。** 这是 D-36 在生活层的对应物：
她讲出来的事必须能在 `life.json` 里找到。编出来的事第二天对不上。

条目只写「不需要持续注意」的日常事（在看书、在收拾屋子、在等外卖），
不写「在开会」「在医院」—— 那会引出「那你怎么有空回我」。

### 短期历史落盘

`convs` 以前是纯内存，重启即忘「刚才聊到哪」。
现在每句追加一行 jsonl，保留 120 行。

不和记忆库混：记忆库是「一轮写两条 + 分词进 FTS + 可降级」，
这里的诉求只是「上一句说了什么」。两种写法和容错要求完全不同 ——
混在一起的结果是一边坏了另一边跟着丢。

## v0.9.0：她会先开口

0.8 给了她自己的时间线 —— 但那还是"你说话之后"的事。
0.9 开始，**你不说话她也会动**。

```
    引擎线程（5 秒）        本地判定，不调模型、不花钱
    ├─ mood.decay_only()    情绪自己往基线回（每 10 分钟）
    ├─ journal.due()        睡前 30 分钟 → 后台写三行
    └─ proactive.gate()     六道闸门全过 → 后台生成

    后台线程                调模型，生成一句话
    └─ outbox.put()

    引擎线程（flush）       真正发送
    └─ sending 三态 + loopguard 记账 + UIA
```

### 为什么 UIA 必须在引擎线程发

UIA 是 COM/STA 的东西。跨线程调用会踩"偶尔发不出去、偶尔发错窗口"，
而且只在真机上出现 —— 本地自检永远绿。

所以后台线程只负责**生成**，结果进 `queue.Queue`，由主循环每 300ms 取出并发送。

### 为什么 World 独立成模块

0.4.1 那次自环事故的复盘写得很清楚：

> 防护全埋在 `_run()` 的闭包里，4500 行的函数，写不了测试 ——
> 所以这次事故没有任何用例能提前发现。

主动开口比回环防护更危险（唯一没有对方消息作为起点的发送路径），
所以这次不再往 `_run` 里塞，而是 `bigfish/world.py` 一个类，可单独构造、可测。

### 六道闸门

| # | 条件 | 是否可配 |
|---|---|---|
| 1 | 开关 + 今天条数 | `per_day` 可配 |
| 2 | 距上一条 ≥90 分钟 | 写死 |
| 3 | 9:00–22:30 | **写死** |
| 4 | 她醒着、精力 ≥22 | 写死 |
| 5 | 你最近 30 分钟没在聊 | **写死** |
| 6 | 候选分数 ≥55 | 写死 |

第 3、5 条不给开关：半夜发消息、在人家正聊时插话是灾难。
"可配"和"可关"是两件事 —— 灾难性的默认值不该开放。

## v0.10.0：内在状态的三层回路

到 0.9.7 为止，她的状态是**并列**的：灵魂、心情、生活、记忆、主动、关系，
各写各的文件，各注各的段落。它们同时出现在 system 里，但互不影响。

0.10 把它们接成一条回路：

```
                ┌──────────────────────────────┐
   被无视 ─────▶ │ neglect_level（1/2/3）        │
   （8h 没回）    │ 心情 -2~-8 · 主动分数 ×0.75…  │
                └──────────────┬───────────────┘
                               │
                ┌──────────────▼───────────────┐
   一轮结束 ───▶ │ afterglow（余韵）             │
   （情绪真的动） │ conflict/hurt/worry/warm      │
                └──────────────┬───────────────┘
                               │
                ┌──────────────▼───────────────┐
   下一轮 ─────▶ │ policy（表达预算）            │
                │ 条数 / 字数 / 不接许可         │
                └──────────────────────────────┘
```

三个环各自独立、又叠在一起：

| 环 | 输入 | 输出 | 文件 |
|---|---|---|---|
| 被无视 | `dropped`（8h 没回） | `neglect_level`、mood、check_in 候选 | `proactive.json` |
| 余韵 | 一轮的 mood 差值 | 一条带由头的短句 + 预算修正 | `afterglow.json` |
| 预算 | mood / energy / 时段 / 余韵 | 条数、字数、不接许可、强制回阈值 | 不落盘，每轮算 |

### 两条被刻意分开的东西

**状态 vs 描述**
心情是状态（mood.json），余韵是描述（afterglow.json）。
前者回答"此刻几分"，后者回答"刚才那件事还留着什么"。
混在一起会变成"用分数表达事件"，而分数表达不了对象和方向。

**收敛 vs 坏掉**
被无视只压**主动开口**的分数，不碰回复。她能一整天不再找你，
但你说话她照样回 —— 这是"收敛"。如果连回复也压，那是"坏了"。

### v0.10.0 新增模块

| 模块 | 职责 | 关键设计 |
|---|---|---|
| `policy.py` | 状态 → 表达预算 | 纯函数；只给预算不给情绪标签；`apply_afterglow` 叠余韵 |
| `afterglow.py` | 余韵状态机 | 只在该写时写；同类只留最新；道歉软消 + 30 分钟尾韵 |
| `plan.py` | 日程生成 | 宽松解析 + 严格校验；`ensure_yesterday` 补连续性 |
| `narrative.py` | 睡前复盘 | 一次调用写两处；空数组合法 |
| `senses.py` | 天气/节日/近期事件 | `render` 只读缓存；`refresh` 后台联网；零依赖 |
| `plugins/plan.py` | 872 注入面 | 关掉只是不说，日程照常影响 `doing` |
| `plugins/afterglow.py` | 930 注入面 | 关掉只是不说，余韵照常记录和衰减 |

### 数据落点（没有新增文件类型）

```
<数据根>/
  soul.json         she is —— selfNotes 多了自动条目（带 MM-DD 前缀）
  mood.json         此刻 —— 被无视和冲突都会写这里
  life.json         今天 —— 新增 plan / plan_day / narrative_day
  afterglow.json    还留着什么 ← 新
  senses.json       窗外 ← 新
  memory.sqlite3    记得什么 —— 新增 bond_events 表（关系事件）
  proactive.json    想不想说话 —— 新增 neglect_level / penalty_until
```

`afterglow.json` 和 `senses.json` 是**缓存型状态**：删掉只会让她
"这一轮少一段"，不会丢记忆、不会丢人格。这是刻意的 ——
新加的东西必须可以随时扔，否则升级就成了风险。

## v0.10.1~0.10.3：她自己的本子

到 0.10.0 为止，她的产出全是"对你说的话"。日记是第一种**只写给她自己、
但由你来看**的东西。

```
    睡前 30 分钟        睡前 20 分钟
         │                   │
    ┌────▼─────┐        ┌────▼─────┐
    │  复盘     │        │  日记     │
    │ JSON     │        │ Markdown │
    │ → 灵魂   │        │ → 文件   │
    └──────────┘        └──────────┘
     改认知               记生活
```

| | 复盘 | 日记 |
|---|---|---|
| 模块 | `narrative.py` | `journal.py` |
| 座位 | 860 灵魂 | **无**（不进提示词） |
| 落点 | `soul.json` 的 `selfNotes` | `journal/YYYY-MM-DD.md` |
| 契约 | 严格 JSON | 自由散文 |
| 素材闸门 | 不复述对话 ≥3 条 | 有"今天"就写 |

**为什么两次调用**：JSON 字符串里的换行和引号会逼模型把句子写平，
试出来的东西像"带 JSON 外壳的周报"。

**为什么日记不进提示词**：上千字塞进 system 会挤掉记忆和对话；
她"记得今天"靠 memory / mood / facts，不是重读日记。

### 素材不够时补素材，不是让模型闭嘴

0.10.1 的日志要"至少一句真实对话"，结果平淡的日子全不写。
0.10.2 拆了闸门，模型立刻开始编（煮面、泡茶、楼下小孩）。

真正的解法是 `life.day_trace`：今天 `doing` 变过几次就记几条。

```
06:20 在沙发上看书
09:20 在收拾屋子
12:20 在沙发上看书
```

同一个空白日：536 字（全靠编）→ 124 字（时间动作全对）。

### 触发窗口跟着她的床钟

```
[bedtime - 20 分钟, bedtime + 2 小时)
```

`bedtime` 由 `life.plan_day()` 每天醒来时算（23:20 ± 42 分钟 + 睡眠债）。
睡后 2 小时仍可补写 —— 她可能提前困倒，也可能那个点程序没开。

`day` 用 `life.day` 不是 `day_key(now)`：入睡点会跨午夜，
用日历天的话 23:50 写的日记会记到第二天名下，而 `day_trace` 是前一天的。
