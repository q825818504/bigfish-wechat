## 2026-11-11 22:15 —— 0.13.1（判定卡死 / 消息丢失）

用户实测反馈两件事，其实是同一个根因的两面：

1. 连发几句，判定说完了，然后**两分半没有任何动作**，「跟卡死了一样」
2. 再发一句"怎么不说话了"，她只回「在想怎么回你呢」，**前面的话题全没了**

### 怎么确认"她真的没收到"

`D:\大肥鱼\prompts\` 每次调模型都落一份快照，可以直接对账：

```
21:48:02  21:49:23  21:50:56   ←  空白  →  21:55:07
```

21:55:07 那份的「最近的对话」尾部是：

```
我: 那不行，看你被气得那样我开心不起来。
老爸: 怎么不说话了？
```

**「成为一个想干什么就能干什么的」「最自由的大肥鱼」一行都没有。**
所以不是忘，是那句从来没进 prompt。`[收]` 说明了消息到过程序手里。

### 三处洞

1. **`awaiting` 没有墙钟兜底**（D-121）。判定请求卡在本地模型服务上没回来，
   `urlopen(timeout=6)` 是 socket 级超时，服务端挂着连接不吐数据时不一定响。
   → `tick()` / `due()` 全部跳过这个会话，**静默冻结，无异常无日志**。
2. **`verdict()` 结论过时就 `return None`**（D-122）。对方在判定期间又说话，
   这一轮结论作废、什么都不做，下一轮 due 再提交 —— 连发时永远在打转。
3. **`feed()` 的返回值被丢掉**（D-123）。攒满 `max_batch` 时就地封批并返回，
   调用方没接：那批消息既不在桶里也没人处理，**凭空消失且不打日志**。

### 复现与验证

拿真实时间线（21:51:52 起、含判定超时与 feed 打断）跑纯状态机：

- 修前：`verdict → None`，然后 `due` 又提交一次，之后永久无输出。
- 修后：`verdict → SEAL n=4 reason=judged_stale`，四条全在。
- 卡死场景：8 秒后 `_thaw` 解冻，`tick → SEAL n=3`，一条不丢。

`selftest_listen` 从 80 项加到 90 项，新增「判定卡死 8 秒后强制封批」
「解冻封批一条不丢」「没判定在跑时 verdict 被忽略」等回归。

### 顺带

- 冷场话术：prompt 里那条「被催时一句带过、不要展开」执行成了**整句敷衍**。
  改成两步 —— 一句带过，但**必须接上他前面那半截**。

## 2026-11-11 21:10 —— 0.13.0（已部署）

用户一句话定的方向：「她没有属于自己的人生」。
三处具体症状：日程随机没逻辑、首页心情不够实时、**没开软件她的人生就停滞**。

### 主线：catch_up 按边界补算

`life.py` 新增 `catch_up(state, now)`：把 `[last_tick, now]` 按**状态边界**
（时段切换 / 入睡点 / 醒来点 / 午睡窗口 / 整点）切成若干段，逐段推进。

- 关 30 天实测：0.01 秒补 291 个事件，`day` 正确推进、energy 82、债 0。
- 关在入睡点之后（23:50 关、6:00 开）：那一觉补在正确位置。
- `MAX_CATCH_STEPS = 512`（≈42 天）；超了走"按当前时刻重新对齐"，
  不再像旧兜底那样只 `_advance_flat`（那会让四个字段互相打架且落盘）。

**删掉 `RESUME_GAP_HOURS = 26.0`**：那个"超过 26 小时就算冷启动"的特判
正是"第二天早上才睡"的元凶——它把一整段时间当成"醒着"推进。

### 踩的坑（按发现顺序）

1. **`tick` 里 `catch_up` 之后 `expire_plan` 又跑一次** —— 幂等，保留
   （`refresh_doing` 有三处早退，tick 末尾那次才是"区间过完就结算"的兑现）。
2. **`_next_boundary` 只认 > t 的候选** —— 已过点的入睡点不进候选，导致
   21:25 的睡点拖到 23:00，那 95 分钟还被按 overtime 收了一遍。
   修法：循环开头先 `_on_boundary(state, t)` 处理"t 这一刻本来就该发生的事"。
3. **repair 拿 `wake_at` 当哨兵** —— `wake_at=0` 时恰好把补睡关掉，
   而 0 还会让 `_wake` 去算 1970 年，Windows 上 `.timestamp()` 直接抛 OSError。
   修法：哨兵改成 `deadline > 0 and t > deadline`，醒来时刻用 `_fall_asleep`
   刚重算的那个；并且**不回拨 t**（回拨会让已按清醒扣过费的窗口再加睡眠增益）。
4. **陪聊延长被三重惩罚** —— overtime 基准用 `bedtime` 而不是"允许熬到的时刻"，
   于是"我愿意陪你多聊 96 分钟"当晚扣一次、债里又记一次、次日再扣一次。
   修法：overtime 用允许时刻；**`_fall_asleep` 的债仍按 bedtime**
   （延长多少就真的少睡多少）。两者故意不同。
5. **跨午夜时提示词把昨天的安排写成"你今天打算做的"** —— 守卫用了
   `state.day`，而她凌晨还没醒时 `state.day` 停在前一天，等于"昨天==昨天"。
   修法：三处守卫（`expire_plan` / `current_plan_item` / `plan_for_prompt`）
   全部改用 `day_key(now)` 这个**日历日**。
6. **`set_plan` 的 `dur` 无 try** —— `int("45分钟")` 抛 ValueError，
   而调用方把异常当成"日程生成失败"，**整天日程全丢**。加 `_clamp_int`。
   同时给 `at` 加范围校验：`"99:99"` 以前能落库，永不命中、永不 expire。
7. **`_fact_score` 与 SQL 的 `confidence=0` 分歧** —— Python 写
   `float(x or 0.5)`，`0.0 or 0.5` = 0.5；SQL 用真值 0.0。同一条事实两边
   排序反转。修法：`0.5 if x is None else float(x)`。
8. **`use_count` 加成无上限**（注释写着"但有上限"，代码没有）——
   被注入过的每轮 +1，几十轮后时间衰减彻底失效。加 `USE_COUNT_CAP = 20`。
9. **`_worth_showing` 判据方向反了** —— 字符集 Jaccard 丢掉顺序和重复，
   精确地吞掉"高重合但语义全变"：`喜欢他→不喜欢他`、`620→602`、
   `猫咬狗→狗咬猫`。修法：先判三种"一定值得看"（数字变了 / 否定翻转 /
   同字换序），再看措辞重合。
10. **`world.py` 两处 `list_facts(owner=A, tier=owner)` 实际返回全库** ——
    `scope_filter` 在 `strict_owner=False` 时产出
    `(owner=A OR visibility IN (...))`，而 `visible_visibilities(TIER_OWNER)`
    是**全部三种**，于是 OR 那一半恒真。别人的私密会进日记正文、
    进复盘的 `changed_view`（写进 `soul.selfNotes` 长期留存）。
    修法：调用方自己再收一刀（和 `facts_for_prompt` 一致）。
11. **日记互相取代** —— `predicate="那天"` 固定 + `anchor` 留空，
    `_find_same` 按 (owner, anchor, predicate) 判"同一件事"，
    于是第二天的日记把第一天的当"纠正"给 supersede 掉。
    修法：`anchor` 用完整日期（MM-DD 的话一年后同一天还会撞）。
12. **`world.py` 用了 `time.time()` 但没 `import time`** ——
    `NameError` 被 `except` 吞成"没有天气"，心情底子少算一档且永不报错。
    这个只有 pyflakes 抓得到。

### 语音：吞字与长对话

- 症状：她说"大肥鱼蓝鲸一条，住在电脑里"，发出去的是"大肥鱼蓝鲸一条住在电"。
- 根因三层：① 心情预算把文本压到 14-18 字 ② 硬切切在字中间

- 拆段规则：每段 ≤200 字（≈44 秒）、最多 3 段、按句>逗号>硬切、
  **剩下的并进最后一段不丢内容**、条间停 1.1-1.5 秒。

### 闪退与内存

- 2026-11-11 15:07 闪退。Windows 事件日志：
  `Qt6WebEngineCore.dll` / `0xc0000005` / 偏移 `0xf722d3`。
  **不是 Python 异常**（系统直接终止进程，异常钩子轮不到执行），
  所以程序日志里一个字都没有。
- 实测内存（引擎未启动、纯界面空转）：466.8 → 468.4 MB，2 分钟涨 1.6MB，
  **句柄反而减少（1917→1906）、线程不变** → 纯堆增长。
- 根因：每次 `get_status` / `get_today` 都是跨 C++ 边界的字符串往返，
  V8 把临时对象攒在老生代，默认上限很大，不到点不回收。
- 修法：`--js-flags=--max-old-space-size=192` 逼它勤收（验证出现回落：
  256→253.5，旧版四条数据没有一次往下走）；轮询 2s→3s/15s；
  看门狗 750MB 重载；渲染进程崩了自动重载。

## 0.10.6 —— 发送收尾缩进塌陷（hotfix，未提交）

**用户看到的现象**：微信里对方明明收到了两条，日志写
「[发] 这一轮一条都没发出去」，而且成功日志 `[发] ...` 一行都没有。

**根因**：b56f51f 加「短期历史落盘」时，把

```python
try:
    _H3.append(...)
except Exception:
    pass
```

插在了 `if sent_any:` 的**同级**（16 空格）。于是：

- 后面 120 行收尾（`reply_count` / `remember_sent(reply)` / 熔断 /
  `[发]` 成功日志 / 后置表情 / `vault.record_exchange` / 心情 / 反思 /
  习惯观察）全部是 20 空格 —— 掉进 `except` 块，只有 history 抛异常才执行；
- 原来的 `else:`（发送失败的结论）变成了这个 history-try 的 else，
  history 正常写入 → 每轮都打「一条都没发出去」。

语法完全合法，所以跑得起来、也不报错。

**修法**：收尾回 `if sent_any:`；history 只在真的发出去之后写，且写清理过的
正文（`{{split}}` 以前会原样进 history 再被带进下一轮 prompt）；
`r"\\s+"` → `r"\s+"`；结果未知不再说"一条都没发出去"。

**防复发**：`tools/selftest_send_tail.py` —— 用 AST 断言收尾必须在
`if sent_any` 里、`else` 只能有失败文案，并全包扫描

## 本轮：表情包在两千张时还能用（2026-11-05）

### 起点

用户：「批量导入 2000 张之后，导入完也依然无敌卡」。

量下来库是 2181 张 / 836 MB，卡的不是导入，是**每次刷新都全量解码原图**：
`<img src="file:///…stk_0001.gif">` 为了显示 132px 的格子，把 800×800 原图
完整解了一遍 —— 1580 Mpx，165 Mpx/s，约 10 秒。

### 四次迭代，每次都被实测推翻了上一版的判断

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| 1 | 256px PNG 缩略图 + `content-visibility` | PNG 平均 259 KB、全库 620 MB，等于没优化；`content-visibility` 让滚动帧 16.6 → 22.0 ms |
| 2 | 换 WebP q82 + 删 `content-visibility` | 33 MB / 14 KB 每张；但「进页仍卡」没解决 |
| 3 | 分页 120 张 + 滚动自动追加 | 首屏好了，用户体验是"划不到底" |
| 4 | 一页 60 张真翻页 + 精简列表 + 状态探测缓存 | 37 ms 首屏、8~12 ms 翻页 |

**教训**：`content-visibility: auto` 不是无脑加速器。每格带 `border-radius +
overflow:hidden` 时，浏览器要为每个屏外格子做尺寸评估 + 裁剪，比直接画更贵。
以后用之前先量。

### 进页卡顿的真凶不在表情包

`get_status` 每 2 秒跑一次 `_find_weixin_pids()`（三路合一：EnumWindows +
NtQuerySystemInformation + tasklist），**173 ms**，全在 GUI 线程。
用户点「表情包」时有一半概率撞上它 —— 于是所有"进表情包就卡"的观察
都被这一条解释掉了。改成 30 秒缓存（诊断信息晚 30 秒无所谓）。

```
差异格数 ≤2 且 最大色差 ≤40  → 确定重复，跳过
```

## 当前状态：v0.6.0 —— 三件「出事时能定位」的事（未发布）

### 起点

0.5.0 支持 19 家渠道后，出现两个新问题：

1. 某个渠道 429 一次，这一轮就没有回复 —— 用户看到的是「她不理我」。
2. 她答得不对时，分不清是渠道问题、模型问题还是提示词问题。

第二轮的对比结论里把这三条列为 P0，这一版就只做它们，不加功能。

### 做了什么

| 功能 | 落点 | 关键设计 |
|---|---|---|
| 模型重试 | `replier.call_model` | 只重试「换个时间可能成功」的：429/5xx/网络/解析失败；4xx 直接抛 |
| 空正文扩预算 | `replier.call_model` | reasoning 吃光 token 时 `max_tokens ×1.5` 再试一次，而不是报「她不回复」 |
| 请求快照 | `prompt_trace.py`（新） | 每轮一份 JSON，旁路写、不阻塞、绝不写 api_key |
| 记忆降级 | `memory.search_with_fallback` + `bridge_client` | 桥接挂了用本地库兜底；都挂了才空记忆，并标记 degraded |
| 打包数据保护 | `tools/deploy.py` | 备份按 `settings.json` 的 dataRoot；打包前后对比数据指纹 |

### 关键决定

- **重试不写在每个调用点**，写在 `call_model` 内部：画像归纳、断句、测试连接全都自动受益，
  也不会出现「这个调用点忘了加重试」。
- **快照按文件名滚动，不按 mtime**：Windows 的 mtime 精度约 100ms，同一批写入会撞在一起，
  按 mtime 排序会把刚写的那份当最旧的删掉（实测踩过）。
- **降级只在桥接报错时触发**，桥接正常但没命中时**不**兜底 —— 否则每轮都会塞进「最近原文」，
  看起来像她突然只会重复昨天的话。
- **deploy 的备份改看 settings.json**：以前只备份 `dist/BigFish/data`，
  而实际数据根是 `D:\大肥鱼`，等于备份了一个空目录。

   加 `--force` 先删再传。

**"兼容 OpenAI 接口"这句话不能用。** 它没说清兼容到哪一层：地址？认证？

## 2026-11-03 晚 · 表情接上心情

### 用户的原话

> 大肥鱼在不同的心情下，如果有同类的表情包，就根据不同心情展示不同的
> 表情包，比如同样是高兴，一个就一般高兴，一个就非常高兴
>
> 一定要配合到我们的心情插件，里面就有情绪维度！

### 先纠正一个说法

**不需要新增「情绪值」** —— 心情系统已经有两层：

```
score   0~100
dims    七根：开心 / 踏实 / 甜蜜 / 心疼 / 担心 / 难过 / 吃醋
```

真正缺的是两个：

```
① 挑表情时完全没读心情（插件只看对话文本）
② 表情没有维度也没有强度（十张都叫"高兴"，不知道哪张是微笑）
```

### 表情加两个字段

```
mood_dim    七根之一，或空 = 不归类（无语/疑惑这类）
intensity   1~5
```

**存 key 不存中文**：标签会改，key 不会。标签显示时查表。

`MOOD_DIM_KEYS` / `MOOD_DIM_LABELS` 和 `vault.MOOD_DIMS` 对齐，
**有测试断言两边一致** —— 不一致的话挑表情永远匹配不上。

### 视觉模型顺手判这两样

实测两张图：

```
微笑（小弧线嘴、圆眼）  → calm  强度 2  brief=微笑
大笑（大弧嘴、弯眼）    → happy 强度 3  brief=开心
```

prompt 里写死了：`mood_dim` 只能从七个里选，或者空。
「无语」「疑惑」这类不许硬塞进 happy。

### 挑表情时读心情

```
她现在的心情：心情不错（72/100）
情绪偏向：开心 45、甜蜜 12

可用的表情：
- stk_0003 [动图·强度2·开心] 微微一笑
- stk_0007 [动图·强度5·开心] 笑到打滚
- stk_0012 [动图·强度3·难过] 眼泪汪汪
```

prompt 规则：

```
第一步：维度要对上。她正在开心就挑「开心」类的。
       没标维度的（无语/疑惑）任何心情都能用。
第二步：强度跟分数对上。≥70 挑 4~5，40~70 挑 2~3，<40 挑 1~2。
       心情差的时候发狂喜，看着像装的。
但以这句话为准：明显在开玩笑，哪怕心情低也能发自嘲。
```

**心情读的是最新落盘的那份**，不是本轮开始时的快照 ——
心情判断是上一轮结束后写的，用最新的更准。

### 一个设计判断

**没让模型每次从 detail 里推强度，而是存成字段。**

理由：「这张图有多强烈」是图的固有属性，一次判断长期复用；
让模型每次重推，结果会飘。

### 版本号统一

以前散在三处：`__init__.py` 0.1.0、`updater.py` 0.2.1、
`make_installer.py` 0.1.0。发版时改一处忘两处，装出来的包
版本号和程序自称的不一样。

现在只在 `bigfish/__init__.py` 定义，另两处都 import。

### 关键决定

**表情包是插件，不是内建页面。** 侧边栏那一项跟着插件开关走。

**这一页只管库，不管行为。** 开关和频率搬去插件配置。

### 数据结构（schema v2）

```json
{
  "version": 2,
  "seq": 12,
  "items": {
    "stk_0007": {
      "code": "stk_0007",
      "file": "stk_0007.gif",
      "brief": "开心",
      "detail": "眉毛倒竖……",
      "tags": ["开心", "兴奋"],
      "mood_dim": "happy",
      "intensity": 3,
      "source": "import",
      "auto": true,
      "frames": 4, "w": 512, "h": 512

}
```

旧格式 `{文件名: {desc}}` 第一次读时自动迁移。

### 格式统一转 GIF

微信只把 `.gif` 认成原生表情。有损，但做了三件事缓解：

1. >1024 等比缩小（微信上限，超过当文件发）
2. 调色板 ADAPTIVE（按实际颜色分布）
3. 多帧保留（GIF / 动 WebP 逐帧转）

透明只能二值化 —— GIF 1 位透明的格式限制。

### 自动备注

本地网关支持视觉（实测：发红色圆形返回"红色圆形"）。
图缩到 512 再 base64。任何失败都不拒绝导入。

## 2026-11-03 晚 · 拖放（试了三条路）

用户反馈"拖拽无效"三次，前两条路都修错了地方：

| | 做法 | 为什么不行 |
|---|---|---|
| ① | HTML5 `dataTransfer.files` | QtWebEngine 里没有 `path` 属性 |
| ② | QWidget eventFilter + OLE | 管理员权限下被 UIPI 拦住 |
| ③ | **Windows 原生 `WM_DROPFILES`** | 通了 |

第 ② 条甚至写了 `ChangeWindowMessageFilterEx` 放行三条消息
（API 全返回 True），事件还是没到。

**真正的冲突**：窗口只要注册了 OLE drop target，系统就只走 OLE，
再也不发 `WM_DROPFILES`。而 OLE 在管理员权限下被 UIPI 卡死。
两条路互相打架。

解法：先 `RevokeDragDrop` 撤掉 OLE 注册，让系统回到老式路径。

自己构造 `WM_DROPFILES` 验证整条链路：
```
WM_DROPFILES 文件数=2
已交给页面：2 个
页面 pending: {"n":2, "p":["动图_512.gif","动图_240.gif"]}
```

日志写到 `<程序目录>/data/_drop.log` —— 界面在管理员权限下跑，
看不到控制台，出问题只能靠这个。

## 2026-11-03 凌晨 · 表情包发送通道

### 关键发现：GIF 文件就是原生表情

微信把剪贴板里的 `.gif` 文件识别成表情消息（`local_type 47`）。
对方收到的是原生表情 —— 能长按添加、会动。

### 真机踩出来的四个坑

**① 剪贴板格式不全**（`CF_HDROP` 不够）
微信是 Qt 应用，走 OLE，认 `DataObject` / `FileNameW`。
**格式存在 ≠ 别人读得懂。**

**② 临时目录被拒**（最贵的一个）

```
D:\大脑\表情测试\x.gif       → 彩色占比 10.3%，发出是表情
%TEMP%\bigfish-xxx\x.gif     → 彩色占比 0.0%，什么都没发生
```

**微信拒绝从临时目录粘贴文件。** 而我一直用 `%TEMP%` 造测试图 ——
十几轮都在查功能，其实功能没问题。

**③ 判据用灰度差，5.9 卡在阈值 6 下面**
输入框只有 88px 高，缩略图缩成 48×16 后差值被稀释。
换成**彩色像素占比**：空框 0.00%，有图 10.88%，阈值 2%。

**④ 验证过滤掉了自己发的消息**
`if sender_id != 2: continue`（照抄 vendor）。这台机器上自己发的
`sender_id=4`，于是永远返回 False。

### 真机结果

```
聚焦后 前台='微信' 焦点='微信'
草稿已进输入框（彩色占比 8.5%）
发送后新增 1 条
  · type='动画表情' sender_id=4

`.tmp/probe_bridge_speed.py` 在真机上量的：

- `node -e "0"`：**53 ms**

**② `[收]` 日志在 `handle()` 里，不是消息到手时。**
轮询 ≤1.2s + 攒批 2.0s，所以日志天然晚 2~3 秒。用户体感「卡住」，
但消息其实一直在手里。

| 文件 | 改动 |

| `bigfish/bridge_client.py` | `_NO_WINDOW` + `creationflags`；注释写清为什么 |
| `bigfish/desktop.py`（记忆页搜索） | 同样补 `CREATE_NO_WINDOW` |
| `bigfish/desktop.py`（`enqueue`） | 消息到手立刻打 `[收]` |
| `bigfish/desktop.py`（`handle`） | 删掉重复的 `[收]`，保留 `chat_event.emit` |

## 2026-11-08 23:3x — 「[跳过] 自己发的消息」为什么会出现

### 用户问

23:29:32 [跳过] 老爸：自己发的消息；allow_self 没对这个会话开
```

### 两层原因，一层是设计，一层是我上一轮引入的

**① `[跳过]` 本身是设计内的自环防护，不是异常。**

她发完 → 微信异步写库（实测 10~12 秒）→ watcher 1.2s 轮询读到 → 进 `feed`。
这时 `is_self=True`，**必须丢掉**，否则她会回自己（v0.4.1 那次自问自答的成因）。
问题只在于：以前**每条**都打一行，文案还写着「allow_self 没对这个会话开」，
和紧邻的 `[收]` 一对照，看起来像"对方的消息被跳过了"。

**② `[收]` 挪到 `enqueue()` 后没过滤 `is_self` —— 这是我上一轮引入的回归。**

所以日志里会出现「[收] 老爸：那你今天干点啥了」这种句式，
而那其实是**她刚发出去**的话（23:29:36 的 `[发]` 里就有同一句）。
「收 + 跳过」并排出现，正是同一个消息被读成两次的效果。

### 改了什么

| 文件 | 改动 |
|---|---|
| `bigfish/desktop.py` | `enqueue` 里只对**对方**的消息打 `[收]`；自己的由 `[发]` 覆盖 |
| `bigfish/listen.py` | 新增 `_note_self_skip()`：同会话 120 秒只提示一次，带她的原话，改说「属正常闭环」 |

新文案长这样：

```
[跳过] 老爸：她自己刚发的「那你今天干点啥了」被读回来，属正常闭环（allow_self 未开，不再重复提示）
```

## 2026-11-08 23:4x — 攒批太短 + 连发两条被回两轮

### 用户报

> 现在的时间还是太短了，我稍微犹豫一点发，她就已经回复了。
> 然后假如她回的很多，每句话 3 条，我连发两条，她一下子就会 6 条，这不就成了刷屏？

两件事，两个不同的根因。

### ① 攒批窗口：4.0s 太短

`adaptive_quiet()` 在 [1.5, 6.0] 之间按字数取值，短消息取上限。
原来的上限是 **4.0s**，而真人发微信常见节奏是
「在吗」→ 想 3 秒 →「问你个事」→ 再停 4 秒 → 正文。
4 秒刚好卡在中间，于是被切成两轮：她回一次，对方再发，她又回一次。

**改成 6.0s**。长句/有句号的消息仍走 `quiet_min`（1.5s），
所以"说完一句"的回复速度没变慢 —— 只有"看起来没说完"的才多等。

### ② 一次 6 条：预算只看单轮，不记得自己刚说过什么

`policy.response_policy()` 原来只看心情 / 精力 / 时段。
心情不错 → 4 条上限，`say` 插件配的是 3 条 → 每轮 3 条。
对方连发两条 = 两轮 = **6 条**，单轮看每轮都合理。

**新增跨轮配额**：`recent_parts` / `recent_replies`（最近 90 秒的条数与轮数），
由 `EngineWorker._note_sent_parts()` 在发送成功后记账：

| 最近 90 秒已发 | 这一轮 |
|---|---|
| ≥ 6 条 | 1 条，≤16 字 |
| ≥ 3 条 | 1 条，≤24 字 |
| 已回 ≥ 2 轮 | 1 条 |

第一版写的是「≥3 条 → 2 条」，算下来两轮还是 5 条，用户照样会觉得在刷屏 ——
所以直接压到 1 条。配额只收紧、不放宽，不会出现"聊得越久她越能说"。

`_sent_parts` 只放内存，进程重启清零（和账本 D-9 同一个理由）。

### 验证

- `selftest_listen` 59/59：窗口断言全部改成读 `ListenPolicy` 的值
  （`quiet_max`、`adaptive_quiet`、`post_reply_grace`），调参不再需要改测试。

### 留给用户调的

（v0.10.4 的 D1 修过"心情量纲三处不一致"，UI 这一处漏了。）

改法：
1. `app.js`：`Math.min(100, v) / 100`。
2. **数值也调了**：单次增量 3~5、半衰期 90 分钟，一天下来长期停在 0~10，
   显示成 4%/9% 也确实是"几乎没有情绪"。加 `mood_judge.DIM_GAIN = 3`
   （单次 9~15，稳态 30~50），`sigDim` 默认 5 → 15 保持"显著"的原意。
   ⚠ 这是标定值，不是推导值；只在 `selftest_mood` 里钉住。
3. **视觉**：轨道 7px → 10px、加内阴影、填充改渐变。
   （`color-mix()` 不能用 —— Qt WebEngine 的 Chromium 版本不支持，整条会透明。）

`selftest_mood` 19 → 23（新增 4 项：增益、封顶、未提及维度保持 0）。

**存量数据不用清**：旧值 0~10 会随着后面几轮判定自然涨到 30~50，
衰减也仍按 90 分钟半衰期往回走。
