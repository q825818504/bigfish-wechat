## 最新：0.10.6 —— 发送收尾缩进塌陷（hotfix，未提交）

**用户看到的现象**：微信里对方明明收到了两条，日志写
「[发] 这一轮一条都没发出去」，而且成功日志 `[发] ...` 一行都没有。

**根因**：b56f51f 加「短期历史落盘」时，把

```python
try:
    _H3.append(...)
except Exception:
    pass
```

插在了 `if sent_any:` 的**同级**（16 空格）。于是：

- 后面 120 行收尾（`reply_count` / `remember_sent(reply)` / 熔断 /
  `[发]` 成功日志 / 后置表情 / `vault.record_exchange` / 心情 / 反思 /
  习惯观察）全部是 20 空格 —— 掉进 `except` 块，只有 history 抛异常才执行；
- 原来的 `else:`（发送失败的结论）变成了这个 history-try 的 else，
  history 正常写入 → 每轮都打「一条都没发出去」。

语法完全合法，所以跑得起来、也不报错。

**修法**：收尾回 `if sent_any:`；history 只在真的发出去之后写，且写清理过的
正文（`{{split}}` 以前会原样进 history 再被带进下一轮 prompt）；
`r"\\s+"` → `r"\s+"`；结果未知不再说"一条都没发出去"。

**防复发**：`tools/selftest_send_tail.py` —— 用 AST 断言收尾必须在
`if sent_any` 里、`else` 只能有失败文案，并全包扫描
「`except: pass` 后面还有语句」的形状。拿修复前的文件反向跑，它报 5 项失败。

**同一批另修十一条**（用户同一天报的）：

1. **关系提炼失败后 6 小时不重试** —— `_last_bond` 写在 `call_model` 之前，
   一次 502（推理吃光 token → 空正文）等于关掉功能 6 小时。改成跑完才计时，
   失败退避 30 分钟。
2. **窗口挑错** —— `FindWindowW("Qt51514QWindowIcon", None)` 抓到哪个不保证。
   微信从托盘恢复会重建顶层窗口，旧的还留着（标题仍是「微信」、`IsWindow`
   为真，但点不动）—— 用户看到的「界面没反应、X 关不掉」就是它。
   改成枚举 + 跳过 `IsHungAppWindow` + 按面积取最大（`bigfish` 与
   `vendor/.../uia_driver._wechat_hwnds` 两处）。「打不开会话」的报错现在
   带窗口尺寸；窄到微信收起导航栏时直说是窗口太小。
3. **UIA 启动失败就整晚不发** —— `_run()` 开头只试一次，失败就
   `self.sender=None` 到重启；界面还显示「运行中」。改 `_ensure_sender()`
   每轮重试（成功打「自动恢复」，失败 60 秒一次）；`force_show_wechat()`
   改 `visible_only=False` 找句柄（**0.10.6 第一版把它写成只找可见窗口，
   导致托盘里的微信永远叫不出来 —— 自己的回归**）；`wake()` 叫出来后
   最多再等 3.2 秒；UI 增 `sender` 字段，发不出去时显示
   「运行中 · 发不出去 / 只监听 · 不发送」。
4. **「打开微信」弹出的窗口点不动** —— 那个窗口属于正常的 `Weixin.exe`、
   也不 hung，是微信**收进托盘后留下的残留顶层窗口**：`ShowWindow` 能让它
   重新出现，但 Qt 那头不再处理输入（用户实测：点它没反应、X 也关不掉）。
   微信托盘图标走的是自己的重建路径，所以点托盘才好。程序模拟不了托盘回调。
   已把按钮改走统一 `force_show_wechat()`、返回 `{ok,msg}` 直接说恢复路径；

### 发布前自检抓到的三个"哑巴 bug"

跑 `pyflakes` 全包扫描时抓到三处**未定义名**，三处都被 `except: pass` 包着：

1. `desktop.py` 的 `_M.observe_habit(...)` —— `_M` 从未 import。
   所以**习惯观察一次都没跑过**。之前以为是"没调用"（v6 的死代码），
   实际是调用了、NameError、被吞了。`habits` 表恒空、score 永不衰减，
   根因在这里，不在 `refresh_habits`。
2. `desktop.py` 发送失败分支的 `f"{r.detail}"` —— `r` 不存在。
   首条就失败时会抛 NameError，而外层只 `except SendError`，捕获不到。
   那两行还是重复记录（失败原因在循环里已经记过），已删。
3. `_maybe_narrative` 外层 except 不 `mark_done` ——
   模型超时/429 一次就每 5 秒重试到窗口结束，日志却写"明天再试"。

**教训记在这里**：这个项目里 `except Exception: pass` 是最大的藏 bug 的地方。
以后新增的 except 至少要留一行 `self._log(..., "")`，不要静默 ——
静默的代价是"功能不存在"和"功能坏了"在日志里长得一模一样。

自检结论：`pyflakes` 未定义名 0、`compileall` 通过、50 个模块 import 全成功。

### 打包态自检：源码 23/23，exe 20+1skip+1fail

### 这一批最贵的一次教训

0.10.1 的日志要求"至少一句真实对话"才写。用户一句"允许当天啥也没发生也能写"
把它推翻了 —— 而平淡正是日记该记的东西。

拆掉闸门之后，模型开始编。同一个空白日（没人说话、只有"在沙发上看书"）：

```
0.10.1  536 字：煮面、泡茶、楼下小孩、整理柜子、书里讲的故事
0.10.2  124 字：时间、动作全部来自 day_trace，没有编
```

**结论：素材不够的时候，补素材，不是让模型闭嘴，也不是放它瞎写。**
`life.day_trace` 就是为这件事加的：今天 `doing` 变过几次记几条。

## 本轮：表情包在两千张时还能用（2026-11-05）

### 起点

用户：「批量导入 2000 张之后，导入完也依然无敌卡」。

量下来库是 2181 张 / 836 MB，卡的不是导入，是**每次刷新都全量解码原图**：
`<img src="file:///…stk_0001.gif">` 为了显示 132px 的格子，把 800×800 原图
完整解了一遍 —— 1580 Mpx，165 Mpx/s，约 10 秒。

### 四次迭代，每次都被实测推翻了上一版的判断

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| 1 | 256px PNG 缩略图 + `content-visibility` | PNG 平均 259 KB、全库 620 MB，等于没优化；`content-visibility` 让滚动帧 16.6 → 22.0 ms |
| 2 | 换 WebP q82 + 删 `content-visibility` | 33 MB / 14 KB 每张；但「进页仍卡」没解决 |
| 3 | 分页 120 张 + 滚动自动追加 | 首屏好了，用户体验是"划不到底" |
| 4 | 一页 60 张真翻页 + 精简列表 + 状态探测缓存 | 37 ms 首屏、8~12 ms 翻页 |

**教训**：`content-visibility: auto` 不是无脑加速器。每格带 `border-radius +
overflow:hidden` 时，浏览器要为每个屏外格子做尺寸评估 + 裁剪，比直接画更贵。
以后用之前先量。

### 进页卡顿的真凶不在表情包

`get_status` 每 2 秒跑一次 `_find_weixin_pids()`（三路合一：EnumWindows +
NtQuerySystemInformation + tasklist），**173 ms**，全在 GUI 线程。
用户点「表情包」时有一半概率撞上它 —— 于是所有"进表情包就卡"的观察
都被这一条解释掉了。改成 30 秒缓存（诊断信息晚 30 秒无所谓）。

```
差异格数 ≤2 且 最大色差 ≤40  → 确定重复，跳过
```

### 起点

### 做了什么

| 功能 | 落点 | 关键设计 |
|---|---|---|
| 模型重试 | `replier.call_model` | 只重试「换个时间可能成功」的：429/5xx/网络/解析失败；4xx 直接抛 |
| 空正文扩预算 | `replier.call_model` | reasoning 吃光 token 时 `max_tokens ×1.5` 再试一次，而不是报「她不回复」 |
| 请求快照 | `prompt_trace.py`（新） | 每轮一份 JSON，旁路写、不阻塞、绝不写 api_key |
| 记忆降级 | `memory.search_with_fallback` + `bridge_client` | 桥接挂了用本地库兜底；都挂了才空记忆，并标记 degraded |
| 打包数据保护 | `tools/deploy.py` | 备份按 `settings.json` 的 dataRoot；打包前后对比数据指纹 |

### 关键决定

- **重试不写在每个调用点**，写在 `call_model` 内部：画像归纳、断句、测试连接全都自动受益，
  也不会出现「这个调用点忘了加重试」。
- **快照按文件名滚动，不按 mtime**：Windows 的 mtime 精度约 100ms，同一批写入会撞在一起，
  按 mtime 排序会把刚写的那份当最旧的删掉（实测踩过）。
- **降级只在桥接报错时触发**，桥接正常但没命中时**不**兜底 —— 否则每轮都会塞进「最近原文」，
  看起来像她突然只会重复昨天的话。
- **deploy 的备份改看 settings.json**：以前只备份 `dist/BigFish/data`，
  而实际数据根是 `D:\大肥鱼`，等于备份了一个空目录。

## 2026-11-03 晚 · 表情接上心情

### 用户的原话

> 大肥鱼在不同的心情下，如果有同类的表情包，就根据不同心情展示不同的
> 表情包，比如同样是高兴，一个就一般高兴，一个就非常高兴
>
> 一定要配合到我们的心情插件，里面就有情绪维度！

### 先纠正一个说法

**不需要新增「情绪值」** —— 心情系统已经有两层：

```
score   0~100
dims    七根：开心 / 踏实 / 甜蜜 / 心疼 / 担心 / 难过 / 吃醋
```

真正缺的是两个：

```
① 挑表情时完全没读心情（插件只看对话文本）
② 表情没有维度也没有强度（十张都叫"高兴"，不知道哪张是微笑）
```

### 表情加两个字段

```
mood_dim    七根之一，或空 = 不归类（无语/疑惑这类）
intensity   1~5
```

**存 key 不存中文**：标签会改，key 不会。标签显示时查表。

`MOOD_DIM_KEYS` / `MOOD_DIM_LABELS` 和 `vault.MOOD_DIMS` 对齐，
**有测试断言两边一致** —— 不一致的话挑表情永远匹配不上。

### 视觉模型顺手判这两样

实测两张图：

```
微笑（小弧线嘴、圆眼）  → calm  强度 2  brief=微笑
大笑（大弧嘴、弯眼）    → happy 强度 3  brief=开心
```

prompt 里写死了：`mood_dim` 只能从七个里选，或者空。
「无语」「疑惑」这类不许硬塞进 happy。

### 挑表情时读心情

```
她现在的心情：心情不错（72/100）
情绪偏向：开心 45、甜蜜 12

可用的表情：
- stk_0003 [动图·强度2·开心] 微微一笑
- stk_0007 [动图·强度5·开心] 笑到打滚
- stk_0012 [动图·强度3·难过] 眼泪汪汪
```

prompt 规则：

```
第一步：维度要对上。她正在开心就挑「开心」类的。
       没标维度的（无语/疑惑）任何心情都能用。
第二步：强度跟分数对上。≥70 挑 4~5，40~70 挑 2~3，<40 挑 1~2。
       心情差的时候发狂喜，看着像装的。
但以这句话为准：明显在开玩笑，哪怕心情低也能发自嘲。
```

**心情读的是最新落盘的那份**，不是本轮开始时的快照 ——
心情判断是上一轮结束后写的，用最新的更准。

### 一个设计判断

**没让模型每次从 detail 里推强度，而是存成字段。**

理由：「这张图有多强烈」是图的固有属性，一次判断长期复用；
让模型每次重推，结果会飘。

### 版本号统一

以前散在三处：`__init__.py` 0.1.0、`updater.py` 0.2.1、
`make_installer.py` 0.1.0。发版时改一处忘两处，装出来的包
版本号和程序自称的不一样。

现在只在 `bigfish/__init__.py` 定义，另两处都 import。

**表情包是插件，不是内建页面。** 侧边栏那一项跟着插件开关走。

**这一页只管库，不管行为。** 开关和频率搬去插件配置。

### 数据结构（schema v2）

```json
{
  "version": 2,
  "seq": 12,
  "items": {
    "stk_0007": {
      "code": "stk_0007",
      "file": "stk_0007.gif",
      "brief": "开心",

本地网关支持视觉（实测：发红色圆形返回"红色圆形"）。

## 2026-11-03 晚 · 拖放（试了三条路）

用户反馈"拖拽无效"三次，前两条路都修错了地方：

| | 做法 | 为什么不行 |
|---|---|---|
| ① | HTML5 `dataTransfer.files` | QtWebEngine 里没有 `path` 属性 |
| ② | QWidget eventFilter + OLE | 管理员权限下被 UIPI 拦住 |
| ③ | **Windows 原生 `WM_DROPFILES`** | 通了 |

第 ② 条甚至写了 `ChangeWindowMessageFilterEx` 放行三条消息
（API 全返回 True），事件还是没到。

**真正的冲突**：窗口只要注册了 OLE drop target，系统就只走 OLE，
再也不发 `WM_DROPFILES`。而 OLE 在管理员权限下被 UIPI 卡死。
两条路互相打架。

解法：先 `RevokeDragDrop` 撤掉 OLE 注册，让系统回到老式路径。

自己构造 `WM_DROPFILES` 验证整条链路：
```

页面 pending: {"n":2, "p":["动图_512.gif","动图_240.gif"]}

看不到控制台，出问题只能靠这个。

## 2026-11-03 凌晨 · 表情包发送通道

### 关键发现：GIF 文件就是原生表情

微信把剪贴板里的 `.gif` 文件识别成表情消息（`local_type 47`）。
对方收到的是原生表情 —— 能长按添加、会动。

### 真机踩出来的四个坑

**① 剪贴板格式不全**（`CF_HDROP` 不够）
微信是 Qt 应用，走 OLE，认 `DataObject` / `FileNameW`。
**格式存在 ≠ 别人读得懂。**

**② 临时目录被拒**（最贵的一个）

```
D:\大脑\表情测试\x.gif       → 彩色占比 10.3%，发出是表情
%TEMP%\bigfish-xxx\x.gif     → 彩色占比 0.0%，什么都没发生
```

**微信拒绝从临时目录粘贴文件。** 而我一直用 `%TEMP%` 造测试图 ——
十几轮都在查功能，其实功能没问题。

**③ 判据用灰度差，5.9 卡在阈值 6 下面**
输入框只有 88px 高，缩略图缩成 48×16 后差值被稀释。
换成**彩色像素占比**：空框 0.00%，有图 10.88%，阈值 2%。

**④ 验证过滤掉了自己发的消息**
`if sender_id != 2: continue`（照抄 vendor）。这台机器上自己发的
`sender_id=4`，于是永远返回 False。

### 真机结果

```
聚焦后 前台='微信' 焦点='微信'
草稿已进输入框（彩色占比 8.5%）
发送后新增 1 条
  · type='动画表情' sender_id=4
✓ 新增消息里有「动画表情」
耗时 9.3s
```

### 教训

**测试环境必须和真实环境同构。**

用 `%TEMP%` 做测试图是很自然的习惯，但它让一个和功能无关的
路径限制变成了「功能不工作」。而我先排查功能、后对齐环境，
白烧了十几轮。

同类错误还有一次：把 `paste_only.py` 报的「⚠ Ctrl+V 没生效」
当成了成功（因为看到输入框里有缩略图，而那是用户之前自己贴的）。

**读日志要读结论那一行，不要读自己希望看到的那一行。**

排查靠 `tools/ui_console.py`（把 console 消息全打出来）。

**`@Slot` 签名写错** —— `@Slot(str, result=str)` 但方法无参。
Qt 找不到匹配的槽，调用静默失败。犯过两次
（`list_memory_sessions`、`sticker_pick_files`）。
后来加了 `tools/check_slots.py` 静态检查。

**`__file__` 是相对路径** —— PyInstaller 打进去的模块，
`os.path.abspath(__file__)` 会按**当前工作目录**解析。
算出来的界面路径取决于用户从哪儿启动 exe。从 `dist/BigFish`
启动时恰好对，换个目录就找不到 `ui/index.html`。
新建 `bigfish/paths.py` 用 `sys._MEIPASS` 做锚点。

**`sticker_dir()` 无条件 makedirs** —— 鲸落删掉数据目录后，
随便一次界面刷新又把空目录建回来，"她不存在了"就不成立。

# 2026-11-04 · v0.4.0 说法层

## 起点

用户的原话：**「默认的思考、对话有点奇怪，不像真实人类」**，具体两条：

1. 一次发一大段，而不是「知道了」→「那明天去长坂坡吧」→「先看樱花再看枣树」
2. 对方连发三句时，第一句到就开跑，第二句还没发出来就被插话

参考了 MaiBot 与 AstrBot：前者有 `response_splitter` + `debounce`，
后者有 `SegmentationPolicy` + `ConversationFlow`。两边都没有发送确认。

## 做了什么

### 1. `bigfish/say.py`（610 行）

| 函数 | 职责 |
|---|---|
| `split_reply` | 分条：marker → 句末标点 → 逗号（>15 字）→ 硬切 50 |
| `plan_pacing` | 节奏：0.8 + 0.09×n^0.8，cap 3.5，抖动 ±20%，总 12s |
| `send_parts` | 逐条发送 + 三级确认（L1/L2/L3） |
| `split_reply_with_llm` | 可选兜底（默认关） |

保护：URL / @ / 代码 / 颜文字 / 数字单位 / **成对引号与括号**。

### 2. `bigfish/listen.py`（247 行）

`MessageBatcher`：同人 2s / 换人 0.8s / @ 1s / 纯图 4s，上限 8s、8 条。
纯状态机（`feed` / `tick`），时间由调用方给，测试直接跳时间。

### 3. 插件化

`bigfish/plugins/say.py`（176 行），座位 **890 · 说法**，
`plugins/__init__.py` 的 `PLUGIN_SEATS` 加 890。
面板自动出现（`inventory()` 驱动），8 个参数写 `plugins.json`。

**两个入口都读同一份配置**：
- 命令行 `app.py`：`_refresh_say_config()` 每批读一次
- 桌面端 `desktop.py`：`_say_plan()` 每轮读一次

### 4. 表情位置

原来固定「文字 → 表情」。改成按回应类型：

- 回应 ≤12 字 **且** 情绪强度 ≥60 → **先发表情**
- 其余 → 跟在文字后

判据抄 AstrBot 的 INSTRUCTION：「轻松、即时且图片足够表达时，可以只发一张原图；
需要解释时先说清文字。」

## 教训

1. **换目录 = 换实例**。数据根是 `<exe 目录>/data`，我每次打包到新文件夹，
   用户打开就是空数据 —— 看起来像"不保存"。以后统一部署到 `dist/BigFish`。
2. **`--selftest` 不跑引擎启动流程**，所以抓不到"一启动就崩"。
   现在打包前会跑 `pyflakes`，把未定义名挡在前面。
3. **强杀进程前先备份数据**：SQLite WAL 会自动恢复，但备份是零成本的保险。
