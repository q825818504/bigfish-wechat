> 2026-11-04 23:10 更新（**v0.6.0 本地完成，未发布**）

## 发布策略

**hotfix 不单独发版。** 本地改、本地打包、本地验证，攒到下一个大版本一起发。

理由：这个项目只有一个人跑，没有别的用户在等修复。单独为 0.4.1 出一个
Release 要重新走打包 + 清单 + 上传，收益为零；而版本号快速跳跃会让
CHANGELOG 里的 v0.4.x 变成一堆细碎条目，回头看找不到重点。

`bigfish/__init__.py` 里版本号照常往前走（0.4.1），这样本地自检、
部署脚本、`--selftest` 的版本显示能对得上。只是不打 tag、不传 Release。

下一个对外发布点：**0.5.0**（已按这个策略攒完，2026-11-04 发布）。

## 下一步优先级（v0.5.0）

### P0：失控类问题 —— 先保证不会自己跑飞

自环事故之后调整了优先级：**能自己跑飞的问题，比"回得好不好"更重要**。
它一旦发生，用户只能杀进程，而且记忆库会被污染。

- [x] 自环防护（v0.4.1 已完成）
- [x] **模型失败重试**（v0.6.0）：429/5xx/网络重试 3 次，4xx 直接报错
- [ ] **同类审计**：还有哪些地方是「精确识别 + 没有兜底」？
      - 表情包回环：`_send_sticker` 现在记的是空串，靠 `is_self` 单层
      - 群里 @ 自己：`parts[0] = f"@{sender} {parts[0]}"`，被读回时前缀
        能不能剥干净？现在 `_normalize` 剥 `@\S+\s*`，多人连续 @ 要验
      - 攒批层：`listen.py` 里 `is_self` 过滤是单层，没有熔断
      - 三条都要补：要么加熔断，要么写测试证明不需要
- [ ] **真机跑一晚**：验证 0.4.1 在同一场景下不再自环，
      同时看 `[回环]` 日志频率是否正常（每轮 1~4 行）

### P1：参数标定 —— 先量出来，再改

- [ ] **节奏标定**：`per_char=0.09` 与 `confirm_timeout=3s` 都是拍的。
      跑一天，统计「发送→确认」延迟分布，按 P50/P90 反推
- [ ] **攒批窗口标定**：2.0s 是抄 MaiBot 的，微信场景要实测（对方平均打字间隔）
- [ ] **熔断阈值标定**：`trip=4` / `mute=120s` 是估的。
      4 轮是否太敏感？看日志里有没有误熔断

### P2：质量

- [ ] **回复像不像人**：现在只能靠 prompt 压「不要解释自己」。
      需要按具体失败句子迭代（用户贴日志 → 改 prompt → 再跑）
- [ ] **表情与分条配合**：表情目前跟"整轮"走，没有跟具体某一条绑定
- [ ] **LLM 断句兜底**：`say_llm_split` 开关已留，默认关（多一次调用，慢一倍），
      需要确认长回复场景值不值

### P3：稳定性

- [ ] 微信重启后自动重连（现在要手动重启程序）
- [ ] 长时间运行（8 小时+）内存与连接泄漏
- [ ] 记忆库长期增长后的检索速度（现在没压测过）
- [x] 模型不可用时给界面提示（v0.6.0：重试 + 降级日志；**界面红点仍待做**）

### 明确不做的

- 概率合并断句（MaiBot 的随机切分）—— 不可复现，单人项目调试会疯
- 词表断句（AstrBot 的 words 模式）—— 中文微信场景收益低
- 自动合并跨平台账号 —— 技术上不可靠
- 让模型修改 visibility —— 它一定会被诱导
- 数据根跨目录自动共享 —— 见 decisions D-55
- 为 0.4.1 单独发版 —— 见本文开头「发布策略」
