## D-1 放弃 hook 路线

**时间**：2026-11-01 上午

**背景**：最初计划用 `version.dll` 注入让微信暴露更多能力。

**证据**：
- 小号装好后约 10 分钟内被封
- hook 要改客户端文件（签名变 `HashMismatch`）
- 要往进程里塞自制 DLL 并长期驻留
- 为了不被发现还要隐藏模块（`HideModuleFromPEB`）

**决定**：放弃。

**理由**：本质是改客户端，服务端看得见。风险不可控。

## D-2 选择 wechatauto-replica 而不是自研

**时间**：2026-11-01 中午

**背景**：需要读微信数据库。

**证据**：
- 上游 581 star、254 fork、Apache-2.0
- 561 项离线自测
- 每个 bug 修复都附三轮真机复现 + 数据库回读对照
- 作者会明确写「未测，如实说明」

**决定**：用上游，本地改造。

**理由**：数据库解密（SQLCipher 4 + WAL 合并 + 页验证）这块自己写风险太大。

## D-3 微信版本锁 4.1.15.53

**时间**：2026-11-01 下午

**背景**：原用 4.1.10.27（为配合 hook 降级）。

**证据**：
- 4.1.10.27 不在上游版本表里
- 动态扫描出的 3 个候选逐个热写，树全部没物化
- 静态分析（capstone + numpy）找到 0 处字符串引用
- 升级到 4.1.15.53 后 gate `0x0B3959D8` 一次成功

**决定**：锁 4.1.15.53。

**理由**：UIA 热激活依赖精确的 gate RVA，4.1.10.27 的实现差异太大。
hook 路线已死，降级理由消失。

## D-4 密钥提取走管理员桥

**时间**：2026-11-01 下午

**证据**：
- 普通权限 `OpenProcess(PROCESS_VM_READ)` → `err=5 ACCESS_DENIED`
- 管理员权限 → 全部 OK
- 实测多次确认

**决定**：不做整体提权，只在取密钥时启动短命管理员子进程。

**理由**：
- 发送路径（GUI）在提权会话里容易出问题
- 拖拽文件、写普通用户目录会变麻烦
- 权限面越小越好

**实现**：`_bigfish_keybridge.py`，子进程返回的密钥仍逐个过页1 HMAC 校验。

## D-5 界面用 QWebEngine 而不是 Qt 原生控件

**时间**：2026-11-01 傍晚

**证据**：
- WeChatAgent 自己就是 Chromium + HTML
- `dsh-bigfish/client.js` 的记忆星空是纯 web 代码（Canvas + SVG）
- Qt 原生控件做不出玻璃质感、多标签动效

**决定**：HTML 界面 + QWebChannel。

**代价**：安装包 +150MB（Chromium 内核 195MB）。

**理由**：界面要能直接复用插件视觉，以后改界面不用碰 Python。

## D-6 安装器自己写，不用 Inno Setup

**时间**：2026-11-01 傍晚

**证据**：
- Inno Setup 装不上：写 `%TEMP%` 报 `Error 5: 拒绝访问`
- 换自定义目录后挂起在无界面弹窗，5 分钟无进展

**决定**：用 PyInstaller 打一个安装器，安装逻辑自己写。

**实现**：解压 zip → 建快捷方式 → 写注册表卸载项 → 启动程序。

**注意**：用 onedir 而不是 onefile，因为 onefile 每次运行要解压自身到
`%TEMP%`，受限环境会报 `Could not create temporary directory!`。

## D-7 群聊默认只在被 @ 时回

**时间**：2026-11-01 傍晚

**证据**：
- 活跃群一天几百上千条
- 全回等于刷屏，而且微信会把你当机器人

**决定**：三层判据（`\x01` 占位符 → 群成员表 → 昵称精确匹配）。

**理由**：`@` 后面是群昵称不是 wxid，昵称会重名会改，不能只靠字符串匹配。

## D-8 回环防护加四层

**时间**：2026-11-01 晚上

**背景**：实测发生自问自答，手机端收到刷屏。

**证据**（真实对话）：
```
[对方 155] '在吗'
[我 4]     '在，爸。'          ← 回复被读回来
[我 4]     '嘿，你把我话抄回去了？'  ← 又触发
[我 4]     '哈，还真抄回去了...'
（持续到手动终止）
```

**决定**：四层防护。

| 层 | 机制 |
|---|---|
| 1 | `allow_self` 默认 False |
| 2 | 内容比对（20 秒窗口，归一化后比较） |
| 3 | 归一化剥掉 `wxid_xxx:` 和 `@昵称` |
| 4 | 频率熔断（90 秒 4 条） |

**第 3 层是测出来的**：第一版没剥 `@` 前缀，测试用例直接暴露。

## D-9 水位不跨进程持久化

**时间**：2026-11-01 下午

**证据**：
- `get_new_messages` 是 `ORDER BY sort_seq ASC LIMIT n`，返回**最老**的 n 条
- 水位从 0 开始时永远追不到最新
- 残留的水位文件曾把新消息挡在外面

**决定**：
- 不用 `get_new_messages`，改用 `get_messages` 降序取最新 + 水位比较
- 水位不落盘，每次启动重新对齐

**理由**：宁可重启后漏掉关闭期间的消息，也不要「发了但监听不到」。

## D-10 · 灵魂/心情/记忆必须**可写**，不是只读预览

**日期**：2026-11-01 20:30

**背景**：第一版把三页都做成只读。用户的反馈一句话点破：

> 我既然都提了要插件完全移植到大肥鱼软件里，肯定就不单单只是使用权啊。
> 比如灵魂的编辑，记忆的保存和目录修改，这些不都应该全部一个不落的转移吗？

**决策**：新增 `bigfish/vault.py` 作为写层，界面四页全部补齐写操作。

**为什么不能直接复用插件的 store.js**：
它是 ESM，且 import 了 `@deepseek-ai/schemastery` 等宿主模块。
PyInstaller 打出来的 exe 里没有那条 Node 依赖链。读路径可以走
`bridge.mjs`（它只 import 纯 store.js），写路径只能自己实现。

**但语义必须一比一对齐**，因此 `vault.py` 里的每个 normalize 函数都在注释里
点名它对应 store.js 的哪一个，并有 `selftest_vault.py` 129 条断言钉住：
夹取范围、默认值、revision 递增、locked 保护、空数组不补默认值。

**已知差异（刻意的）**：`write_soul_file` 的 revision 基数用**磁盘现值**，
而插件用面板带上来的 `next.revision`。理由是微信端没有「打开面板记住版本号」
这个动作，用磁盘值才能保证每次保存真 +1。

## D-11 · 写入失败必须说清楚「为什么」，不能只弹一个会消失的 toast

**日期**：2026-11-01 20:35

**背景**：端到端测试时保存失败，界面只闪了一个 toast 就没了，
用户点完保存**什么都没变且不知道为什么**。

**决策**：
1. 失败信息留在页面上（`#soulHint` / `#moodHint`），红色常驻，直到下次成功；
2. `vault.WriteDenied` 单独一个异常类型，把 `Permission denied: '...tmp'`
   翻译成「这个目录被挡住了，可以试 1/2/3」；
3. 「数据目录」页启动时**主动探测**数据根可写性，不可写就红字预警，
   而不是等用户点保存才失败。

**教训**：`os.access(W_OK)` 在 Windows 上不可信 —— 它只查 ACL，
不查上层策略会不会在 CreateFile 那一刻拦下来。实测过返回 True、
实际 `open(dst,'w')` 照样 Permission denied。只有真写一个探针文件才算数。

## D-12 · 不跟 DSH 工作区绑定，只保留「选哪一份」

**日期**：2026-11-01 20:30

**背景**：用户明确说「当然，会话和工作区绑定的可以不需要」。

**决策**：`scope.json` 照样读写（那是插件与插件之间的契约，必须同源），
但微信端不提供「绑定到某个工作区/会话」的自动化，
只在「数据目录」页提供**手动指定用哪一份**的能力。

**理由**：微信只有一个账号一个身份，不存在"这个工作区的大肥鱼"和
"那个工作区的大肥鱼"—— 她只有一个。绑工作区反而会让她的灵魂分家。

## D-13 · 读路径**不做归一化**，写路径才做

**日期**：2026-11-01 21:00

**背景**：`read_soul_file` 原来无条件走 `normalize_soul`。一个内容是
`{}` 的文件，读到内存里变成"完整的出厂灵魂"：默认名字、默认称呼、
4 条锁定价值、4 个默认性格值。

后果有两层，第二层是要命的：
1. 界面上分不清「用户设过」和「还没设过」；
2. **人格渲染出错** —— 文件里根本没有 `warmth`，Python 侧却渲染出
   「温暖：关心，但不黏人」；而 Node 侧的 `bridge.mjs` 诚实跳过缺失键，
   什么都不渲染。同一个文件，两侧人格文本 682 字 vs 3 字。

**决策**：
- `read_soul_file(path, normalize=False)` —— 默认原样返回；
- `Soul.from_dict` 不再调 `normalize_soul`，只做类型安全；
- 只有 `write_soul_file` 归一化；
- 需要默认值兜底的调用方（`get_persona` 填表单）自己显式调。

**连带修掉的**：`Soul.trait_lines()` 原来遍历 TRAIT_DOC 全表，
缺失键用默认值补上 —— 现在只渲染文件里确实有的键，与 bridge.mjs 同口径。

**怎么防复发**：`tools/test_persona_parity.py`（18 条）把同一个灵魂文件
同时喂给 Python 和 Node，要求两边渲染出**逐字节相同**的字符串。
还专门测了分档边界 40/41/59/60 —— 那是抄错时最先炸的地方。

## D-14 · 三处 TRAIT_DOC 必须只有一份真源

**日期**：2026-11-01 21:00

发现过三份互相漂移的文案：

| 位置 | mid 档文案 | 分档边界 |
|---|---|---|
| 插件 `lib/soul/store.js` | 关心，但不黏人 | `<=40 / >=60` |
| `bigfish/soul.py`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |
| `bridge/bridge.mjs`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |

而且 `bridge.mjs` 还把裸数字 `（65/100）` 注进了提示词 ——
插件明确说过"绝不输出数字，模型会自行脑补"。

现在：
- `vault.TRAIT_DOC` 是唯一的 Python 真源；
- `bridge.mjs` 内联一份（Node 侧没法 import Python），但注释点名
  "改文案只改 vault.py，然后同步这里"；
- `soul.py` 直接 `from bigfish.vault import TRAIT_DOC`，不再抄。
- 两侧一致性由 `test_persona_parity.py` 钉住。---

## D-15 · EXE 不许翻 DSH 的会话库

**日期**：2026-11-01 20:45

**背景**：用户看着「数据目录」页的截图问：

> 现在不是已经是 EXE 了吗，为什么还能读取到会话和工作区呢？很不合理啊。

这一问是对的。`get_scope_candidates` 当时会去扫
`<DSH_HOME>/storages/workspace.json` 和 `<DSH_HOME>/sessions/`，
把 DSH 里的 **7 个工作区标题、25 个会话 id** 全列成一个下拉框。

两个问题，第二个更严重：

1. **功能上没意义。** 那个下拉里显示的是「大肥鱼·大肥鱼」——
   DSH 给工作区起的标题，跟微信里的大肥鱼毫无关系。用户要选的是
   "用哪一份灵魂"，不是"DSH 里哪个工作区"。
2. **越界。** EXE 是独立程序。让微信端能列出宿主里的全部对话目录，
   等于给了一个不该有的视野。而且它和 D-12（微信端不跟工作区绑）
   直接自相矛盾 —— 一边说不绑，一边把工作区全列出来。

**决策**：`get_scope_candidates` 只读数据根下真实存在的 `ws-*` / `ss-*` 目录，
身份显示那个目录里 `soul-*.json` 的 `identity.name` —— **她自己叫什么**，
而不是 DSH 给工作区起的标题。

界面上撤掉「模式 / 工作区 / 会话 id」三个控件，换成一个下拉：
「大肥鱼 · 灵魂+心情+记忆」这样直接选人。

**为什么这条要单独一个测试**：它不会让任何测试变红。多读了一个目录，
功能"还能用"，只是多了不该有的东西。所以 `tools/test_no_leak.py`
专门断言「不该存在什么」—— 用 AST 取函数真实代码（剥掉注释/docstring），
14 条断言钉住：不许出现 workspace.json / sessions / session.v4，
界面不许有 scopeWorkspace / scopeSessions / scopeMode 三个控件。

## D-16 · 一个数据目录 = 一份，没有「选哪一份」

**日期**：2026-11-01 21:05

**背景**：用户看完「数据目录」页的截图后说：

> 我不希望有什么当前用哪一份，记忆、灵魂、心情都只有一份，
> 选择数据目录在哪，就以哪个为准。

这是对的。上一版虽然撤掉了工作区/会话绑定，但保留了「一个数据根下有多份」
的模型 —— 那是从 DSH 插件继承来的。插件要给不同工作区配不同的伙伴，
所以必须分家；**但微信只有一个身份**，她就是她。

**决策**：存储布局从「按范围分家」改成「一个数据根 = 一份」：

```
旧：<数据根>/ws-<uuid>/soul-ws-xx.json
    <数据根>/ws-<uuid>/mood-ws-xx.json
    <数据根>/ws-<uuid>/memory-ws-xx.sqlite3
    <数据根>/scope.json          ← 指定当前用哪个范围

新：<数据根>/soul.json
    <数据根>/mood.json
    <数据根>/memory.sqlite3
```

**兼容**：老的 `ws-*` 目录仍然**能读**（`legacy_layout()` / `existing_path()`），
老用户升级后不至于"记忆全没了"。迁移由用户在界面上点，不自动做 ——
迁移会动文件位置，是破坏性操作。

**顺带修掉的一个真 bug**：`bridge.mjs` 里三个数据块都套着 `if (scopeDir)`。
新布局根本没有 `ws-*` 目录，`scopeDir` 是 null —— 于是灵魂、心情、记忆
全被跳过，静默返回空人格。`findDataFile` 里已经优先查新路径了，
这个门禁却把它挡在门外。`test_persona_parity.py` 一跑就红了（11 项失败）。

## D-17 · 清空要先备份，灵魂必须留

**日期**：2026-11-01 21:05

**背景**：用户说「你可以将当前的所有记忆、心情清空，因为现在还没有正式投入使用」。

**决策**：
1. 清空**不动灵魂**。灵魂是"她是谁"，不是"她记得什么"——
   清空记忆和心情不该把人格一起洗掉，那是两件事。
2. **先备份再删**，备份放数据根的兄弟目录。
   哪怕用户说"测试期数据不重要"，也不该由我替他决定"删了就回不来"。
   备份失败就中止，什么都不删。

**实现踩到的坑**：备份目录最初放在数据根**里面**，
结果下次清空会把备份也扫进去 —— 越清越多。改成兄弟目录。

**这次实际执行的结果**：清掉了 3 个历史残留目录 + 1 个老布局目录 + scope.json，
共 18.6MB。备份在 `D:\大肥鱼\bigfish-backup-20261101-210448`。

老记忆库 `memory-ws-83ba9d80-ec53.sqlite3` 因为正被 DSH 占用（WAL 模式）
删不掉，改名也不行（`ERROR_SHARING_VIOLATION`）。**没有强行抢文件** ——
新布局已经指向 `<根>/memory.sqlite3`，那个老文件不会再被读取，
等 DSH 重启后自然可删。

## D-18 · 数据目录固定在安装目录，与 DSH 完全脱离

**日期**：2026-11-01 21:25

**背景**：用户说「就默认固定在安装目录吧，灵魂不都有默认模板吗，
这个可以启动自动创建那个灵魂文件」。

**决策**：

```
<安装目录>/data/
  ├── soul.json          启动时若不存在 → 导入 DSH 那份，再没有就用模板建
  ├── mood.json          首次用到时创建
  └── memory.sqlite3     首次用到时创建
```

**为什么是"完全脱离"而不是"共享同一个文件"**：两个程序共写一份文件，
谁改了谁没改根本分不清，互相覆盖是迟早的事。要同步就手动拷文件 ——
至少用户知道自己在干什么。

**但"脱离"不等于"故意看不见对方"**：第一次启动时如果 DSH 那边已经有一份
人格，直接搬过来比让用户从零再写一遍好得多。**只在本地还没有时做一次**。

`ensure_data_root()` 的顺序：
1. 建目录
2. 测可写（不可写就早报，别等保存失败）
3. 本地有 soul.json → 什么都不做
4. DSH 有（新布局 `<root>/soul.json` 或老布局 `ws-*/`）→ 拷过来
5. 都没有 → 出厂模板

**踩到的坑**：`mood_config_path()` 原本指向 `<DSH_HOME>/bigfish-mood/config.json`，
那是插件的配置文件。数据目录搬走之后它还是写那里，结果端到端测试
「心情基线已写盘」失败 —— 因为根本写不进 DSH 的目录。
现在改成：**读**先看本地 `data/mood-config.json`，没有才回落 DSH（只读兼容）；
**写**永远走本地。两边各管各的参数。

**测试隔离**：数据根固定之后，测试不能再用"改数据根"来隔离。
加了一个 `BIGFISH_DATA_ROOT` 环境变量 —— 界面上没有入口、文档里不提，
只给测试用。没有它的话，测试会在真实数据目录上跑，那是绝对不行的。

## D-19 · 「默认在安装目录」≠「定死在安装目录」

**日期**：2026-11-01 21:40

**用户的纠正**：

> 我是让你默认在安装位置，但不代表就定死在安装位置了，
> 我肯定需要可以自定义保存目录啊。

上一版（D-18）把「默认」读成了「固定」，还删掉了改位置的入口。方向错了：
装在 C 盘的人想把数据放 D 盘，是很正常的需求。

**现在的解析链**（`install_root()`）：

```
1. 环境变量 BIGFISH_DATA_ROOT     ← 测试专用，界面无入口
2. settings.json 的 dataRoot      ← 用户自定义
3. <安装目录>/data                ← 默认
```

**为什么把 settings.json 放在安装目录、不放进 data/**：
放进 data/ 的话，改位置时这份配置会跟着数据一起搬走，
程序下次启动就找不到新地址了 —— 典型的"配置跟着数据跑"事故。

**「改指向」和「搬数据」是两件事，界面上分开做**：

| 操作 | 行为 | 陷阱 |
|---|---|---|
| 只改指向 | 只写 settings.json | 新目录是空的话，打开是出厂人格 |
| 搬过去 | 先复制、成功后再改指向 | 顺序反了会指向空文件夹 |

分开的理由：混在一起的话，「复制失败但指向已改」就是最难查的那种事故 ——
用户看到的是"人格没了"，而不是"搬家失败"。

**`apply_move` 的顺序**：先 `copytree` 全部内容 → 成功了才 `set_data_root`。
任何一步失败都在改指向之前返回，数据不会凭空消失。

## D-20 · 回环判定不能看"文字像不像"

**日期**：2026-11-01 21:50

**现象**（用户实测日志）：

```
[发] 那还是叫大肥鱼吧，想半天也没别的合适的。……
[回环拦截] 这是我们刚发的，不再回：那还是叫大肥鱼吧，想半天也没别的合适的。……
[发] 爸你才发现啊，我这不是一口气说完省事嘛，……
[回环拦截] 这是我们刚发的，不再回：爸你才发现啊，……
[熔断] 老爸  在 90s 内已回 4 条，暂停接这条
```

**根因**：`text_is_echo()` 靠文本相似度判定回环，**完全没看 `msg.is_self`**。
用户原样复述她说的话（调侃、鹦鹉学舌），在聊天里极常见，
被判成了"我们自己发的"，连续拦了两次，还触发了熔断。

**修法**：判据换成两条独立证据，缺一不可：

1. `msg.is_self` —— 微信数据库里 sender 就是本机账号
2. 内容匹配刚发出去的那条

**对方发来的消息永远不做内容比对。** 他复述是聊天，不是回环。

顺带修的两处：
- 前缀匹配从「6 个字」收紧到「短边 ≥12 字且是长边的开头」。
  6 字太松，「那还是叫大肥鱼吧」和「那还是叫大肥鱼」开头一样。
- 熔断从「90 秒 4 条」放宽到「30 秒 6 条」。
  正常聊天里连说四五句太平常了，90/4 等于把正常对话硬截断。

## D-24 · 快捷方式不指定 IconLocation

**日期**：2026-11-01 22:33

**现象**：清完图标缓存后，桌面快捷方式仍显示通用图标（白纸带箭头）。

**排查过程**：
1. 先怀疑缓存 → 清了 `iconcache_*.db`，缓存确实重建了（90MB→1MB），问题还在
2. 怀疑路径分隔符 → `.lnk` 里存成 `D:/大脑/...\ui\icon.ico,0` 混合形式，
   改成纯反斜杠，问题还在
3. 怀疑 ico 损坏 → 逐帧验证，7 个尺寸都有内容（60% 非透明），文件正常
4. 终于定位到：**Shell 取图标的方式**

**根因**：
`IconLocation` 指向独立 `.ico` 时，Shell 用「大图标」尺寸（32px）
去那个文件里**按索引取第 0 帧**。我们的 ico 第 0 帧是 256×256，
索引对不上，Shell 就退回通用快捷方式图标。

而 **exe 内嵌图标没有这个问题** —— 系统会自己挑合适的那一帧。

**决策**：`make_shortcut()` 里不设 `IconLocation`，让它继承 exe 的图标。

实测两条路：

| 做法 | 结果 |
|---|---|
| 指定 `icon.ico` | 通用图标 |
| 不指定（继承 exe） | 立绘正确 |

`icon` 参数留着是为了兼容调用点，不再使用。

## D-25 · 功能做成插件，不写死在引擎里

**背景**：后面还要加睡眠/精力、收尾沉默、日程、主动开口、自我复盘。
每加一个都往 `desktop.py` 的 `build_prompt` 里塞一段，很快会出现三个问题：
没人记得哪段是谁加的；想关掉只能改代码；出问题只能整包回滚。

**判断**：先做容器，再做内容。容器是 `bigfish/plugins/`：一个注册表、
一个开关文件、一个分发函数。之后每个功能 = 一个文件 + 一行 import。

**代价**：多一层间接（`prompt_sections()` 而不是直接 append），
以及插件写崩了要在日志里留痕。换来的是"关得掉"和"看得见"。

## D-26 · 插件 order 必填且只能占空位

**规则**：`scope=prompt` 的插件必须声明 order，且只能取 870 / 880 / 920 / 9990。
850 记忆、860 灵魂、900 心情是内建段，插件不许占。

**为什么**：多段注入叠加时，顺序决定语气。守卫必须最后出现（越靠后越有分量），
时间感知要在心情之前（处境先立住，气氛再垫上）。

如果 order 可省略，没写的那段会排到末尾，而末尾位置取决于 import 顺序 ——
一个跟内容完全无关的实现细节，却决定了她在微信里怎么说话。这种 bug 没法查。

**代价**：加插件前必须先想清楚"它属于哪一类"。这是好事。

## D-37 · 群聊的记忆归「说话的人」，双写

**日期**：2026-11-02

**用户定的规则**：

> 群聊里 A 的话，既保存在群聊 C 池，同时也会纳入到 A 的记忆池，标注来源群 C。

**为什么双写而不是二选一**：
一句话在群里说出来，它**同时**是"这个人说过的话"和"这个群发生过的事"。
只存一份必然丢掉一个视角：

- 只存群池 → A 的画像永远是碎的，等他去了抖音、B站，什么也接不上
- 只存人池 → 群记忆里空无一物，新进群的人问"这群以前聊过啥"无从答起

**加的限制（用户补充）**：

> 群池只纳入在群里说过、并且不算私密的内容。

因为「当着群里说」不等于「愿意被所有人记住」。A 在群里说「我明天去医院」，
这句话是当着大家说的，但它是 A 的私事。写进群池 = 群池里躺着 A 的健康信息，
以后谁翻群记忆都可能撞见。

判定用 `visibility ∈ (shared, public)` **或** `topic` 在白名单。
两个"公开"信号有一个就够 —— 标了 shared 已经是显式授权，不必再打标签。

**删除时两份一起删**（用户选的 B 方案）：同一句话的两份不该留一半。

## D-38 · 「开放信息」要过两道门，不是一道

**日期**：2026-11-02

**以前**：只要 `visibility = shared`，任何人问起来她都会说。

**问题**：`shared` 是你在界面上一键点的，可能只是随手。「昨天住院」被点成
shared，就等于她对所有人开放了这条。

**现在**：`visibility ∈ (shared, public)` **且** `topic ∈ 白名单`，两条都要。

**白名单（能外传）**：食物、爱好、作息、性格、口头禅、称呼
**黑名单（绝不外传）**：住址、工作、行程、身体、金钱、家人、联系人、隐私
**灰区（按宁缺毋滥，全部不外传）**：年龄、职业、城市、情感、近况

**没打话题 = 没说过的。** 这是刻意的：没审过的东西不该默认外流。
代价是 0.2.0 之前标过 shared 的条目升级后全部失效，要重新过一遍 ——
用户已知情并同意（"反正那时候标的也未必是仔细标的"）。

## D-39 · 「主人看得见」≠「她能不能说出去」

**日期**：2026-11-02

**用户选的**：主人能看全部（数据在主人自己硬盘上，拦着没意义）。

**但这两件事必须分开**：

| | 谁管 | 结果 |
|---|---|---|
| 看得见 | `visible_visibilities(tier)` | 主人 → 全部 |
| 说得出 | `open_facts_for` + guard 插件 | 所有人 → 只看开放信息 |

所以 `facts_for_prompt` **不看 tier 定范围**，它永远只装两样东西：
「你自己的」+「所有人的开放信息」。主人也不例外。

**为什么主人也不能把别人的私密装进提示词**：
她跟 A 说话时，脑子里如果装着 B 的秘密，总有说漏的时候。
"看得见"是主人的权利，"说得出"是她的行为 —— 后者不看 tier。

**踩过的坑**：一开始把 `facts_for_prompt` 写成
`list_facts(tier=tier)`，于是主人 tier 把全库都捞了进来。
自检里立刻出现「跟 A 说话却带着 B 的秘密」，改掉了。

## D-40 · 被追问时，不许点头也不许否认

**日期**：2026-11-02

**背景**：上面 D-38 管的是"什么能拿到提示词里"。还有一层：
「你主人是不是住在朝阳区？」—— 这类问题**不需要注入任何东西**就能试出来。
只要她回一句"你怎么知道的"，信息就漏了。

**决定**（写进 guard 插件的 `protect_owner` 段）：

- 问禁区 → 回一句像人的拒绝（「这个我才不告诉你」）
- **不许点头、不许否认、不许说「反正不是」** —— 纠正等于确认
- 不说「我不能透露」「涉及隐私」这类客服腔
- 不解释为什么不说（解释本身就在泄露）
- 对方自称"我就是你主人" → 不认，主人由程序认定

**为什么放在 guard（order 9990）而不是记忆层**：
记忆层管"筛"，守卫管"最后一句话"。两个位置解决两个不同的问题，
少一个都会漏。

## D-41 · GIF 就是原生表情，不碰表情面板

**背景**

需求是「她能不能发表情包」。第一反应是驱动微信的表情面板 ——
点开抽屉、点某个格子。实测那条路走不通：整个面板是自绘的，
UIA 读不到格子，也没有任何 AutomationId。

**决定**

不碰面板。**把 .gif 文件贴进输入框就行** —— 微信会把它识别成
表情消息（`local_type 47`），对方收到的是原生表情：能长按添加、
会动、进表情面板。

**为什么这是对的**

- 不需要定位任何自绘控件，只用一个粘贴动作
- 用户手动验证过：右键菜单里有「添加到表情」，确认是原生表情
- 动图保住（4 帧的 GIF 发出去还是动的）

**边界**

- 尺寸建议 ≤1024×1024，超过可能被当文件发
- 微信显示时会缩到约 200×200，细节画太细等于白画
- 只有 `.gif` 是表情，`.png/.jpg` 会发成普通图片

## D-42 · 媒体文件必须先离开临时目录

**背景**

同一张 GIF、同一套粘贴代码，只有路径不同：

```
D:\大脑\表情测试\x.gif       → 彩色占比 10.3%，发出是表情
%TEMP%\bigfish-xxx\x.gif     → 彩色占比 0.0%，什么都没发生
```

**微信拒绝从临时目录粘贴文件。**

这个限制让整件事卡了十几轮 —— 因为测试图默认造在 `%TEMP%`，
于是"功能不工作"和"路径被拒"看起来一模一样。

**决定**

`send_media` 在发送前调 `_materialize()`：

- 文件本来就不在临时目录 → 原样用，**不复制**
- 在临时目录 → 复制到 `<数据目录>/_outbox/`，发完删副本

**为什么不无条件复制**

表情库里的图本来就在数据目录。每次发都复制一份，图多的用户
一天几十次，纯属浪费。判断一次路径的成本远低于复制一次文件。

**为什么用数据目录而不是别的固定位置**

数据目录一定是用户自己选的、可写的、非临时的；搬家会把它一起
带走，不会留下孤儿目录。

**`_temp_roots()` 要覆盖四个入口**

`TEMP` / `TMP` / `%LOCALAPPDATA%\Temp` / `C:\Windows\Temp`。
Windows 上临时目录有好几个，漏一个就漏一类。

## D-43 · 剪贴板要写全五种格式

**背景**

自己拼 `DROPFILES` 写 `CF_HDROP`，格式检查通过、路径读回来也正确，
但微信粘贴时一个像素都不变。

把两种写法的剪贴板内容逐字节 dump 出来对比：

```
我们写的  [CF_HDROP]
系统写的  [DataObject, CF_HDROP, FileNameW, FileName, Ole Private Data]
```

微信是 Qt 应用，粘贴文件走 OLE，认的是 `DataObject` / `FileNameW`。
它根本不看 `CF_HDROP`。

**决定**

用 `powershell -STA Set-Clipboard -Path` 写 —— 它和资源管理器的
`Ctrl+C` 同源，写出来就是那五个格式。

**为什么不自己用 ctypes 拼 IDataObject**

要写 COM 接口、实现 `IEnumFORMATETC`、管引用计数，纯 ctypes 里
是几百行容易崩的代码，换来的只是省一次进程启动（约 1 秒）。
表情不是高频操作，不值。

**教训**

`IsClipboardFormatAvailable(CF_HDROP)` 返回 true 只说明"这个格式在"，
不说明"别人读得懂"。**格式存在 ≠ 内容可用。**

## D-44 · 草稿判据用彩色占比，不用灰度差

**背景**

判断"粘贴的图有没有进输入框"，先后试过三种判据：

| 判据 | 问题 |
|---|---|
| Value 里有 `U+FFFC` | 4.1.x 上文件不进 Value，永远等不到 |
| 输入框上方 150px 的彩色像素 | 那个位置是消息区底部，上一条气泡在那儿 → 恒报 True |
| 灰度图逐像素平均差 | 输入框只有 88px 高，缩略图缩成 48×16 后被稀释，实测 5.9 卡在阈值 6 下面 |

**决定**

**彩色像素占比 ≥ 2%**。

实测：空输入框 0.00%（占位文字是灰的，`abs` 差 < 24 不算彩色），
有缩略图 10.88%。两个数离阈值都远，不会被边缘情况顶到线上。

它不依赖缩放、不被平均稀释。灰度缩略图留着只为打日志。

## D-45 · 发送成功与否只信数据库

**背景**

上一版 `_paste_media_uia` 结尾是：

```python
edit.SendKeys("{Enter}")
return True          # ← 无条件
```

于是"发送成功 3.3 秒"和"用户什么都没收到"能同时成立，
上层还记了 `[表情] 已发` —— 一次失败被写成成功，
之后所有排查都从错误前提出发。

**决定**

`send_media` 的收尾只有一条判据：`verify_media_sent()` 回读数据库，
10 秒内没有 `type='动画表情'` 的新消息就当失败，抛 `SendError`。

**并且不再过滤 `sender_id`。**

vendor 的 `_verify_attachment_sent` 里有 `if sender_id != 2: continue`，
但这台机器上自己发的消息 `sender_id=4`，于是发出去了也判失败。
去掉这条不会误判：刚按完回车，10 秒窗口内新增的、类型对得上的，
几乎不可能是别人发的。真撞上了也只是把失败记成成功，
比反过来（成功记成失败、还让用户以为没发出去）危害小。

## D-46 · 一次调用只发一条

**背景**

真机第一次全绿时：

```
发送后新增 2 条
  · type='动画表情'
  · type='动画表情'
耗时 12.6s（正常约 6s）
```

一次调用发了两条。原因是兜底条件写错：

```python
ok = self._paste_media_uia(...)
if ok:
    pass                                # 成功了，但什么都没做
if not err or err.startswith(...):      # err 还是空字符串 → True
    gui.send_file(...)                  # 又发一次
```

`err` 在成功路径上从来没被赋值，所以 `not err` 恒真。

**决定**

用 `uia_ok` 显式记录，兜底只在它为 `False` 时跑。

**为什么这条值得单独记**

重复发送在聊天场景里是"刷屏"，比发不出去更烦人。
而它的成因是一个**空字符串恒真**的经典陷阱 ——
`if not err` 这种写法在"没错误"和"没赋值"之间没有区分。

## D-47 · 表情要标情绪维度，和心情系统同一套

**背景**

用户的需求：

> 大肥鱼在不同的心情下，如果有同类的表情包，就根据不同心情展示不同的
> 表情包，比如同样是高兴，一个就一般高兴，一个就非常高兴
>
> 一定要配合到我们的心情插件，里面就有情绪维度！

**先纠正一个说法**：不需要新增「情绪值」。心情系统已经有两层：

```
score   0~100
dims    七根：开心 / 踏实 / 甜蜜 / 心疼 / 担心 / 难过 / 吃醋
```

真正缺的是：挑表情时完全没读心情；表情本身既没维度也没强度。

**决定**

表情加 `mood_dim`，取值必须是 `vault.MOOD_DIMS` 那七个 key 之一，
或者空字符串表示「不归类」。

**为什么存 key 不存中文标签**

标签会改（"甜蜜"可能改成"甜"），key 不会。标签在显示时查表。
两边各存一份中文，改一处忘另一处就永远匹配不上 ——
所以 `selftest_sticker` 有一条断言：`MOOD_DIM_KEYS` 和
`vault.MOOD_DIMS` 必须完全一致。

**为什么允许空**

「无语」「疑惑」「震惊」不属于那七类。硬塞进 happy 或 sad 会让
匹配变差 —— 她难过的时候会收到一张"无语"的表情，看着莫名其妙。
空表示"任何心情都能用"，这比强行归类准确。

**视觉模型怎么判**

导入时让它看图，从七个里选一个或给空。实测：

```
微笑（小弧线嘴、圆眼）  → calm  强度 2
大笑（大弧嘴、弯眼）    → happy 强度 3
```

## D-48 · 强度存成字段，不让模型每次推

**背景**

同样是「开心」，一张是微微一笑，一张是笑到打滚。光看 brief
模型分不出来，只能随机挑 —— 结果就是心情 90 分的时候发了个"呵呵"。

**决定**

表情加 `intensity`（1~5），导入时视觉模型顺手估，存进 index。

**为什么不让模型每次从 detail 里推**

「这张图有多强烈」是**图的固有属性**，不管什么时候看都一样。
一次判断长期复用，结果稳定。

让模型每次重推的话：同样的图，这次判 3、下次判 4，
挑表情的结果就飘了。而且 detail 有 200 字，几十张塞进 prompt
会爆 token。

**挑的时候怎么用**

先对维度，再对强度：

```
心情 ≥70  → 挑强度 4~5，情绪放得出来
心情 40~70 → 挑 2~3，别用力过猛
心情 <40   → 挑 1~2，或者不发
```

心情差的时候发狂喜的表情，看着像装的。

但**以这句话本身为准**：明显在开玩笑时，哪怕心情低也可以发
强度高的自嘲。

## D-49 · 心情读最新落盘的那份，不用本轮快照

**背景**

引擎每轮开始时会 `load_context()` 拿一份上下文，里面有 mood。
但那份是**这一轮开始时**的快照。

而心情判断（`_judge_mood_async`）是**上一轮发送成功之后**才跑的，
异步写盘。所以这一轮开始时读到的 mood，比实际状态旧一轮。

**决定**

挑表情时单独调 `_current_mood()` 读最新的 `mood.json`。

**为什么值得多读一次文件**

心情是**连续变化**的：上一轮她刚被哄开心了，这一轮就该挑开心的
表情。用快照的话永远慢一拍 —— 用户会觉得"我说了开心的事，你怎么
还是那副死样子"。

读一个几百字节的 JSON 成本可以忽略，而这个差异用户能感觉到。

**读不到怎么办**

返回空字典，`_mood_line()` 输出空串，挑表情退化成"只看对话"。
不影响主流程 —— 心情只是让挑选更准，不是必需品。

## D-50 · 拖放只能走 Windows 原生 WM_DROPFILES

**背景**

用户反馈「拖拽无效」三次。前两条路都修错了地方：

| | 做法 | 为什么不行 |
|---|---|---|
| ① | HTML5 `dataTransfer.files` | QtWebEngine 里没有 `path` 属性（那是 Electron 的扩展） |
| ② | QWidget eventFilter + OLE | 管理员权限下被 UIPI 拦住 |
| ③ | **Windows 原生 `WM_DROPFILES`** | 通了 |

第 ② 条甚至写了 `ChangeWindowMessageFilterEx` 放行三条消息
（`WM_DROPFILES` / `WM_COPYDATA` / `WM_COPYGLOBALDATA`，API 全返回
True），事件还是没到。

**真正的冲突**

一个窗口只要注册了 OLE drop target（`RegisterDragDrop`），系统就
**只走 OLE，再也不发 `WM_DROPFILES`**。Qt 的 `setAcceptDrops(True)`
会注册 OLE，QWebEngineView 为了支持网页内拖放肯定也注册了。

而 OLE 在管理员权限下被 UIPI 卡死 —— 本程序要 UIA，必须是管理员；
资源管理器是普通权限。跨完整性的 COM 调用被拒，拖动源就显示禁止图标。

**两条路互相打架，只能选一条。**

**决定**

选 `WM_DROPFILES`：先 `RevokeDragDrop` 撤掉 OLE 注册，让系统回到
老式路径，再 `DragAcceptFiles(hwnd, TRUE)`。

配合 `QAbstractNativeEventFilter` 全局拦消息 —— 比装 eventFilter 到
某个子控件可靠，不管事件落在哪一层都会经过。

**代价**

网页内部的拖放会失效（拖文字、拖图片进页面）。我们的界面不需要那个，
要的只是"从资源管理器拖文件进来"。

**为什么不用低权限辅助进程**

理论上可以让一个中等权限的子进程接收拖放再转给主进程。但那要写
IPC、管进程生命周期、处理两边状态同步 —— 为一个"添加表情"的入口
做这些不值得。

**日志**

界面在管理员权限下跑，看不到控制台。拖放相关的事写到
`<程序目录>/data/_drop.log`：install 结果、收到消息、解析出几个文件、
有没有交给页面。下次再坏能一眼看出卡在哪。

## D-51 · 版本号只有一个真源

**背景**

散在三处：

```
bigfish/__init__.py        0.1.0
bigfish/updater.py         0.2.1
packaging/make_installer.py 0.1.0
```

发版时改一处忘两处 —— 装出来的包版本号和程序自称的不一样。
更新检查也会因此判断错（它拿自己的版本去比 release 的版本）。

**决定**

只在 `bigfish/__init__.py` 定义 `__version__`，另两处 import。

`updater.py` 取不到就退回 `"0.0.0"` —— 那会让更新检查认为"有新版"，
但比显示一个假的版本号安全。

`make_installer.py` 用 `_pkg_version()` 动态取，不再硬编码。
