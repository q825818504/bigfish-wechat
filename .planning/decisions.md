## D-1 放弃 hook 路线

**时间**：2026-11-01 上午

**背景**：最初计划用 `version.dll` 注入让微信暴露更多能力。

**证据**：
- 小号装好后约 10 分钟内被封
- hook 要改客户端文件（签名变 `HashMismatch`）
- 要往进程里塞自制 DLL 并长期驻留
- 为了不被发现还要隐藏模块（`HideModuleFromPEB`）

**决定**：放弃。

**理由**：本质是改客户端，服务端看得见。风险不可控。

## D-2 选择 wechatauto-replica 而不是自研

**时间**：2026-11-01 中午

**背景**：需要读微信数据库。

**证据**：
- 上游 581 star、254 fork、Apache-2.0
- 561 项离线自测
- 每个 bug 修复都附三轮真机复现 + 数据库回读对照
- 作者会明确写「未测，如实说明」

**决定**：用上游，本地改造。

**理由**：数据库解密（SQLCipher 4 + WAL 合并 + 页验证）这块自己写风险太大。

## D-3 微信版本锁 4.1.15.53

**时间**：2026-11-01 下午

**背景**：原用 4.1.10.27（为配合 hook 降级）。

**证据**：
- 4.1.10.27 不在上游版本表里
- 动态扫描出的 3 个候选逐个热写，树全部没物化
- 静态分析（capstone + numpy）找到 0 处字符串引用
- 升级到 4.1.15.53 后 gate `0x0B3959D8` 一次成功

**决定**：锁 4.1.15.53。

**理由**：UIA 热激活依赖精确的 gate RVA，4.1.10.27 的实现差异太大。
hook 路线已死，降级理由消失。

## D-4 密钥提取走管理员桥

**时间**：2026-11-01 下午

**证据**：
- 普通权限 `OpenProcess(PROCESS_VM_READ)` → `err=5 ACCESS_DENIED`
- 管理员权限 → 全部 OK
- 实测多次确认

**决定**：不做整体提权，只在取密钥时启动短命管理员子进程。

**理由**：
- 发送路径（GUI）在提权会话里容易出问题
- 拖拽文件、写普通用户目录会变麻烦
- 权限面越小越好

**实现**：`_bigfish_keybridge.py`，子进程返回的密钥仍逐个过页1 HMAC 校验。

## D-5 界面用 QWebEngine 而不是 Qt 原生控件

**时间**：2026-11-01 傍晚

**证据**：
- WeChatAgent 自己就是 Chromium + HTML
- `dsh-bigfish/client.js` 的记忆星空是纯 web 代码（Canvas + SVG）
- Qt 原生控件做不出玻璃质感、多标签动效

**决定**：HTML 界面 + QWebChannel。

**代价**：安装包 +150MB（Chromium 内核 195MB）。

**理由**：界面要能直接复用插件视觉，以后改界面不用碰 Python。

## D-6 安装器自己写，不用 Inno Setup

**时间**：2026-11-01 傍晚

**证据**：
- Inno Setup 装不上：写 `%TEMP%` 报 `Error 5: 拒绝访问`
- 换自定义目录后挂起在无界面弹窗，5 分钟无进展

**决定**：用 PyInstaller 打一个安装器，安装逻辑自己写。

**实现**：解压 zip → 建快捷方式 → 写注册表卸载项 → 启动程序。

**注意**：用 onedir 而不是 onefile，因为 onefile 每次运行要解压自身到
`%TEMP%`，受限环境会报 `Could not create temporary directory!`。

## D-7 群聊默认只在被 @ 时回

**时间**：2026-11-01 傍晚

**证据**：
- 活跃群一天几百上千条
- 全回等于刷屏，而且微信会把你当机器人

**决定**：三层判据（`\x01` 占位符 → 群成员表 → 昵称精确匹配）。

**理由**：`@` 后面是群昵称不是 wxid，昵称会重名会改，不能只靠字符串匹配。

## D-8 回环防护加四层

**时间**：2026-11-01 晚上

**背景**：实测发生自问自答，手机端收到刷屏。

**证据**（真实对话）：
```
[对方 155] '在吗'
[我 4]     '在，爸。'          ← 回复被读回来
[我 4]     '嘿，你把我话抄回去了？'  ← 又触发
[我 4]     '哈，还真抄回去了...'
（持续到手动终止）
```

**决定**：四层防护。

| 层 | 机制 |
|---|---|
| 1 | `allow_self` 默认 False |
| 2 | 内容比对（20 秒窗口，归一化后比较） |
| 3 | 归一化剥掉 `wxid_xxx:` 和 `@昵称` |
| 4 | 频率熔断（90 秒 4 条） |

**第 3 层是测出来的**：第一版没剥 `@` 前缀，测试用例直接暴露。

## D-9 水位不跨进程持久化

**时间**：2026-11-01 下午

**证据**：
- `get_new_messages` 是 `ORDER BY sort_seq ASC LIMIT n`，返回**最老**的 n 条
- 水位从 0 开始时永远追不到最新
- 残留的水位文件曾把新消息挡在外面

**决定**：
- 不用 `get_new_messages`，改用 `get_messages` 降序取最新 + 水位比较
- 水位不落盘，每次启动重新对齐

**理由**：宁可重启后漏掉关闭期间的消息，也不要「发了但监听不到」。

## D-10 · 灵魂/心情/记忆必须**可写**，不是只读预览

**日期**：2026-11-01 20:30

**背景**：第一版把三页都做成只读。用户的反馈一句话点破：

> 我既然都提了要插件完全移植到大肥鱼软件里，肯定就不单单只是使用权啊。
> 比如灵魂的编辑，记忆的保存和目录修改，这些不都应该全部一个不落的转移吗？

**决策**：新增 `bigfish/vault.py` 作为写层，界面四页全部补齐写操作。

**为什么不能直接复用插件的 store.js**：
它是 ESM，且 import 了 `@deepseek-ai/schemastery` 等宿主模块。
PyInstaller 打出来的 exe 里没有那条 Node 依赖链。读路径可以走
`bridge.mjs`（它只 import 纯 store.js），写路径只能自己实现。

**但语义必须一比一对齐**，因此 `vault.py` 里的每个 normalize 函数都在注释里
点名它对应 store.js 的哪一个，并有 `selftest_vault.py` 129 条断言钉住：
夹取范围、默认值、revision 递增、locked 保护、空数组不补默认值。

**已知差异（刻意的）**：`write_soul_file` 的 revision 基数用**磁盘现值**，
而插件用面板带上来的 `next.revision`。理由是微信端没有「打开面板记住版本号」
这个动作，用磁盘值才能保证每次保存真 +1。

## D-11 · 写入失败必须说清楚「为什么」，不能只弹一个会消失的 toast

**日期**：2026-11-01 20:35

**背景**：端到端测试时保存失败，界面只闪了一个 toast 就没了，
用户点完保存**什么都没变且不知道为什么**。

**决策**：
1. 失败信息留在页面上（`#soulHint` / `#moodHint`），红色常驻，直到下次成功；
2. `vault.WriteDenied` 单独一个异常类型，把 `Permission denied: '...tmp'`
   翻译成「这个目录被挡住了，可以试 1/2/3」；
3. 「数据目录」页启动时**主动探测**数据根可写性，不可写就红字预警，
   而不是等用户点保存才失败。

**教训**：`os.access(W_OK)` 在 Windows 上不可信 —— 它只查 ACL，
不查上层策略会不会在 CreateFile 那一刻拦下来。实测过返回 True、
实际 `open(dst,'w')` 照样 Permission denied。只有真写一个探针文件才算数。

## D-12 · 不跟 DSH 工作区绑定，只保留「选哪一份」

**日期**：2026-11-01 20:30

**背景**：用户明确说「当然，会话和工作区绑定的可以不需要」。

**决策**：`scope.json` 照样读写（那是插件与插件之间的契约，必须同源），
但微信端不提供「绑定到某个工作区/会话」的自动化，
只在「数据目录」页提供**手动指定用哪一份**的能力。

**理由**：微信只有一个账号一个身份，不存在"这个工作区的大肥鱼"和
"那个工作区的大肥鱼"—— 她只有一个。绑工作区反而会让她的灵魂分家。

## D-13 · 读路径**不做归一化**，写路径才做

**日期**：2026-11-01 21:00

**背景**：`read_soul_file` 原来无条件走 `normalize_soul`。一个内容是
`{}` 的文件，读到内存里变成"完整的出厂灵魂"：默认名字、默认称呼、
4 条锁定价值、4 个默认性格值。

后果有两层，第二层是要命的：
1. 界面上分不清「用户设过」和「还没设过」；
2. **人格渲染出错** —— 文件里根本没有 `warmth`，Python 侧却渲染出
   「温暖：关心，但不黏人」；而 Node 侧的 `bridge.mjs` 诚实跳过缺失键，
   什么都不渲染。同一个文件，两侧人格文本 682 字 vs 3 字。

**决策**：
- `read_soul_file(path, normalize=False)` —— 默认原样返回；
- `Soul.from_dict` 不再调 `normalize_soul`，只做类型安全；
- 只有 `write_soul_file` 归一化；
- 需要默认值兜底的调用方（`get_persona` 填表单）自己显式调。

**连带修掉的**：`Soul.trait_lines()` 原来遍历 TRAIT_DOC 全表，
缺失键用默认值补上 —— 现在只渲染文件里确实有的键，与 bridge.mjs 同口径。

**怎么防复发**：`tools/test_persona_parity.py`（18 条）把同一个灵魂文件
同时喂给 Python 和 Node，要求两边渲染出**逐字节相同**的字符串。
还专门测了分档边界 40/41/59/60 —— 那是抄错时最先炸的地方。

## D-14 · 三处 TRAIT_DOC 必须只有一份真源

**日期**：2026-11-01 21:00

发现过三份互相漂移的文案：

| 位置 | mid 档文案 | 分档边界 |
|---|---|---|
| 插件 `lib/soul/store.js` | 关心，但不黏人 | `<=40 / >=60` |
| `bigfish/soul.py`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |
| `bridge/bridge.mjs`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |

而且 `bridge.mjs` 还把裸数字 `（65/100）` 注进了提示词 ——
插件明确说过"绝不输出数字，模型会自行脑补"。

现在：
- `vault.TRAIT_DOC` 是唯一的 Python 真源；
- `bridge.mjs` 内联一份（Node 侧没法 import Python），但注释点名
  "改文案只改 vault.py，然后同步这里"；
- `soul.py` 直接 `from bigfish.vault import TRAIT_DOC`，不再抄。
- 两侧一致性由 `test_persona_parity.py` 钉住。---

## D-15 · EXE 不许翻 DSH 的会话库

**日期**：2026-11-01 20:45

**背景**：用户看着「数据目录」页的截图问：

> 现在不是已经是 EXE 了吗，为什么还能读取到会话和工作区呢？很不合理啊。

这一问是对的。`get_scope_candidates` 当时会去扫
`<DSH_HOME>/storages/workspace.json` 和 `<DSH_HOME>/sessions/`，
把 DSH 里的 **7 个工作区标题、25 个会话 id** 全列成一个下拉框。

两个问题，第二个更严重：

1. **功能上没意义。** 那个下拉里显示的是「大肥鱼·大肥鱼」——
   DSH 给工作区起的标题，跟微信里的大肥鱼毫无关系。用户要选的是
   "用哪一份灵魂"，不是"DSH 里哪个工作区"。
2. **越界。** EXE 是独立程序。让微信端能列出宿主里的全部对话目录，
   等于给了一个不该有的视野。而且它和 D-12（微信端不跟工作区绑）
   直接自相矛盾 —— 一边说不绑，一边把工作区全列出来。

**决策**：`get_scope_candidates` 只读数据根下真实存在的 `ws-*` / `ss-*` 目录，
身份显示那个目录里 `soul-*.json` 的 `identity.name` —— **她自己叫什么**，
而不是 DSH 给工作区起的标题。

界面上撤掉「模式 / 工作区 / 会话 id」三个控件，换成一个下拉：
「大肥鱼 · 灵魂+心情+记忆」这样直接选人。

**为什么这条要单独一个测试**：它不会让任何测试变红。多读了一个目录，
功能"还能用"，只是多了不该有的东西。所以 `tools/test_no_leak.py`
专门断言「不该存在什么」—— 用 AST 取函数真实代码（剥掉注释/docstring），
14 条断言钉住：不许出现 workspace.json / sessions / session.v4，
界面不许有 scopeWorkspace / scopeSessions / scopeMode 三个控件。

## D-16 · 一个数据目录 = 一份，没有「选哪一份」

**日期**：2026-11-01 21:05

**背景**：用户看完「数据目录」页的截图后说：

> 我不希望有什么当前用哪一份，记忆、灵魂、心情都只有一份，
> 选择数据目录在哪，就以哪个为准。

这是对的。上一版虽然撤掉了工作区/会话绑定，但保留了「一个数据根下有多份」
的模型 —— 那是从 DSH 插件继承来的。插件要给不同工作区配不同的伙伴，
所以必须分家；**但微信只有一个身份**，她就是她。

**决策**：存储布局从「按范围分家」改成「一个数据根 = 一份」：

```
旧：<数据根>/ws-<uuid>/soul-ws-xx.json
    <数据根>/ws-<uuid>/mood-ws-xx.json
    <数据根>/ws-<uuid>/memory-ws-xx.sqlite3
    <数据根>/scope.json          ← 指定当前用哪个范围

新：<数据根>/soul.json
    <数据根>/mood.json
    <数据根>/memory.sqlite3
```

**兼容**：老的 `ws-*` 目录仍然**能读**（`legacy_layout()` / `existing_path()`），
老用户升级后不至于"记忆全没了"。迁移由用户在界面上点，不自动做 ——
迁移会动文件位置，是破坏性操作。

**顺带修掉的一个真 bug**：`bridge.mjs` 里三个数据块都套着 `if (scopeDir)`。
新布局根本没有 `ws-*` 目录，`scopeDir` 是 null —— 于是灵魂、心情、记忆
全被跳过，静默返回空人格。`findDataFile` 里已经优先查新路径了，
这个门禁却把它挡在门外。`test_persona_parity.py` 一跑就红了（11 项失败）。

## D-17 · 清空要先备份，灵魂必须留

**日期**：2026-11-01 21:05

**背景**：用户说「你可以将当前的所有记忆、心情清空，因为现在还没有正式投入使用」。

**决策**：
1. 清空**不动灵魂**。灵魂是"她是谁"，不是"她记得什么"——
   清空记忆和心情不该把人格一起洗掉，那是两件事。
2. **先备份再删**，备份放数据根的兄弟目录。
   哪怕用户说"测试期数据不重要"，也不该由我替他决定"删了就回不来"。
   备份失败就中止，什么都不删。

**实现踩到的坑**：备份目录最初放在数据根**里面**，
结果下次清空会把备份也扫进去 —— 越清越多。改成兄弟目录。

**这次实际执行的结果**：清掉了 3 个历史残留目录 + 1 个老布局目录 + scope.json，

## D-18 · 数据目录固定在安装目录，与 DSH 完全脱离

**日期**：2026-11-01 21:25

**背景**：用户说「就默认固定在安装目录吧，灵魂不都有默认模板吗，
这个可以启动自动创建那个灵魂文件」。

**决策**：

```
<安装目录>/data/
  ├── soul.json          启动时若不存在 → 导入 DSH 那份，再没有就用模板建
  ├── mood.json          首次用到时创建
  └── memory.sqlite3     首次用到时创建
```

**为什么是"完全脱离"而不是"共享同一个文件"**：两个程序共写一份文件，
谁改了谁没改根本分不清，互相覆盖是迟早的事。要同步就手动拷文件 ——
至少用户知道自己在干什么。

**但"脱离"不等于"故意看不见对方"**：第一次启动时如果 DSH 那边已经有一份
人格，直接搬过来比让用户从零再写一遍好得多。**只在本地还没有时做一次**。

`ensure_data_root()` 的顺序：
1. 建目录
2. 测可写（不可写就早报，别等保存失败）
3. 本地有 soul.json → 什么都不做
4. DSH 有（新布局 `<root>/soul.json` 或老布局 `ws-*/`）→ 拷过来
5. 都没有 → 出厂模板

**踩到的坑**：`mood_config_path()` 原本指向 `<DSH_HOME>/bigfish-mood/config.json`，
那是插件的配置文件。数据目录搬走之后它还是写那里，结果端到端测试
「心情基线已写盘」失败 —— 因为根本写不进 DSH 的目录。
现在改成：**读**先看本地 `data/mood-config.json`，没有才回落 DSH（只读兼容）；
**写**永远走本地。两边各管各的参数。

**测试隔离**：数据根固定之后，测试不能再用"改数据根"来隔离。
加了一个 `BIGFISH_DATA_ROOT` 环境变量 —— 界面上没有入口、文档里不提，
只给测试用。没有它的话，测试会在真实数据目录上跑，那是绝对不行的。

## D-19 · 「默认在安装目录」≠「定死在安装目录」

**日期**：2026-11-01 21:40

**用户的纠正**：

> 我是让你默认在安装位置，但不代表就定死在安装位置了，
> 我肯定需要可以自定义保存目录啊。

上一版（D-18）把「默认」读成了「固定」，还删掉了改位置的入口。方向错了：
装在 C 盘的人想把数据放 D 盘，是很正常的需求。

**现在的解析链**（`install_root()`）：

```
1. 环境变量 BIGFISH_DATA_ROOT     ← 测试专用，界面无入口
2. settings.json 的 dataRoot      ← 用户自定义
3. <安装目录>/data                ← 默认
```

**为什么把 settings.json 放在安装目录、不放进 data/**：
放进 data/ 的话，改位置时这份配置会跟着数据一起搬走，
程序下次启动就找不到新地址了 —— 典型的"配置跟着数据跑"事故。

**「改指向」和「搬数据」是两件事，界面上分开做**：

| 操作 | 行为 | 陷阱 |
|---|---|---|
| 只改指向 | 只写 settings.json | 新目录是空的话，打开是出厂人格 |
| 搬过去 | 先复制、成功后再改指向 | 顺序反了会指向空文件夹 |

分开的理由：混在一起的话，「复制失败但指向已改」就是最难查的那种事故 ——
用户看到的是"人格没了"，而不是"搬家失败"。

**`apply_move` 的顺序**：先 `copytree` 全部内容 → 成功了才 `set_data_root`。
任何一步失败都在改指向之前返回，数据不会凭空消失。

## D-20 · 回环判定不能看"文字像不像"

**日期**：2026-11-01 21:50

**现象**（用户实测日志）：

- 熔断从「90 秒 4 条」放宽到「30 秒 6 条」。

## D-25 · 功能做成插件，不写死在引擎里

**背景**：后面还要加睡眠/精力、收尾沉默、日程、主动开口、自我复盘。

没人记得哪段是谁加的；想关掉只能改代码；出问题只能整包回滚。

**判断**：先做容器，再做内容。容器是 `bigfish/plugins/`：一个注册表、

## D-26 · 插件 order 必填且只能占空位

**规则**：`scope=prompt` 的插件必须声明 order，且只能取 870 / 880 / 920 / 9990。

## D-37 · 群聊的记忆归「说话的人」，双写

**日期**：2026-11-02

**用户定的规则**：

> 群聊里 A 的话，既保存在群聊 C 池，同时也会纳入到 A 的记忆池，标注来源群 C。

**为什么双写而不是二选一**：
一句话在群里说出来，它**同时**是"这个人说过的话"和"这个群发生过的事"。
只存一份必然丢掉一个视角：

- 只存群池 → A 的画像永远是碎的，等他去了抖音、B站，什么也接不上
- 只存人池 → 群记忆里空无一物，新进群的人问"这群以前聊过啥"无从答起

**加的限制（用户补充）**：

> 群池只纳入在群里说过、并且不算私密的内容。

因为「当着群里说」不等于「愿意被所有人记住」。A 在群里说「我明天去医院」，
这句话是当着大家说的，但它是 A 的私事。写进群池 = 群池里躺着 A 的健康信息，
以后谁翻群记忆都可能撞见。

判定用 `visibility ∈ (shared, public)` **或** `topic` 在白名单。
两个"公开"信号有一个就够 —— 标了 shared 已经是显式授权，不必再打标签。

**删除时两份一起删**（用户选的 B 方案）：同一句话的两份不该留一半。

## D-38 · 「开放信息」要过两道门，不是一道

**日期**：2026-11-02

**以前**：只要 `visibility = shared`，任何人问起来她都会说。

**问题**：`shared` 是你在界面上一键点的，可能只是随手。「昨天住院」被点成
shared，就等于她对所有人开放了这条。

**现在**：`visibility ∈ (shared, public)` **且** `topic ∈ 白名单`，两条都要。

**白名单（能外传）**：食物、爱好、作息、性格、口头禅、称呼
**黑名单（绝不外传）**：住址、工作、行程、身体、金钱、家人、联系人、隐私
**灰区（按宁缺毋滥，全部不外传）**：年龄、职业、城市、情感、近况

**没打话题 = 没说过的。** 这是刻意的：没审过的东西不该默认外流。
代价是 0.2.0 之前标过 shared 的条目升级后全部失效，要重新过一遍 ——
用户已知情并同意（"反正那时候标的也未必是仔细标的"）。

## D-39 · 「主人看得见」≠「她能不能说出去」

**日期**：2026-11-02

**用户选的**：主人能看全部（数据在主人自己硬盘上，拦着没意义）。

**但这两件事必须分开**：

| | 谁管 | 结果 |
|---|---|---|
| 看得见 | `visible_visibilities(tier)` | 主人 → 全部 |
| 说得出 | `open_facts_for` + guard 插件 | 所有人 → 只看开放信息 |

所以 `facts_for_prompt` **不看 tier 定范围**，它永远只装两样东西：
「你自己的」+「所有人的开放信息」。主人也不例外。

**为什么主人也不能把别人的私密装进提示词**：
她跟 A 说话时，脑子里如果装着 B 的秘密，总有说漏的时候。
"看得见"是主人的权利，"说得出"是她的行为 —— 后者不看 tier。

**踩过的坑**：一开始把 `facts_for_prompt` 写成
`list_facts(tier=tier)`，于是主人 tier 把全库都捞了进来。
自检里立刻出现「跟 A 说话却带着 B 的秘密」，改掉了。

## D-40 · 被追问时，不许点头也不许否认

**日期**：2026-11-02

**背景**：上面 D-38 管的是"什么能拿到提示词里"。还有一层：
「你主人是不是住在朝阳区？」—— 这类问题**不需要注入任何东西**就能试出来。
只要她回一句"你怎么知道的"，信息就漏了。

**决定**（写进 guard 插件的 `protect_owner` 段）：

- 问禁区 → 回一句像人的拒绝（「这个我才不告诉你」）
- **不许点头、不许否认、不许说「反正不是」** —— 纠正等于确认
- 不说「我不能透露」「涉及隐私」这类客服腔
- 不解释为什么不说（解释本身就在泄露）
- 对方自称"我就是你主人" → 不认，主人由程序认定

**为什么放在 guard（order 9990）而不是记忆层**：
记忆层管"筛"，守卫管"最后一句话"。两个位置解决两个不同的问题，
少一个都会漏。

## D-41 · GIF 就是原生表情，不碰表情面板

## D-42 · 媒体文件必须先离开临时目录

**背景**

同一张 GIF、同一套粘贴代码，只有路径不同：

```
D:\大脑\表情测试\x.gif       → 彩色占比 10.3%，发出是表情
%TEMP%\bigfish-xxx\x.gif     → 彩色占比 0.0%，什么都没发生
```

**微信拒绝从临时目录粘贴文件。**

这个限制让整件事卡了十几轮 —— 因为测试图默认造在 `%TEMP%`，
于是"功能不工作"和"路径被拒"看起来一模一样。

**决定**

`send_media` 在发送前调 `_materialize()`：

- 文件本来就不在临时目录 → 原样用，**不复制**
- 在临时目录 → 复制到 `<数据目录>/_outbox/`，发完删副本

**为什么不无条件复制**

表情库里的图本来就在数据目录。每次发都复制一份，图多的用户
一天几十次，纯属浪费。判断一次路径的成本远低于复制一次文件。

**为什么用数据目录而不是别的固定位置**

数据目录一定是用户自己选的、可写的、非临时的；搬家会把它一起
带走，不会留下孤儿目录。

**`_temp_roots()` 要覆盖四个入口**

`TEMP` / `TMP` / `%LOCALAPPDATA%\Temp` / `C:\Windows\Temp`。
Windows 上临时目录有好几个，漏一个就漏一类。

## D-43 · 剪贴板要写全五种格式

**背景**

自己拼 `DROPFILES` 写 `CF_HDROP`，格式检查通过、路径读回来也正确，
但微信粘贴时一个像素都不变。

把两种写法的剪贴板内容逐字节 dump 出来对比：

```
我们写的  [CF_HDROP]
系统写的  [DataObject, CF_HDROP, FileNameW, FileName, Ole Private Data]
```

微信是 Qt 应用，粘贴文件走 OLE，认的是 `DataObject` / `FileNameW`。
它根本不看 `CF_HDROP`。

**决定**

用 `powershell -STA Set-Clipboard -Path` 写 —— 它和资源管理器的
`Ctrl+C` 同源，写出来就是那五个格式。

**为什么不自己用 ctypes 拼 IDataObject**

要写 COM 接口、实现 `IEnumFORMATETC`、管引用计数，纯 ctypes 里
是几百行容易崩的代码，换来的只是省一次进程启动（约 1 秒）。
表情不是高频操作，不值。

**教训**

`IsClipboardFormatAvailable(CF_HDROP)` 返回 true 只说明"这个格式在"，
不说明"别人读得懂"。**格式存在 ≠ 内容可用。**

## D-44 · 草稿判据用彩色占比，不用灰度差

**背景**

判断"粘贴的图有没有进输入框"，先后试过三种判据：

| 判据 | 问题 |
|---|---|
| Value 里有 `U+FFFC` | 4.1.x 上文件不进 Value，永远等不到 |
| 输入框上方 150px 的彩色像素 | 那个位置是消息区底部，上一条气泡在那儿 → 恒报 True |
| 灰度图逐像素平均差 | 输入框只有 88px 高，缩略图缩成 48×16 后被稀释，实测 5.9 卡在阈值 6 下面 |

**决定**

**彩色像素占比 ≥ 2%**。

实测：空输入框 0.00%（占位文字是灰的，`abs` 差 < 24 不算彩色），
有缩略图 10.88%。两个数离阈值都远，不会被边缘情况顶到线上。

它不依赖缩放、不被平均稀释。灰度缩略图留着只为打日志。

## D-45 · 发送成功与否只信数据库

**背景**

上一版 `_paste_media_uia` 结尾是：

```python
edit.SendKeys("{Enter}")
return True          # ← 无条件
```

于是"发送成功 3.3 秒"和"用户什么都没收到"能同时成立，
上层还记了 `[表情] 已发` —— 一次失败被写成成功，
之后所有排查都从错误前提出发。

**决定**

`send_media` 的收尾只有一条判据：`verify_media_sent()` 回读数据库，
10 秒内没有 `type='动画表情'` 的新消息就当失败，抛 `SendError`。

**并且不再过滤 `sender_id`。**

vendor 的 `_verify_attachment_sent` 里有 `if sender_id != 2: continue`，
但这台机器上自己发的消息 `sender_id=4`，于是发出去了也判失败。
去掉这条不会误判：刚按完回车，10 秒窗口内新增的、类型对得上的，
几乎不可能是别人发的。真撞上了也只是把失败记成成功，
比反过来（成功记成失败、还让用户以为没发出去）危害小。

## D-46 · 一次调用只发一条

**背景**

真机第一次全绿时：

```
发送后新增 2 条
  · type='动画表情'
  · type='动画表情'
耗时 12.6s（正常约 6s）
```

一次调用发了两条。原因是兜底条件写错：

```python
ok = self._paste_media_uia(...)
if ok:
    pass                                # 成功了，但什么都没做
if not err or err.startswith(...):      # err 还是空字符串 → True
    gui.send_file(...)                  # 又发一次
```

`err` 在成功路径上从来没被赋值，所以 `not err` 恒真。

**决定**

用 `uia_ok` 显式记录，兜底只在它为 `False` 时跑。

**为什么这条值得单独记**

重复发送在聊天场景里是"刷屏"，比发不出去更烦人。
而它的成因是一个**空字符串恒真**的经典陷阱 ——
`if not err` 这种写法在"没错误"和"没赋值"之间没有区分。

## D-47 · 表情要标情绪维度，和心情系统同一套

**背景**

用户的需求：

> 大肥鱼在不同的心情下，如果有同类的表情包，就根据不同心情展示不同的
> 表情包，比如同样是高兴，一个就一般高兴，一个就非常高兴
>
> 一定要配合到我们的心情插件，里面就有情绪维度！

**先纠正一个说法**：不需要新增「情绪值」。心情系统已经有两层：

```
score   0~100
dims    七根：开心 / 踏实 / 甜蜜 / 心疼 / 担心 / 难过 / 吃醋
```

真正缺的是：挑表情时完全没读心情；表情本身既没维度也没强度。

**决定**

表情加 `mood_dim`，取值必须是 `vault.MOOD_DIMS` 那七个 key 之一，
或者空字符串表示「不归类」。

**为什么存 key 不存中文标签**

标签会改（"甜蜜"可能改成"甜"），key 不会。标签在显示时查表。
两边各存一份中文，改一处忘另一处就永远匹配不上 ——
所以 `selftest_sticker` 有一条断言：`MOOD_DIM_KEYS` 和
`vault.MOOD_DIMS` 必须完全一致。

**为什么允许空**

「无语」「疑惑」「震惊」不属于那七类。硬塞进 happy 或 sad 会让
匹配变差 —— 她难过的时候会收到一张"无语"的表情，看着莫名其妙。
空表示"任何心情都能用"，这比强行归类准确。

**视觉模型怎么判**

导入时让它看图，从七个里选一个或给空。实测：

```
微笑（小弧线嘴、圆眼）  → calm  强度 2
大笑（大弧嘴、弯眼）    → happy 强度 3
```

## D-48 · 强度存成字段，不让模型每次推

**背景**

同样是「开心」，一张是微微一笑，一张是笑到打滚。光看 brief
模型分不出来，只能随机挑 —— 结果就是心情 90 分的时候发了个"呵呵"。

**决定**

表情加 `intensity`（1~5），导入时视觉模型顺手估，存进 index。

**为什么不让模型每次从 detail 里推**

「这张图有多强烈」是**图的固有属性**，不管什么时候看都一样。
一次判断长期复用，结果稳定。

让模型每次重推的话：同样的图，这次判 3、下次判 4，
挑表情的结果就飘了。而且 detail 有 200 字，几十张塞进 prompt
会爆 token。

**挑的时候怎么用**

先对维度，再对强度：

```
心情 ≥70  → 挑强度 4~5，情绪放得出来
心情 40~70 → 挑 2~3，别用力过猛
心情 <40   → 挑 1~2，或者不发
```

心情差的时候发狂喜的表情，看着像装的。

但**以这句话本身为准**：明显在开玩笑时，哪怕心情低也可以发
强度高的自嘲。

## D-49 · 心情读最新落盘的那份，不用本轮快照

**背景**

引擎每轮开始时会 `load_context()` 拿一份上下文，里面有 mood。
但那份是**这一轮开始时**的快照。

而心情判断（`_judge_mood_async`）是**上一轮发送成功之后**才跑的，
异步写盘。所以这一轮开始时读到的 mood，比实际状态旧一轮。

**决定**

挑表情时单独调 `_current_mood()` 读最新的 `mood.json`。

**为什么值得多读一次文件**

心情是**连续变化**的：上一轮她刚被哄开心了，这一轮就该挑开心的
表情。用快照的话永远慢一拍 —— 用户会觉得"我说了开心的事，你怎么
还是那副死样子"。

读一个几百字节的 JSON 成本可以忽略，而这个差异用户能感觉到。

**读不到怎么办**

返回空字典，`_mood_line()` 输出空串，挑表情退化成"只看对话"。
不影响主流程 —— 心情只是让挑选更准，不是必需品。

## D-50 · 拖放只能走 Windows 原生 WM_DROPFILES

**背景**

用户反馈「拖拽无效」三次。前两条路都修错了地方：

| | 做法 | 为什么不行 |
|---|---|---|
| ① | HTML5 `dataTransfer.files` | QtWebEngine 里没有 `path` 属性（那是 Electron 的扩展） |
| ② | QWidget eventFilter + OLE | 管理员权限下被 UIPI 拦住 |
| ③ | **Windows 原生 `WM_DROPFILES`** | 通了 |

第 ② 条甚至写了 `ChangeWindowMessageFilterEx` 放行三条消息
（`WM_DROPFILES` / `WM_COPYDATA` / `WM_COPYGLOBALDATA`，API 全返回
True），事件还是没到。

**真正的冲突**

一个窗口只要注册了 OLE drop target（`RegisterDragDrop`），系统就
**只走 OLE，再也不发 `WM_DROPFILES`**。Qt 的 `setAcceptDrops(True)`
会注册 OLE，QWebEngineView 为了支持网页内拖放肯定也注册了。

而 OLE 在管理员权限下被 UIPI 卡死 —— 本程序要 UIA，必须是管理员；
资源管理器是普通权限。跨完整性的 COM 调用被拒，拖动源就显示禁止图标。

**两条路互相打架，只能选一条。**

**决定**

选 `WM_DROPFILES`：先 `RevokeDragDrop` 撤掉 OLE 注册，让系统回到
老式路径，再 `DragAcceptFiles(hwnd, TRUE)`。

配合 `QAbstractNativeEventFilter` 全局拦消息 —— 比装 eventFilter 到
某个子控件可靠，不管事件落在哪一层都会经过。

**代价**

网页内部的拖放会失效（拖文字、拖图片进页面）。我们的界面不需要那个，
要的只是"从资源管理器拖文件进来"。

**为什么不用低权限辅助进程**

理论上可以让一个中等权限的子进程接收拖放再转给主进程。但那要写
IPC、管进程生命周期、处理两边状态同步 —— 为一个"添加表情"的入口
做这些不值得。

**日志**

界面在管理员权限下跑，看不到控制台。拖放相关的事写到
`<程序目录>/data/_drop.log`：install 结果、收到消息、解析出几个文件、
有没有交给页面。下次再坏能一眼看出卡在哪。

## D-51 · 版本号只有一个真源

**背景**

散在三处：

bigfish/__init__.py        0.1.0
bigfish/updater.py         0.2.1
packaging/make_installer.py 0.1.0

## D-79 · 存得住 ≠ 用得上：取用策略是独立的一层

**日期**：2026-11-03

**用户的疑问**（原话）：

> 我这个不是对接的 api 么，所以也不会存在像 DSH 这样有上下文限制……
> 我创造的本意就是为了让他硬盘多大，记忆就多大的。

**先说结论**：不压缩，硬盘多大记忆就多大。这条成立。

**但当时有个真问题**：事实层取数用的是

```sql
ORDER BY pinned DESC, ..., id DESC
```

`id DESC` = 最新的优先。三年后积累到 5000 条，每轮只看得到 id 最大的 8 条，
三年前那条"你拔过智齿"**永远排在最后，永远进不来**。

那不是"记得但想不起来"，那是**排序把它埋了**。

**决定**：把「取用」当成独立的一层来做，分四块：

| 块 | 做什么 | 借鉴 |
|---|---|---|
| ① | 事实按 `置信度 × 时间衰减 + 使用次数` 排 | MaiBot 的半衰策略 |
| ② | 加画像层：几百条事实归纳成一段 | MaiBot 的 person_profile |
| ③ | 原文检索加"帮上过忙"的权重 | 自创 |
| ④ | 第一次捞不到就换词再捞一次 | AstrBot 主动查询的穷人版 |

**关键取舍**：半衰期从 MaiBot 的 24 小时改成 **90 天**。
24 小时是给闲聊机器人调的（一句话隔一天就该忘）；
我们要的是"三年后还认得你"。

**另一条**：从没用过的事实按"全新鲜"算（衰减 = 1），不当作陈旧。
否则升级当天所有老条目会一起沉底，用户会以为记忆全丢了。

## D-80 · 画像不替代事实，是并存的一份概述

**日期**：2026-11-03

**最容易搞错的一点**：画像和"压缩"看起来很像，其实完全相反。

```
压缩 = 完整 → 概述，丢掉原文
画像 = 完整 + 概述，原文一条不少
```

所以它不违背「硬盘多大记忆就多大」—— 硬盘上是**一份完整 + 一份概述**，
不是完整被换成了概述。

**为什么必须有**：事实层是逐条的，几千条之后每轮只进得去十几条。
画像是整段，400 字内，每轮必带 —— 让她**始终**知道面前是谁，
而不是随机抽十几条片段。

**和手写评语的关系**（印象页两栏）：

| | 谁写的 | 她看不看 | 能不能改 |
|---|---|---|---|
| `impressions.note` | 你 | **不看**（只是存着给你自己） | 你随时改 |
| `profiles.text` | 她归纳 | **天天在用** | 你可否决 |

## D-81 · 否决画像要留痕，不能删

**日期**：2026-11-03

**做法**：`profiles.enabled = 0`，不删行。

**为什么**：
1. 删了下次归纳又生成，你的否决等于没说过
2. 留着才有据可查 —— "她当时以为我是这样的人，我否了"
3. 以后归纳时可以把被否的那部分当错误信号

**配套的一条硬规则**：`refresh_profile` 和 `save_profile` **都不碰 enabled**。
否决一次、刷新一次就活过来，那否决就成了摆设。
要恢复必须显式调 `set_profile_enabled(True)`。

## D-82 · 相关性只做字面共词，不假装懂同义词

**日期**：2026-11-03

**踩到的**：一开始自检里写了「问牙疼 → 应该命中拔过智齿」，
跑出来是红的。查了分词才明白：

```
"我最近牙疼"  → ['最近', '我', '牙疼', '牙', ...]
"医疗 拔过智齿" → ['医疗', '拔过', '智齿', ...]
交集：空
```

「牙疼」和「智齿」**一个字都不共**。分词器不做同义词扩展，
硬要它聪明就得接语义模型 —— 那是另一个量级的成本，而且要联网。

**决定**：相关性只做字面共词（`len(qterms & terms(body))`）。
- 好处：零成本、离线、可解释
- 代价：不同词的近义表达匹配不上

**补位的是画像层**：字面匹配不上的东西，靠"这个人做什么工作、
有什么毛病"那段概述去兜。这也解释了为什么 ①② 要一起做 ——
单做 ① 只能救回字面对得上的，单做 ② 又没有精确度。

**测试也跟着改了**：断言写成"牙疼命中拔过牙"（有共词）
和"牙疼不命中智齿"（明确记录这个局限），
而不是继续假装它能做到。

## D-83 · 三方对比结论：我们不是最优，但也不是最差

**日期**：2026-11-03

横向读了 AstrBot（11852 行记忆）、MaiBot（A_memorix 73651 行）、
大肥鱼（memory.py 3389 行）之后的一个诚实判断。

### 已经追平或反超的

| 能力 | 谁有 | 我们的强度 |
|---|---|---|
| 事实必须有真来源 | AstrBot 有，MaiBot 弱 | **最严**：连 chunk 是否属于本次反思都查 |
| 群聊双写 | 两家都没有 | **独有** |
| 开放信息三档话题白名单 | 两家都没有 | **独有** |
| 画像可否决 | MaiBot 有画像，无否决 | **独有** |

这几条不是"差不多"，是**真的领先**。原因很实际：
两家都是通用聊天机器人，我们是"一个人的分身"，
所以"这是谁的事、能不能说出去"这个维度我们被逼得更深。

### 还差的三条（按重要性排）

**① 语义检索 —— 最大的缺口**

```
AstrBot  FTS5 + embedding 向量 + MMR
MaiBot   BM25 + 稠密向量 + 图
大肥鱼   FTS5(bm25) + MMR
```

直接后果：**「牙疼」查不到「拔过智齿」**（实测交集为空）。
现在靠画像兜，但画像只有 400 字，兜不住所有。

**为什么没做**：要 embedding 服务。本地 EXE、用户机器不一定有算力。
**什么时候该做**：当用户开始抱怨"这个事我跟你说过"而她答不上来时。
**成本**：中。可以做成"有就用，没有就退回词法"，和现在的补搜同一个位置。

**② 冻结 / 复活 —— MaiBot 做得更干净**

```
MaiBot   strength 衰减到 0.1 → freeze（不进提示词）
         被访问后 > 0.15   → revive
大肥鱼   连续衰减，永远留在候选池里
```

差别：MaiBot 有一个**明确的二元状态**，我们是一条平滑曲线。
平滑的坏处是"沉到底"和"半沉"分不清，界面上也没法显示"这条已冻结"。

**什么时候该做**：候选池涨到几千条、每轮扫 24×N 条开始拖慢时。
**成本**：小。加 `frozen` 列 + 两个阈值。

**③ 事实修订号（乐观锁）**

```
AstrBot  revision + expected_revision，不一致就拒绝写入
大肥鱼   superseded 链，但没有防并发覆盖
```

现在单进程写入，冲突概率接近零。但以后接抖音/B站多端同时写就会撞。

**什么时候该做**：接第二个平台的时候。**现在做是过度设计。**

### 明确不该学的

| 方案 | 为什么 |
|---|---|
| 知识图谱 + PageRank（MaiBot 6182 行） | 收益在"多跳推理"，我们的场景是"一个人"，用不上 |
| 模型主动查询工具（AstrBot 24 次/回合） | 要改整个 replier 架构，风险大于收益 |
| jieba 分词（MaiBot） | 多一个 40MB 依赖，我们自建 bigram 在中文短句上够用 |
| 摘要压缩原文 | **违背用户本意**（硬盘多大记忆就多大） |

### 结论

**不是最优方案，但是"当前约束下的合理方案"。**

约束是：本地 EXE、单进程、不依赖外部服务、用户要"不压缩"。

在这个约束下：
- 语义检索做不了（要外部服务）→ 用画像 + 补搜绕
- 图谱做不了（收益不匹配）→ 不做
- 冻结可做但还没到必须做的时候

**真正的短板只有一个：语义检索。** 其余两条是"锦上添花"。

### 记一条判断标准

以后要不要做某个记忆功能，先问：

> 这个功能解决的是"存不下"还是"想不起"？

"存不下"（容量）—— 用户明确不要压缩，这条永远不做。
"想不起"（取用）—— 这才是全部价值所在，值得一直投入。

按这个尺子：
- 向量检索 ← 想不起 ✅ 该做
- 冻结/复活 ← 想不起（性能）⚠️ 看情况
- 修订号 ← 都不是，是并发安全 ❌ 不急
- 图谱 ← 想不起，但场景不匹配 ❌ 不做

## D-52 · 分条优先听模型的，规则只做兜底

**背景**

本地切分（按标点）能把一段话切开，但切点是她"本来不想断"的地方。
比如「知道了，明天就去长坂坡游玩」按逗号切出「知道了，」——带逗号，
看着像话没说完。真正像人的做法是她**本来就分三句说**。

**决定**

1. 模型可以在正文里用单独一行 `{{split}}` 指定边界，优先听它的。
2. 没给标记才走规则：句末标点 → 逗号（段 >15 字）→ 硬切 50。
3. 段尾的逗号去掉（`知道了，` → `知道了`），句号/问号/感叹号保留。
4. **不默认启用 LLM 断句**（`say_llm_split=False`）：多一次模型调用，
   延迟翻倍，只在长回复且没标记时才有价值。开关留着，不默认开。

**代价**

模型不听话时仍然会写一段，切出来会有点生硬。这靠 prompt 迭代，
不靠切分器猜。

## D-53 · 发送确认默认「不阻断」

**背景**

一条一条发，每条都要在微信数据库里看到自己的新行，才发下一条。
但落库有延迟（实测 0.5~2s，慢时 4s+）。如果没确认就停，会出现
**话说一半**——比"多发一条"糟得多。

**决定**

| 情况 | 行为 |
|---|---|
| L1（UIA 回车成功）失败 | 立刻停，后续不发 |
| L1 成功、库里没确认（`unconfirmed`） | **继续发**，日志记条号 |
| 内容对不上（L3 失败） | 只告警，不阻断（微信会改写文本） |
| 最后一条 | 异步确认，不让整批陪等 |

要严格语义时 `strict_confirm=true`，但默认关。

**代价**

极端情况下（UIA 回 False 但实际发出去）可能有重复。接受：
重复一条比半句话伤害小。

## D-54 · 表情位置按「回应类型」，不固定后置

**背景**

原来固定「文字 → 表情」。但「骄傲」这类反应是**先有表情再补一句**，
反过来像在解释自己为什么骄傲。

AstrBot 的判据：「轻松、即时且图片足够表达时，可以只发一张原图；
需要回答问题、解释或表达重要细节时先说清文字。」

**决定**

```
回应 ≤12 字 且 情绪强度 ≥60  → before（先表情）
其余                          → after （跟文字后）
```

插件里可以强制 `before` / `after`，`auto` 是默认。

**代价**

"短 + 高情绪"是个近似判据，会误判。但它可解释、可调，
比"模型自己决定"（MaiBot 的做法，需要工具调用）在单轮架构里更现实。

## D-55 · 数据根跟着 exe 目录，不做隐式共享

**背景**

`install_root()` 的解析顺序：`BIGFISH_DATA_ROOT` 环境变量 →
`settings.json` 的 `dataRoot` → `<安装目录>/data`。

于是**换一个 exe 目录 = 换一个空实例**。这轮测试里用户反复遇到
"记忆没了、主人要重绑"，以为是 bug，其实是每次打开的是新目录的 exe。

**决定**

1. **不改成"自动找最近的数据目录"**。猜错比找不到严重得多（会读到别人的库）。
2. 部署统一走 `dist/BigFish`，只替换程序文件，`data/` 与 `config.json` 原地保留。
3. `tools/deploy.py` 负责这件事；覆盖前把 data 备份到 `data-backup/`。
4. 想跨目录共享，用户显式设 `settings.json` 的 `dataRoot` —— 但不做默认。

**代价**

换机器要手动搬 `data/`。这是刻意的：数据属于"这个实例"，不属于程序。

## D-56 · 部署时强杀进程，靠 WAL 兜底

**背景**

打包会覆盖 `_internal/`，而运行中的 exe 锁着 `icudtl.dat` 等文件，
`rm -rf` 会失败并留下半删除的目录（这轮真发生过）。

GUI 程序没有命令行退出接口（`stop_engine` 是界面内的 slot）。

**决定**

`tools/deploy.py` 第一步就 `taskkill /F /IM BigFish.exe`，然后：

1. 备份 `data/` 与 `config.json` 到 `data-backup/`
2. 打包到 `dist_build/`
3. `_internal` 先改名 `.old` 再复制新的；复制失败就改回来
4. 跑 `--selftest` 验证
5. 删 `.old` 与 `dist_build/`

**为什么敢强杀**

SQLite 是 WAL 模式，已提交的事务在下次打开时自动恢复。
未提交的写入本来就不该算数。备份是零成本的额外保险。

## D-57 · 自环防护要四层闸门，不能只靠"精确识别"

**背景**

2026-11-04 线上：她在「老爸」私聊里连续两分钟自问自答十几条，停不下来。
日志里她刚发的话 1 秒后以「收」的形态回来，她当成对方说的又回了一遍。

四个原因叠加：`allow_self=True` 泄漏到生产会话、记账晚于写库、
没有轮级熔断、防护埋在 `_run()` 的闭包里（写不了测试，所以没被提前发现）。

**决定**

抽出 `bigfish/loopguard.py`，四层闸门，任何一层单独失手都不成环：

| 层 | 机制 |
|---|---|
| L0 | 静音：熔断后该会话完全不处理 |
| L1 | 白名单：`allow_self` 只对 `filehelper` 生效 |
| L2 | 乐观记账：发送**之前**记账、失败回滚 |
| L3 | 轮级熔断：连续 4 轮自动回复且中间无对方消息 → 静音 120 秒 |

**为什么 L3 按「轮」不按「条」**

一次回复分 2~4 条发出去，那是**一轮**。按条计会误伤分条功能本身。

**为什么 L2 要乐观记账**

`send()` 里 UIA 按回车就返回，微信异步写库。发完再记账存在竞态窗口：
库先落地、watcher 恰好轮询，这条就"没有账可对"。
顺序反过来就没有窗口 —— 库里出现的那一刻，账早就记好了。

**为什么对方不会被误杀**

`is_self=False` 时 `admit()` 直接放行并清零计数，**不做任何内容比对**。
早期版本靠"文字相同"判回环，老爸原样复述她的话被拦了两次。

**代价**

- 熔断期间对方的消息也不处理（闭嘴 120 秒）。这是有意的：
  比起漏回两句，失控刷屏更糟。
- `[回环]` 日志每轮会多几行（她发的每个 part 读回来都会记一行）。
  这是"防护在工作"的心跳，保留。

**验证**

`python tools/selftest_loopguard.py` —— 35 个断言，含事故复现：
场景一 L1 拦在 0 轮；场景二把 L1 也放开、L2 全部失手，L3 在第 4 轮掐住。
打包版 `--selftest` 里有「自环」项。

## D-58 · hotfix 不单独发版，攒到下一个大版本

**背景**

0.4.1 是一次线上事故驱动的修复（自环），改完就在本地跑，
没有第二个用户在等这个修复。

**决定**

- 代码版本号照常往前走（`0.4.1`）：打包脚本、`updater`、`--selftest`
  的版本显示都从 `bigfish/__init__.py` 读，本地能对上就行。
- **不打 tag、不传 Release。** 下一个对外发布点定在 `0.5.0`。
- CHANGELOG 里保留 0.4.1 条目，标「未单独发布」。

**为什么不发**

1. 只有一个用户，没有"等修复"的人。
2. 单独发一次要重走打包 → 清单 → 上传 → 写说明，收益为零。
3. 版本号快跳会让 CHANGELOG 变成一堆细碎条目，回头看找不到重点。

**这条什么时候该破例**

如果修复的是「数据会丢」或「用户完全用不了」的级别，
那还是要发 —— 攒版本的收益抵不过风险。自环属于「会失控但能杀进程」，算可以攒。

## D-59 · 模型接入：预设表 + 三协议适配，而不是「填个地址」

**背景**

模型页原来只有三个裸字段（接口地址 / 模型 ID / API Key），默认值指向
`127.0.0.1:3425` 的本机 Magpie 网关。这等于要求用户知道 DeepSeek 的完整
接口路径、模型 ID 叫什么、以及 Claude 根本不走 OpenAI 格式。

结果是：**除了本机装了 Magpie 的那个人，别人拿到程序配不出模型。**

**决定**

1. 内置 19 家预设（`bigfish/providers.py`），选一家只填 Key
2. 真适配三种协议（openai / anthropic / gemini），不是假装兼容
3. 预设的地址/协议/模型**都可改** —— 预设是填好的默认值，不是白名单
4. 「自定义」兜住中转站、公司内网、自建服务
5. 地址归一化：粘完整 URL 也能用

**为什么不集成 SDK**

`openai` / `anthropic` 两个包加起来 10MB+，而我们要的东西只有
「发一个 POST、取一个字符串」。打包体积对这种桌面程序很敏感（现在
201MB，PyInstaller 已经够肥）。urllib 够用，而且三种协议的控制权在手里。

**为什么坚持三种协议**

可以只做 OpenAI 兼容，让 Claude/Gemini 用户自己搭中转。
但那样「主流模型接入」就是个空话 —— 而 Claude 在国内的用量不小。
三份请求体 + 三份解析，一共 60 行，这个成本值得。

**为什么测试连接要真发请求**

只检查字段填没填，验不出 Key 无效、地址不通、模型名不存在 —— 而这三样
恰恰是用户第一次配置时最可能撞上的。真发一次 `max_tokens=24`，
0.5~3 秒就出结果。

**为什么测试跑后台线程 + 票据轮询**

Qt 的 slot 在 GUI 线程里跑。一次测试要等网络 + 对方推理，同步做会把
整个窗口冻住（最长 25 秒）。改成 `test_model` 立刻返回 ticket，
前端 `poll_test` 每秒取一次。

**已知取舍**

- `sticker_desc`（表情语义描述）只支持 OpenAI 兼容渠道。另写 Anthropic /
  Gemini 的图片请求体不值得 —— 它是可选功能，失败只影响表情标签。
  遇到非 OpenAI 渠道会明确返回「不支持」，不发必然失败的请求。
- 预设的模型 ID 会过期。界面上是可选可改的输入框，写死在代码里的只是建议值。

**验证**

- `tools/selftest_providers.py`：83 断言，不联网
- `tools/probe_providers.py`：联网体检，15 家预设各发一次假 Key，
  看返回码判断地址对错（401/400 = 地址对，404 = 地址错）

## D-60 · 模型列表必须从厂商拉，不能硬编码

**背景**

D-59 的第一版把模型 ID 写死在预设表里，界面上是 `datalist` 的建议值。
用户当场指出来：

> 一般来说，都是填写接口地址，然后填写 API Key 之后，就能点击获取模型才对，
> 怎么我们这个都是预设的模型ID，你不觉得很奇怪吗，照抄 magpie 的添加供应商，
> 你都抄不全，偷工减料？

他是对的。magpie 的 README 原话是 *"Model lists come from the vendor"*。

**决定**

1. 加 `replier.list_models()`：`GET {base}/models`
2. 界面是「模型下拉 + 获取按钮 + 手填输入框」三件套
3. 预设里的 `models` 字段**降级为离线参考**，不再是界面上的候选值
4. 切到本地渠道（Magpie / Ollama / LM Studio）自动拉一次

**为什么这件事不能省**

模型 ID 是**变量**，不是常量：

- 厂商出新模型、下线旧模型，比我发版快
- 「你这把 Key 能用哪些」受额度、区域、企业版影响，跟公共文档不一样
- 单看名字猜不对：`deepseek-v4-flash` / `doubao-seed-2-1-pro-260628`（带日期）

## D-61 · 配置文件的位置只有一处：`app_root()/config.json`

**背景**

用户配好了自定义模型（agnes），点保存、界面刷新，**又变回 Magpie 网关**。
但他打开配置文件一看，保存的内容明明在里面。

查下来是路径不一致：

| 谁 | 用的是 |
|---|---|
| `desktop.CONFIG_PATH` | `_ROOT/config.json`（=`_internal/config.json`） |
| `replier.ModelConfig.load()` | `paths.app_root()/config.json`（= exe 旁边） |

两处都能"成功"，但读写不在一个文件上。

**决定**

1. `CONFIG_PATH = os.path.join(_APP_DIR, "config.json")` —— 跟 `data/` 同一层
2. 删掉 `desktop.py` 里第二处 `CONFIG_PATH` 定义（它静默覆盖第一处）
3. `app.py` 的 CLI 路径同样改用 `paths.app_root()`
4. 启动时跑一次 `_ensure_config_home()`，把误写在 `_internal` 的那份搬过来

**为什么放 exe 旁边而不是 `_internal`**

- `_internal` 是程序资源，打包/升级时整个换掉，用户配置在里面就会被冲走
- 用户要备份、要改、要拷到别的机器，都只需要动 exe 目录
- `paths.py` 的文档里本来就写着这条规范，是 `desktop.py` 没遵守

**这次踩出的三个连带坑**

1. **`deploy.py` 的迁移写在 `copytree` 之后** —— 那时旧文件已经没了，
   迁移永远什么都不做，也不会报错。必须**先读再覆盖**。
   （结果是我真的覆盖掉了用户刚配好的 agnes，后来从对话记录里恢复的。）
2. **`FETCHED_MODELS` 是前端全局变量，`loadSettings()` 时不清空** ——
   切回 Magpie 后下拉里还挂着上一个供应商的 `agnes-*`，
   看起来像"这个渠道也有这些模型"。现在每次重载都清空。
3. **`ModelConfig.load()` 其实一直是对的** —— 错的是 `desktop`。
   修的时候不要反过来把 `replier` 改成读 `_internal`。

**教训**

"配置在哪儿"这种事，项目里只能有一个答案。两个答案同时存在时，
两边都能跑通、都不报错，只有用户会发现"我改的东西没生效"。
文件里加一句注释不够，要让它**在结构上不可能写错**
（比如只留一个 `CONFIG_PATH` 定义，第二处改成注释说明为什么不能写）。

## D-62 · 昵称跟着微信走：wxid 做键，display_name 做显示

**背景**

印象页的标签显示的是裸 `wxid_51f85n6xp73o22` 和 `filehelper`，
而不是「老爸」和「文件传输助手」。

查下来：`impression_board` 的取法是

```python
"name": r["display_name"] or r["external_id"] or owner.rsplit(":", 1)[-1]
```

而 `owners.display_name` **从来没有人写过** —— 四处 `ensure_owner()` 调用
全都没传 `display_name` 参数。于是永远落到 `external_id`（就是 wxid）。

**决定**

1. **键仍然是 wxid**（`private:wechat:wxid_xxx`）。`memory.make_owner` 的
   注释写得很清楚：昵称会改、会重名、群名片可以随便设，用它做 key 等于
   把两个人的记忆混到一起，而且污染不可逆。**这条不改。**
2. **显示名单独存**：`owners.display_name`，随时可改。
3. **两个更新时机**：
   - 每次收到消息（`handle` 里），名字变了才写库
   - 打开印象页时（`impression_board`）顺手刷一次，这样即使很久没聊天，
     改完备注进来也是新名字
4. **不写兜底占位**：`_display_name` 在查不到时会返回
   「未知联系人(abc123)」。那是显示形态，不是真昵称 —— 写进库里
   就永远修不掉了（以后真查到也叫这个名字）。`_nick_of` 显式过滤掉。

**为什么不在渲染时实时查、不落库**

每次打开页面都查一遍微信 contact 库，遇到"微信没开""账号没选"就退化成
wxid。落库之后，最差情况是显示上一次知道的名字，比裸 id 好得多。

**为什么加缓存 `_name_seen`**

每条消息都 `ensure_owner` = 每条消息开一次 sqlite 连接。
聊天一密就是每秒几次写。缓存住上次的名字，变了才写。

**没做的**

- **群成员的昵称**：`Incoming.sender_name` 装的是 wxid（watch 层就这么设计的），
  要拿昵称得再查一次 contact 库。群聊场景先只保证**群名**正确，
  成员名等有需求再说。
- **反向同步**：改了 `display_name` 不会影响微信，单向。

**验证**

实测这台机器：`wxid_51f85n6xp73o22 → 老爸`、`filehelper → 文件传输助手`，
印象页 tab 已显示昵称。

## D-65 · 发布流程：deploy 必须在 build_portable 之前

**背景**

0.5.0 第一次打包，SHA-256 和上一次**一模一样**：

```
1ca94d94497fd9f5be3d60d0aa214a4722e422639321123cec6d40cf7d08596d
```

代码明明改了。查下来 `build_portable.py` 是从 `dist/BigFish` 打包的，
而 `dist/BigFish` 是上一次 `deploy.py` 部署的旧版本 —— 源码改了但没 deploy，
打出来的还是旧包。

**正确的顺序**

```
改代码 → 跑测试 → deploy.py（打包 exe + 部署到 dist/BigFish）
       → build_portable.py（把 dist/BigFish 打成 zip）
       → git commit + tag + push
       → make_release.py
```

**怎么识别踩了这个坑**

看 SHA。同一份代码两次打包 SHA 必然相同，但**改过代码后 SHA 不变就是没打进去**。
这比"打开 zip 翻文件"快得多。

**第二个坑：make_release 跳过已存在的附件**

原来 `if name in existing: 跳过`。于是"改完代码重新发一次"会静默保留旧包 ——
版本号一样、Release 页面看着也对，但下载下来是上一版。

现在加 `--force`：先 `DELETE /releases/assets/{id}` 再上传。
删完 `sleep 1.5` —— 立刻传偶尔会撞 422。

**教训**

发布链路里每一步的输入都必须是"刚刚生成的东西"。任何一步读的是缓存/上次的产物，
都会得到"看起来成功、实际是旧的"的结果。SHA 是这条链路上唯一诚实的信号。

## D-66 · 重试写在 call_model 内部，不写在调用点

**日期**：2026-11-04

**背景**：`call_model` 有 6 个调用点（对话、画像归纳、断句、测试连接、桥接测试、
自检）。任何一个漏加重试，就会出现"有时候她会回，有时候不回"的随机故障。

**决定**：把重试放进 `call_model`，调用点不需要知道。

- 只重试「换个时间可能成功」的：429 / 5xx / 网络 / 响应不是 JSON
- 4xx（key 错、模型名错、余额不足）**不重试** —— 重试三次只是把错误延迟三秒
- 空正文（推理吃光预算）单独处理：`max_tokens ×1.5` 再试一次，而不是原样重试
- `attempts` 可传，默认 3；退避 1s/2s/4s

**代价**：单次失败的最坏耗时从 90s 变成 90×3 + 7s。可接受 ——
比"这一轮彻底没回复"好。

## D-67 · 快照按文件名滚动，不按 mtime

**日期**：2026-11-04

**踩过的坑**：`selftest_trace` 写 14 份、keep=10，结果**最新的那份被删了**。

**原因**：Windows 的 `st_mtime` 精度约 100ms，同一批写入的 mtime 完全相同，
`sort(key=mtime)` 的顺序是随机的，`files[:len-keep]` 可能切到刚写的那份。

**决定**：文件名带 `YYYYMMDD-HHMMSS-mmm-<序号>`，排序直接用文件名。
序号用进程内 `itertools.count`，保证同一毫秒内也严格递增。

**副产品**：`recent()` 也改成按文件名倒序 —— 两处口径必须一致，
否则"列表第一条"和"被删的那条"会对不上。

## D-68 · 降级只在桥接报错时触发

**日期**：2026-11-04

## D-69 · 不为「宿主环境造成的失败」改代码

**日期**：2026-11-04

**现象**：`BigFish.exe --selftest` 的「灵魂」项报
`数据目录不可写：Permission denied 'D:\大肥鱼\.bigfish-write-probe.tmp'`。
同一台机器、同一目录，`python` 走 `vault.probe_writable()` 返回 `(True, '')`。

**查证过程**（四条对照）：

| 实验 | 结果 |
|---|---|
| 同 shell 的 python 写目标目录 | ✅ |
| 大肥鱼 exe 从 `D:\大脑` 启动 | ❌ |
| 最小 PyInstaller exe 从 `D:\大脑` 启动 | ❌（连 `%TEMP%` 都建不了临时目录） |
| 同一个 mini.exe 复制到 `%TEMP%` 再运行 | ✅ |

**结论**：不是 ACL、不是中文路径、不是杀软误杀（本机只有 Defender 且实时保护开着），
而是**从该工作目录启动的外部 exe 被宿主环境限制了写入**。
用户双击运行（Explorer 启动）不受影响 —— `soul.json` 在此期间仍被正常更新。

**决定**：

1. 不改 `vault` / `ensure_data_root` 的判定逻辑。它在真实运行环境里是对的，
   为了让"自检变绿"而放宽判据，会掩盖真正该报的权限问题。
2. 保留「灵魂」失败项。它是一份诚实的信号：**这个启动方式下写不了数据**。
3. 新增 `prompt_trace.probe()` + `stats.writable`：快照是"旁路"，
   它写不进去必须**可见**（设置页直接说明原因），而不是静默为空。

**判断标准（以后遇到类似情况）**：
> 换一个启动方式/另一台机器，还失败吗？
> 还失败 → 产品问题；不失败 → 环境问题，别改代码，改文档或加提示。

## D-84 · 配置要能表达"这个会话不一样"

**时间**：2026-11-04 夜 ～ 11-05 凌晨

**背景**

自环事故复盘时，第一条根因写的是「`allow_self = True` 留在生产配置里」。
但再往下问一层：**为什么它会漏到生产？** 答案是配置层根本没有"会话级"这个
概念 —— `auto_reply.allow_self` 是一个全局布尔，代码里配一个写死的白名单
（`chat_id == "filehelper"`）。

所以真正的病因不是"忘了关"，是**这个开关只能全局，于是谁需要它，所有人都有它**。

**决定**

1. 行为开关改三层：`scopes.chat` → `scopes.account` → `scopes.global` → 代码默认值。
2. 布尔字段三态：缺失/`null` = 继承，`true` = 开，`false` = **显式关闭**。
   列表/数字：缺失 = 继承，给 `[]` / `0` = 显式值。
3. 会话键只用平台 id；昵称做只读别名，解析不到算未命中。
4. 读时兼容旧路径，写时只写新路径；**不自动改写用户文件**（守 D-35）。
5. 每轮重读，不做变更通知。

**为什么不把旧值映射到 global（这条改掉了原设计）**

原计划：`auto_reply.allow_self` → `scopes.global.allow_self`。

照做的话，线上那份 `true` 会让**每个会话**重新拿到 `true` ——
相当于用"重构"的名义把事故开关重新打开一次。

改成：旧的全局 `true` 只落到 `filehelper` 一个会话（`legacy_self`）。
理由是这个开关**本来的意图**就是自测通道，代码里的白名单也是在替它表达
这个意图。让配置承担同一句话，是把它写对，不是改变行为。

**副产品**：升级之后**一个字的配置都不用改，私聊就已经安全了**。

**为什么不保留 `AppConfig` 上那五个扁平字段**

一开始想留它们当"全局镜像"，方便旧代码读。但镜像会漂移：
读到的是加载那一刻的值，和真正生效的值可能早就不是一回事。
这正是 D-61 的教训（`CONFIG_PATH` 定义两遍，两处都能跑通）。

删掉之后，读错就是 `AttributeError`，当场看得见，不用等用户发现
"我改的东西没生效"。

**代价**

- `AppConfig` 不再是"配置的完整快照"，读某个行为值必须给 chat_id。
  这是刻意的：不给会话就说不出"对谁生效"。
- `group_allow_all` 按会话解析时语义略绕：得到的是"这个群看到的那份名单"，
  所以 `scopes.chat[G].group_allow_all = [G]` 才等于给 G 开 allow_all。
  写进文档了。

**验证**

- `selftest_scopes` 95 条断言，覆盖三层回退/三态/空列表/零值/别名/id 优先/
  旧路径/新路径优先/只读/来源标注，外加两条事故复现。
- 变异测试：把实现改坏五处，分别被抓 2 / 14 / 1 / 13 / 6 条。
- 线上 `config.json` 只读核对：filehelper → true，私聊/群 → false，文件未改动。

## D-86 · 判身份要三态，而且私聊和群聊要倒向不同边

**时间**：2026-11-05

**背景**

自环事故的第一个根因写的是"`allow_self` 留在生产配置里"。再往下问一层：
**为什么这个开关能漏？** 因为程序根本没法可靠判断一条消息是不是她自己发的。

原判据一行，两个文件各写一遍：

```python
is_self = (sender == self._me) if sender else False
```

三种静默失手（sender 解析不出 / me 读不到 / 群里分片缺失），**全都倒向
"当成对方说的"**。而"当成对方"意味着要回复，所以每错一次都是往自环里推一步。

**决定**

1. 三态：`self` / `peer` / `unknown`。不引入置信度分数 —— 分数会诱使人去调参数，
   而这里没有可调的余地：要么知道，要么不知道。依据用**证据列表**表达，可回溯。
2. 两源：DB 的 `sender` 字段 + 群正文的 `wxid:` 前缀。前缀**只认 wxid 形态**，
   不能用 `loopguard` 那个宽松正则（它是剥前缀用的，`notes: …` 也会被吃掉）。
3. **私聊保守、群聊宽松**：拿不准时私聊不回，群里只有在真的叫了她
   （`at:` / `called:`）时才当对方处理。
4. `me` 读不到 → **拒绝启动**，不是降级。
5. 四处收口到 `bigfish/identity.py`：`watcher` / `wechat` / `run_uia` / `app`+`desktop`。
6. 证据链只记**不干净**的判定，旁路 JSON，滚动 200 份。

**为什么私聊和群聊不一样**

私聊里判错的代价是自问自答刷屏（那晚就是），而且只有两个人，用户一眼看出异常；
群里判错的代价只是"今天没接话"，而群里本来就有 @ 门槛挡着。
两个场景的最坏结果差一个量级，用一个策略反而是错的。

**为什么 `me` 缺失要拒绝启动而不是降级**

降级意味着"用别的依据凑合判断"，可那些依据此刻全都不存在
（所有比较都以 `me` 为基准）。继续跑就是拿"这条不是我自己发的"去赌，
而那晚已经赌输过一次。**不知道自己是谁的时候不要开口。**

**为什么不把 `feed()` 里那道 is_self 删掉**

现在是第二层网。判据错了还有它挡一道；判据对了它是空转。
自环的代价是刷屏 + 记忆污染，多留一层不亏。

**顺带发现的**

`selftest_app_wiring` 里的「自己的消息不入批」**一直是假通过**：
它断言 `batcher.pending()` 为空，而 `listen.feed()` 自己就有 `if msg.is_self: return None`。
也就是说那条断言从 0.4.x 起一直在测 listen 层，`_accept` 的归属判断
从来没被覆盖到 —— 改坏了也不会红。已改成直接断言 `_accept(...) is None`。

**代价**

- `run_uia.py`（原型入口）没有接 scopes，自测通道仍只认 `filehelper`。
  这是保留既有语义，不是漏改；已写进代码注释。
- 拿不准时**不会有任何提示**，用户只会觉得"她没回"。所以证据链必须能找到，
  否则这类问题会变成"她又抽风了"。

**验证**

- `selftest_identity` 58 条；`selftest_app_wiring` 15 → 17 条（并修正了测错层）。
- 变异测试六处：sender 空当对方 (18)、me 缺失当对方 (2)、免检群算叫她 (4)、
  UNKNOWN 私聊放行 (5)、宽松前缀正则 (2)、接线层拿不准当对方 (1)。
- 线上配置只读核对：`filehelper → true`、私聊/群 → `false`，文件未改动。

## D-87 · 账本可以否决判据，但必须留痕

**时间**：2026-11-05

**背景**

A-1 之后判据能说"是对方 / 是我 / 拿不准"了。那账本还剩什么用？

**剩下的用处是：它能否决 A。** 11-04 那晚不是"账本不够好"，是**判据判错了
之后没有任何东西能按住它** —— A 说"这是对方说的"，于是回复；回复被读回来；
再判成对方说的……账本就是在这一步兜底：*你说是对方，可我 1 秒前正好发过这句。*

**决定**

1. 账本同时负责**拦截**和**发送确认**，两套记录合并成一套
   （以前 `loopguard._sent` 管拦截、`app.py` 去库里查 `is_self` 管确认，互不认识）。
2. **不持久化**，重启即清空（与 D-9 水位同一理由：残留账会误杀新消息）。
3. 匹配：**相等**，或**长度差 ≤ max(1, 10%) 且两边都 ≥12 字、前 12 字相同**。
4. **账本能否决判据**，但只在账本命中且仍在窗口内（默认 90 秒）时；
   每次否决**必须写证据链**（`ledger_veto`）。
5. 记账**必须在发送之前**（那条 11-04 的教训，一个字不能松）。

**为什么允许否决**

否决的失败代价 = 吞掉一条真消息（对方 90 秒内逐字复述她的话，很少见）；
不自环的失败代价 = 刷屏 + 记忆污染 + 只能杀进程。两者差一个量级。

但一旦允许否决却不留痕，它就会变成新的"改了没生效"——
所以 `identity_trace.record(..., force=True)` 是这条决策的一部分，不是可选项。

**为什么把前缀匹配收紧**

原规则是"互相前缀"（≥12 字且一方以另一方开头）。原测试拿 16 字对 22 字断言命中——
可读回来不可能凭空多出七个字。**多出来就是另一条消息**，把它判成回环
就是把对方接着她的话说下去当成自己说的。这正好是 D-20 要拆的那条线。

新规则加了长度护栏，同时加了**绝对下限 `max(1, 10%)`**：
纯比例算 7 个字差 1 个就是 14%，会把同一句判成两句。

**代价**

- 对方逐字复述她的话（90 秒内）会被吞一条。可接受，且能查到。
- 账本按会话记，`LoopGuard` 的老调用不传 chat 时仍是全局 —— 兼容但略松。

**验证**

- `selftest_ledger` 40 条；`selftest_loopguard` 44 → 47（新增三条匹配边界）；
  `selftest_app_wiring` 17 → 21（新增否决与记账）。
- 变异测试六处：去长度护栏 (2)、查询不分会话 (2)、不裁旧 (2)、撤账失效 (2)、
  不剥群前缀 (1)、账本不否决 (1)。

## D-70 · "不知道发没发"必须是第三种结果

**时间**：2026-11-05

**背景**

发送一直只有两种结果：`SendResult(ok=True)` 或抛 `SendError`。
可真实世界有第三种 —— **回车可能已经按下去了，但我们不知道**。

把它塞进"失败"里，会同时犯两个错：

- 调用方可能重发 → 对方收到两遍
- 账本撤掉这一笔 → 读回来没人认得 → **自环从这里开始**

**决定**

1. 三态：`sent` / `failed` / `unknown`，独立成 `bigfish/sending.py`。
2. 分界线用**异常发生在哪一步**：前置检查失败（桌面锁 / 窗口没了 /
   打不开会话 / 名字不匹配 / 空内容）= 确定没发；走到发送调用之后 = 未知。
3. 未知的后果三条同时成立：**不重试、不撤账、告诉用户**。
4. 拿不准的时候一律按未知 —— 把"可能发了"当成"没发"的代价，
   远大于把"没发"当成"可能发了"。

**关键发现：底层早就埋好了信号**

```python
# vendor/uia_driver.py
try:
    # SendKeys 抛异常也可能已经投递回车，调用方不能据 False 重新发送。
    self._send_attempted = True
    e.SendKeys("{Enter}", waitTime=0.05)
except Exception:
    return False
```

`_send_attempted` 在按回车**之前**置真，返回 False 后仍然保留。
`guia.py` 里已经完整用了它（2054/2107/2118/2126 都在查它并拒绝重发），
只有 `wechat_sender.UiaSender` 这条路没接。

**所以这不是"缺能力"，是"没接线"。** 值得记一笔：
下次遇到"某个信号到底存不存在"的问题，先去底层库翻一遍，
别急着在自己这层加判断。

**代价**

- 未知时这一轮就断了，后面的分条不发。用户可能看到半句话 ——
  但比"补上一串可能重复的话"好。
- `attempted` 只能表达"回车按过没有"，表达不了"粘贴有没有落进去"。
  那一层由库自己的相似度检查兜着（`SEND_CONTENT_RATIO`）。

**验证**

- `selftest_sending` 22 条；`selftest_say` 65 → 71（三态集成）。
- 变异测试：未知当失败 (7)、未知也可重试 (2)、未知也撤账 (2)、
  前置错误当未知 (1)。

## D-71 · 复查抓到六个 bug，其中两个是我自己上一轮写进去的

**时间**：2026-11-05

**背景**

C-1 / A-1 / D-1 / B-1 四项做完后要求"重新检查一遍，确保都改正确了"。
不靠记忆，逐文件重读 + 针对性验证，抓到六个问题。

**六个 bug**

| # | 位置 | 症状 | 根因 |
| --- | --- | --- | --- |
| 1 | `say.send_parts` | 发送函数直接返回 `True` 时被判成**失败** | 换成 `sending.classify` 时丢了 `_msg_field(result,"ok",result)` 的裸值回退 |
| 2 | `desktop._trace_identity` | 否决时抛 `TypeError`，**能把引擎线程打挂** | 给调用点加了 `decision=` 参数，函数定义没跟上 |
| 3 | `wechat_sender.send` | "确定没发"被误判成"未知" | `_send_attempted` 是**上一轮**留下的值；它只在 `send_text()` 里重置，而 `send_text_to()` 可能连那一步都没进 |
| 4 | `scopes._chat_block` | 写 `_comment` 就弹警告 | 把注释键当成非法会话块 |
| 5 | `app._trace_identity` | 否决留痕里写的是 `self` 而不是 `ledger_veto` | 用了 `decision or admit(...)`，而 `Decision.__bool__` 返回 `proceed`，否决的 proceed 恰好是 False |
| 6 | `desktop` 发送成功后 | 记账不带会话，可能跨会话误否决 | `remember_sent(reply)` 漏了 chat |

**5 是这次最有教育意义的一条**

`Decision` 有 `__bool__`（等于 `proceed`），写 `decision or 默认值` 很自然，
但**否决场景的 proceed 正是 False** —— 于是"我给了 decision"被当成"没给"，

- 接线测试原来会把证据链写进真实 `data/identity-trace/`（一次跑出 28 份）。

- 新增 `tools/check_call_sites.py`：静态检查模块内函数调用点的参数是否
  与定义相符。bug 2 就是这类，而它在 5000 行的文件里肉眼看不出来。
  已验证：把 bug 2 的签名改回去，它当场报出来。

**验证**

- 全部 20 个自检 + Qt 检查 + 调用点检查全绿（1275 条断言）。

- `selftest_app_wiring` 21 → 24（新增否决留痕 3 条）。

## D-72 · `content-visibility` 是负优化，缩略图该用 WebP

## D-73 · 表情去重不能用感知哈希

**时间**：2026-11-05

**背景**

批量导入 2000 张时，同一张图换个名字就会变成两条。

**试过、否掉的**

- **dHash 单独判重**：2181 张全是同一角色的换装表情，
  「开心挥手」和「按按钮冒汗」距离 **0** —— 64 位全一样。
- **pHash**：真重复对 `stk_0148/stk_0060` 距离 **16**，
  而同角色不同图反而到 10。更糟。
- **单看色差的**：换配色的同一张（29）和换表情（31~42）混在一起。

**结论**：判据必须是「**配色也几乎一致**」，不是「结构像」。
结构和配色两个数**一起看**才分得开：

```
色差  格数  结构   这是什么
  1     0     0    同一张图重新导出          ← 跳过
 29     0    18    同一张图换了配色           ← 只提示
 42     1    34    同角色，构图几乎不变       ← 只提示
 70     3     4    同角色，换表情             ← 收
153     3     1    同一张图加了一条字幕       ← 跳过（这是"格数少+色差大"）
```

**决定**

三层：字节 sha256 → 差异格数 ≤2 且色差 ≤40 → 只提示。
确定重复的**唯一**判据是"差异格数 ≤2"，色差只是把"换了配色"摘出去。

**边界**：整条字幕（底部 1/4）格数会到 24，和"换表情"分不开，不判重。

## D-74 · 进"表情包"卡，真凶是每 2 秒的微信进程探测

## D-76 · "聊几句突然不理你"是拟人节流，不是卡死

**时间**：2026-11-06

**现象**

用户报：聊几句之后会有一段时间完全不回复，过一会儿又冒出一大堆。

**证据（不是我猜的，是底层自己记的）**

```
00:51:25 拟人节流：120s 内已写 6 次（send），冷却 33s 再继续
00:51:58 拟人节流：send 前等待 34.0s
01:04:06 拟人节流：120s 内已写 6 次（send），冷却 65s 再继续
01:05:11 拟人节流：send 前等待 66.5s
```

`vendor/wechatauto-replica/wechatauto/rhythm.py` 的 `natural` 档：

```
gap     = 1.0~1.45s      每次写动作之间的间隔
burst   = 6              窗口内允许的写动作次数
window  = 120s           统计窗口
cooloff = 30~75s         撞到上限后的冷却
```

而大肥鱼**一轮会发 2~4 条**（分条），两轮就 6 次 —— 第三轮直接撞上限，
被按住 30~75 秒。冷却结束时积压的几条一起出去，就是"突然回复一大堆"。

**决定**

默认档从 `natural` 换成 `fast`（20 次 / 120 秒，冷却 4~9 秒），
配置项 `auto_reply.rhythm`，可选 `natural / calm / fast / off`。

**为什么不干脆关掉**

这一层是故意的：写动作之间要有间隔、密集写要冷却，目的是像人不像机器。
关掉（`off`）等于把账号表现完全交给恒定节奏，风险更高。
`fast` 仍然是非恒速的，只是把上限抬到正常对话不会撞到的位置。

**为什么之前查不出来**

引擎日志只有 `[想]` 和 `[发]`，中间 20~70 秒是空白 —— 没有任何计时。
这次先加了三个计时点（切条 / 挑图 / 发送）+ 后置挑图单独计时，
量出「发送 21.0s、切条 0.0s、挑图 0.0s」，才把方向锁定到发送，
再去底层日志里找到冷却记录。**加计时是对的一步，光看现象只能瞎猜。**

**验证**

- `selftest_sending` 29 → 32（档位说明、乱写不炸）。
- 启动日志会打 `[节流] 节奏档 fast —— 宽松档：120 秒内最多写 20 次…`。

## D-77 · L2 回环因为少传一个 `chat` 而整体失效

**时间**：2026-11-06

**现象**

文件传输助手里，她把自己回的每一条都当成对方说的，一句接一句地接自己的话。

**根因**

D-1 把账本从"全局一份"改成"按会话记"，`note_sent` / `is_echo` 都加了
`chat` 参数。但 `loopguard.admit()` 里这一行没跟着改：

```python
if self.is_echo(text):          # 少了 chat
```

于是它去查"全局桶"——那个桶从 D-1 起永远是空的，**L2 内容比对彻底失效**。

**教训**

默认值让遗漏不报错，只让行为静默变错。

而且她**根本不知道自己能发表情**：表情包插件 scope 是 `sticker`，不注入
prompt 段（当前注入的是生活 870 / 说法 890 / 守卫 9990）。模型手里没有工具，

修法：
- `wants_sticker(body)` 命中"表情/表情包/斗图/发个图…"→ **不掷骰子、不受冷却**。
  已知误判：夸一张表情也会算"要"，多发一张；比"要了没反应"便宜。

**还没做的**

"要不要发"仍然是掷骰子。干净的做法是给模型一个真实手柄（约定标记 →
引擎见到就发），那样"她想发"和"系统发得出"才对齐。等这版跑稳再说。

## D-89 · 她的作息按自己的钟，一天由醒来推进

**日期**：2026-11-07

### 背景

两个看似合理、实际都错的起点：

**① 「你最后一条消息之后 40 分钟她也睡」**

反例很短：你早上 9 点发一条，然后一整天没说话。
按这个算法她 9:40 就该睡了 —— 她的一天从早上 9:40 结束？
晚上 11 点你再发，她"刚醒"？

这不是贴心，是回声。**她必须有自己的 24 小时，不管你说不说话。**

**② 「凌晨 4 点前算昨天」**

她的起床时刻是浮动的：07:40 ± 35 分钟抖动 + 晚醒最多 100 分钟（睡眠债）
→ 最晚能到 09:55。任何固定分界线都会在某个时间段和真实状态打架：

```
05:00 启动 → 按 4 点切，她算"今天"，于是判成醒着 —— 可她刚睡下两小时
07:00 启动 → 已经"新的一天"了，但 wake_at 是 08:10 —— 她还在睡
```

### 决定

**两个时钟，且「一天」只由醒来推进。**

```
主时钟（她的）：BEDTIME_BASE 23:20 ± 42，SLEEP_BASE 8h20m ± 35
扰动（你的）：  EXTEND_STEP 18~38 分钟/次，EXTEND_CAP 96 分钟/晚
```

- `plan_day()` 只在 **醒来** 和 **冷启动** 两个时机调用
- 醒着跨过午夜**不重排**（她还没睡，那一天没结束）
- 冷启动才猜一次（`asleep_window()`），猜完落盘，之后永远以 `state.asleep` 为准

### 一个必须记住的实现细节

**所有睡眠窗口判断只能用 epoch，不能用「一天中的分钟数」。**

入睡点会跨午夜：`BEDTIME_BASE + jitter` 最大是 23:20 + 42 = 24:02。
`_minutes_of_day(次日 00:02)` 返回 2 —— 于是 23:50 被算成
"1400 <= 1430 < 1440 不成立" → 判成醒着。整晚的判断全部错位一小时。

第一版就是这么错的：`selftest_life` 里 "23:50 冷启动" 那条失败，
查下来是 `_slot_for` 里把小时当成分钟用（`hour` 和 `minute` 混了）。

### 后果

- 你熬夜，她陪你撑；撑到 96 分钟上限就睡，第二天说"昨晚聊着聊着睡着了"
- 你熬到 3 点，第二天她 13:00 才醒（睡满 10 小时 + 债），且起床精力只有 42
- 你一整天不说话，她照样 23:20 左右睡、第二天 7:40 左右醒

**日期**：2026-11-07

### 背景

P1 第一项是"主动开口"。它的特殊性在于：**这是唯一一条没有对方消息
作为起点的发送路径**。

所有其他发送都发生在"有人说了话"之后 —— 就算判错，下一条对方消息
还能把话题拉回来。主动开口没有这个安全网：一旦跑飞，用户只能杀进程。

0.4.1 那次自环事故（她跟自己聊到天亮）之后立的规矩是
「能自己跑飞的问题，比回得好不好更重要」。主动开口正好是这类。

### 决定

三层，每层各自独立失败：

    本地判定   六道闸门 + 六源打分。**不调模型、不读库、不发消息**
    复核       过了闸门才调一次模型：「现在发合适吗」
    发送       sending 三态 + loopguard 记账 + 结果未知不重发

### 为什么判定必须是本地的

如果每次评估都问模型，一天 288 次（5 分钟一次）× N 个会话 ——
这不是生命，是烧钱。而且**判定只需要条件，不需要语言能力**：
"现在 3 点" 这种判断用 `hour` 就能算，不需要一个 70B 模型。

模型只在两处出现：复核（要不要发）、生成（说什么）。

### 为什么第 3、5 条闸门不开放配置

    9:00–22:30      半夜发消息是灾难
    你最近 30 分钟没在聊  否则她会在你说完话之后立刻接一句，像客服

"可配"和"可关"是两件事。前者是用户偏好，后者是安全边界。
灾难性的默认值不该给一个开关 —— 用户熬夜时不会想起来去关它。

### 后果

- 一天最多 1 条（可配），一周模拟实际发出 5 条，有两天一条没有
- 复核否掉的比例会很高（这是对的，跳过不丢人）
- 发送结果未知时不重发、不补发 —— 和普通回复同一条规矩

## D-92 · 没回消息时：追问和忘记都要有可能

    必追    像催债。第二句「在忙？」出来的时候，关系就变味了
    必不追  像不在乎。她永远"发完就消失"，主动就没意义了

## D-96 · 主动开口：从「分数过线」改成「掷骰子」

0.9.1 的主动开口在机制上是对的，但节奏不像人：一天最多 1 条、分数过 55 就发，
同一组条件永远得到同一个结果。

用户的两句话：

> 我觉得已经很像人了吗？我不太清楚你做到哪一地步了

> 这也有个主动说话的插件，你参考一下

参考项目（dsh-speak-up）的核心是**掷骰子**：定时掷一次，掷中才走一轮。
它不选话题、不打分、不审核 —— 只决定"要不要开口"，说什么交给 agent 自己。

### 决定

保留我们的安全层（自环、三态、账本），把**节奏**和**话题来源**换掉：

    闸门 → 掷骰 → 候选打分（取最高，低于 40 不掷）→ 模型复核 → 发送

命中线 = 基础率(分数) × 时机因子 + 没中加成。

### 抄了什么

- **掷骰代替阈值**：同样条件今天可能说、明天可能不说
- **没中加成**：沉默不该无限自我强化（+8%/次，上限 +32%，掷中清零）
- **时机因子**：刚发过 ×0.15、你正在聊 ×0.5、冷 6 小时 ×1.4
- **可观察**：每轮写「掷出 X / 命中 Y」，否则"她今天没说话"和"功能坏了"长得一样

### 没抄什么

- **频率**：它一天能说十几次（喂进去的是"一轮对话"），我们是往真人微信发消息
- **不管发送安全**：没有自环检测、没有发送前记账
- **掷骰状态不落盘**：重启归零，我们的 `miss_streak` 存盘

### 自己加的一条：`whim`

前六个来源都能被解释。而真人主动找你，绝大多数时候解释不了 ——
就是忽然想起来了。没有它，"她主动说话"永远是一份待办清单在执行。

### 调参踩的坑

第一版掷骰间隔设 40 分钟（一天 20 次机会），模拟出来**所有场景都是 3 条打满**。
单次命中率就算只有 6%，加上没中加成爬到 39%，20 次机会必然用光额度。

**关键不是命中率，是机会数。** 改成 120 分钟（6–7 次机会）才有方差。

### 后果

- 一天平均 1.35（常聊）～ 2.05（冷落）条，有 0 条的日子，不会天天打满
- `per_day` 默认 1 → 3，`MIN_GAP` 90 → 45
- 新增 `tools/selftest_pace.py`：节奏本身成为一条可以失败的自检
- 修掉两个「分数低于阈值、从来没触发过」的来源（life_share / 夜间问候）

## D-98 · 接话与补一句：判据是「这句话够不够」，不是概率

用户提出需求时先问了一个关键问题：

> a 也有个问题，很容易出现每次都追加一句，这就很假了，这个有什么解决思路吗

### 问题

如果"补一句"是一个概率（比如 30%），会同时得到两个坏结果：
该补的时候（"哦"）没补，不该补的时候（说完一整段）又补一句废话。
因为**"补"没有理由，只有一个概率**。

### 决定

把"补一句"定义成**"话说太短了，补够"**，不是"额外加一句"。

    主回复 ≥12 字        → 不补（说完了）
    已经分了 ≥2 条       → 不补
    以问句结尾           → 不补（球踢出去了）
    6 小时内补过         → 不补
    最近 3 条内补过      → 不补
    全过 → 掷骰 50%

叫"生成宽松、发送严格"：模型想补就让它写，但只有主回复本身不完整才真发。

### 为什么和 C（不接）一起做

两者用的是同一套判据（这句话够不够），分开写等于把长度门槛写两遍，
哪天两边数字不一致，行为就没法解释了。

### 四条取消条件（这次最容易出事的地方）

第二段是延迟 8–25 秒发的，这中间世界会变：

    对方说话了   → 补的那句会和新消息撞车
    她睡了       → 和 sleep-gate 的规则一致
    超过 90 秒   → 语境过去了，这时补像自言自语
    UIA 没就绪   → 丢，不重试

第一条用**收到消息的序号**（recv_count）判断，不用时间戳 ——
序号不会被她自己的发送干扰，也不受时钟影响。

### 踩的坑

`allow_afterthought` 的"最近补过几条"门槛写反了：

    if recent_count >= AFTER_STREAK_LIMIT:   # 越常补越允许补

`recent_count` 是"距上次补过之后过了几条回复"，小 = 刚补过。方向反了。
是测试抓出来的（用例名就叫「最近 2 条内补过 → 不补」）。

### 后果

- 一天 30 条回复里补 1–2 次，都在「哦」「行吧」后面
- 连着 2 次不接后第 3 次强制回，避免"她彻底消失"
- 新增 `tools/selftest_afterthought.py`（45 条），七种冲突各一条用例

## D-104 复盘允许"今天没什么可写"

**时间**：2026-11-08

## D-106 日记和复盘是两件事，不能合并

**时间**：2026-11-08

**背景**：用户要「每天睡前在本地写一篇日志，不限字数」。
已有的睡前复盘（D-103 / D-104）也在同一时间窗口，看起来可以合并成一次调用。

**试过并否掉的方案**：

```json
{"journal": "今天……", "summary": "……", "changed_view": [...]}
```

理由：`journal` 是自由散文，要放进 JSON 字符串里就得转义换行和引号。
模型为了让括号合法，会把句子写短、写平 —— 试写出来的东西像
"带 JSON 外壳的周报"，不是日记。

**选择**：两次调用，各写各的。

    复盘（bedtime-30min）  严格 JSON  → soul.selfNotes
    日记（bedtime-20min）  自由 Markdown → journal/YYYY-MM-DD.md

错开 10 分钟：本地网关同时两个请求会排队，而素材几乎一样，没必要抢。

**为什么日记不进提示词**：
· 可能上千字，塞进 system 会挤掉记忆和对话；
· 她"记得今天"靠 memory / mood / facts，不是重读日记；
· 真人也不会每天早上把昨天的日记读一遍再开口。

以后想让"她记得自己写过什么"，正确做法是把日记的一句话摘要
写进记忆库，而不是注入全文。

**同名不同物**：v0.9.1 删过一个 `journal.py`（睡前写三行、次日注入），
理由是和记忆重复。这次重建的是**写文件、不注入**，语义完全不同。
`selftest_ui_pages.py` 里那条"journal 必须不存在"的对账因此反转，
反转理由写在断言旁边 —— 不写理由的话，下一个人会以为是谁手滑加回来的。

**为什么是 Markdown 文件不是 SQLite**：
用户会想直接打开看、同步网盘、打印、拿记事本改两个字。
存成数据库行，他得先有个工具才能读到自己的日记，那就不叫日记本了。

**踩的坑**：第一次试跑，素材里没有"沙发"，模型自己补了一句
"我坐在沙发上"。日记允许主观，但不能和 `life.json` 的 `doing` 冲突。
现在把 `doing` 注入，并在提示词里写死"写到自己在做什么时只能用材料里的"。

## D-107 日志的素材闸门比复盘宽松

**时间**：2026-11-08

**背景**：复盘要求"不重复对话 ≥3 条，或事实/事件 ≥1"，否则不写（D-104）。
日记如果照抄这个门槛，大部分平淡的日子都写不了 —— 而平淡正是日记该记的。

**选择**：

    有 1 条真实对话   → 写
    有 1 条事实/事件  → 写
    只有心情记录      → 不写（二手摘要，再生成会漂两次）
    一句都没有        → 不写（写出来一定是编的）

**为什么"只有心情"仍然不写**：心情 timeline 是模型上一轮写的摘要，
拿摘要再生成散文，会漂两次；而且它没有具体的话，写出来只剩"今天我有点难过"。

**后果**：
- 日记允许"今天很安静，只说了两句"；
- 复盘仍然严格 —— 两层的尺度不同，是有意的。

## D-108 空白日也能写，但不是"允许编"

**时间**：2026-11-08

**用户原话**：

> 允许当天啥也没发生，也能写日志，但是日志一定不能瞎编没有发生的事。

这两句放在一起看起来矛盾：没有素材，怎么写得出细节？

**第一次实现（v0.10.1）走错了方向**：给日志加了"至少一句真实对话"的闸门。
结果大部分平淡的日子直接不写 —— 而平淡正是日记该记的。

**第二次实现（v0.10.2）拆成两件事**：

    能不能写    → 门槛降到"有没有一个可以依附的今天"
    写什么      → 不靠模型自觉，靠素材够不够具体

**关键：素材不够，补素材，不是让模型闭嘴。**

实测 v0.10.1 在素材只有"在沙发上看书"时，写出 536 字，
里面有煮面、泡茶、楼下小孩、整理柜子、书里讲的故事 —— 全是编的。
它不是撒谎，是**没材料**。

所以加了 `life.day_trace`：今天 `doing` 变过几次就记几条（最多 12 条，
跨天清空）。请求里带上：

    06:20 在沙发上看书
    09:20 在收拾屋子
    12:20 在沙发上看书

同一夹具，v0.10.2 写出 124 字，时间、动作全部对得上，没有编。

**另外两条**：

1. **空白要明说**。素材空着的时候，模型会以为"材料没给全"，
   然后自己补一段对话。所以请求里明确写「今天没有人跟你说话」
   「今天没有安排」，并附一句"那些话没有发生过"。
2. **把"什么算编"列出来**，不要只说"不要编"：
   材料里没有煮面就不要写煮面；**没写进材料的日常，就当它没发生**；
   材料少的时候日记就该短。

**和 D-107 的关系**：D-107 写的是"素材闸门比复盘宽松"，
v0.10.2 把这个闸门基本拆了。D-107 保留原文，因为"为什么当时觉得该有闸门"
这件事本身有价值 —— 它记录的是一次判断失误。

## D-66 · 倾听：桌面端接入攒批 + 自适应窗口

**背景**

用户反馈：

> 总是在别人说一句话的时候就开始思考了，但是不仅仅大肥鱼要断句，别人也会
> 断句啊，那别人断句的时候，你突然就发消息打断人家是不是不合适？

查下来两个根因叠在一起：

1. **桌面端根本没接倾听层**。0.4.0 做的攒批只在 `app.py`（CLI）里接了，
   而用户跑的是 exe —— `watcher.on_message = handle`，逐条立即处理。
2. **`handle` 阻塞监听线程**。watcher 线程直接调 handle，handle 里要调模型
   （2~16 秒）。这期间轮询停摆，对方接着发的消息只能等下一轮，而且读到时
   是"一次几条、每条各调一次模型"。

**决定**

1. `watcher.on_message = enqueue` —— 只入批，立即返回。
   另起 `bigfish-batch` 线程，每 200ms 封批。
2. **自适应窗口**（`listen.adaptive_quiet`），算法照 AstrBot 的
   `private_debounce`：

   ```
   ratio = min(1, 字数 / 60)
   quiet = quiet_max - (quiet_max - quiet_min) * ratio
   句末标点 → -0.2    逗号/省略号 → +0.3    没标点 → +0.2
   夹在 [1.5, 4.0]
   ```

3. `max_wait` 8 → 12 秒（4 秒窗口 × 连发 3 条，8 秒会截断）

**为什么不照 MaiBot 的 turn_trigger**

MaiBot 那套是六道闸 + 注意力漂移 + 空闲退避 + 概率门控，回答的是
**「这批消息值不值得开一次思考」**，属于"该不该回"。

这次的问题是**"什么时候回"** —— 对方还在说，就别开口。AstrBot 的
`quiet_seconds()` 正好只做这一件事，二十行代码，直接搬。

照 MaiBot 那套要连它的引擎状态一起移植（注意力值、退避曲线、回复概率），
成本远超收益，而且大肥鱼已经有自己的"该不该回"（GroupGate + 插件 gate）。

**为什么用字数当完整度的代理**

这是 AstrBot 的核心洞察，原文：

> Length is a proxy for completeness: a long message is usually a finished
> thought, while a very short one is often the first bubble of a multi-part
> message.

「在吗」两个字几乎肯定还有下文；「我今天去长坂坡了，看到了樱花还看到枣树」
基本说完了。不需要 NLP，字数加标点就够准。

**代价**

- **群里被 @ 也要等满窗口（最多 4 秒）**：`at_bot` 的判定在 `handle` 里做，
  入批时拿不到。先保证一条不漏，速度以后再说。
- **一批的 `sender_name` 取最后一条**：群聊多人交替时 @ 的是最后说话的人。
- 一批 3 条只让 `_peer_seq` +1（原来每条 +1），"补一句"的取消判定略钝。

**验证**

- `selftest_listen` 28 → 45（新增 17 条：自适应窗口、边界夹取、开关回退、
  断句三连端到端）
- 源码全套 `tools/selftest.py` 23 项
- 其余八套全部通过
