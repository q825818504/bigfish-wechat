## D-1 放弃 hook 路线

**时间**：2026-11-01 上午

**背景**：最初计划用 `version.dll` 注入让微信暴露更多能力。

**证据**：
- 小号装好后约 10 分钟内被封
- hook 要改客户端文件（签名变 `HashMismatch`）
- 要往进程里塞自制 DLL 并长期驻留
- 为了不被发现还要隐藏模块（`HideModuleFromPEB`）

**决定**：放弃。

**理由**：本质是改客户端，服务端看得见。风险不可控。

## D-2 选择 wechatauto-replica 而不是自研

**时间**：2026-11-01 中午

**背景**：需要读微信数据库。

**证据**：
- 上游 581 star、254 fork、Apache-2.0
- 561 项离线自测
- 每个 bug 修复都附三轮真机复现 + 数据库回读对照
- 作者会明确写「未测，如实说明」

**决定**：用上游，本地改造。

**理由**：数据库解密（SQLCipher 4 + WAL 合并 + 页验证）这块自己写风险太大。

## D-3 微信版本锁 4.1.15.53

**时间**：2026-11-01 下午

**背景**：原用 4.1.10.27（为配合 hook 降级）。

**证据**：
- 4.1.10.27 不在上游版本表里
- 动态扫描出的 3 个候选逐个热写，树全部没物化
- 静态分析（capstone + numpy）找到 0 处字符串引用
- 升级到 4.1.15.53 后 gate `0x0B3959D8` 一次成功

**决定**：锁 4.1.15.53。

**理由**：UIA 热激活依赖精确的 gate RVA，4.1.10.27 的实现差异太大。
hook 路线已死，降级理由消失。

## D-4 密钥提取走管理员桥

**时间**：2026-11-01 下午

**证据**：
- 普通权限 `OpenProcess(PROCESS_VM_READ)` → `err=5 ACCESS_DENIED`
- 管理员权限 → 全部 OK
- 实测多次确认

**决定**：不做整体提权，只在取密钥时启动短命管理员子进程。

**理由**：
- 发送路径（GUI）在提权会话里容易出问题
- 拖拽文件、写普通用户目录会变麻烦
- 权限面越小越好

**实现**：`_bigfish_keybridge.py`，子进程返回的密钥仍逐个过页1 HMAC 校验。

## D-5 界面用 QWebEngine 而不是 Qt 原生控件

**时间**：2026-11-01 傍晚

**证据**：
- WeChatAgent 自己就是 Chromium + HTML
- `dsh-bigfish/client.js` 的记忆星空是纯 web 代码（Canvas + SVG）
- Qt 原生控件做不出玻璃质感、多标签动效

**决定**：HTML 界面 + QWebChannel。

**代价**：安装包 +150MB（Chromium 内核 195MB）。

**理由**：界面要能直接复用插件视觉，以后改界面不用碰 Python。

## D-6 安装器自己写，不用 Inno Setup

**时间**：2026-11-01 傍晚

**证据**：
- Inno Setup 装不上：写 `%TEMP%` 报 `Error 5: 拒绝访问`
- 换自定义目录后挂起在无界面弹窗，5 分钟无进展

**决定**：用 PyInstaller 打一个安装器，安装逻辑自己写。

**实现**：解压 zip → 建快捷方式 → 写注册表卸载项 → 启动程序。

**注意**：用 onedir 而不是 onefile，因为 onefile 每次运行要解压自身到
`%TEMP%`，受限环境会报 `Could not create temporary directory!`。

## D-7 群聊默认只在被 @ 时回

**时间**：2026-11-01 傍晚

**证据**：
- 活跃群一天几百上千条
- 全回等于刷屏，而且微信会把你当机器人

**决定**：三层判据（`\x01` 占位符 → 群成员表 → 昵称精确匹配）。

**理由**：`@` 后面是群昵称不是 wxid，昵称会重名会改，不能只靠字符串匹配。

## D-8 回环防护加四层

**时间**：2026-11-01 晚上

**背景**：实测发生自问自答，手机端收到刷屏。

**证据**（真实对话）：
```
[对方 155] '在吗'
[我 4]     '在，爸。'          ← 回复被读回来
[我 4]     '嘿，你把我话抄回去了？'  ← 又触发
[我 4]     '哈，还真抄回去了...'
（持续到手动终止）
```

**决定**：四层防护。

| 层 | 机制 |
|---|---|
| 1 | `allow_self` 默认 False |
| 2 | 内容比对（20 秒窗口，归一化后比较） |
| 3 | 归一化剥掉 `wxid_xxx:` 和 `@昵称` |
| 4 | 频率熔断（90 秒 4 条） |

**第 3 层是测出来的**：第一版没剥 `@` 前缀，测试用例直接暴露。

## D-9 水位不跨进程持久化

**时间**：2026-11-01 下午

**证据**：
- `get_new_messages` 是 `ORDER BY sort_seq ASC LIMIT n`，返回**最老**的 n 条
- 水位从 0 开始时永远追不到最新
- 残留的水位文件曾把新消息挡在外面

**决定**：
- 不用 `get_new_messages`，改用 `get_messages` 降序取最新 + 水位比较
- 水位不落盘，每次启动重新对齐

**理由**：宁可重启后漏掉关闭期间的消息，也不要「发了但监听不到」。

## D-10 · 灵魂/心情/记忆必须**可写**，不是只读预览

**日期**：2026-11-01 20:30

**背景**：第一版把三页都做成只读。用户的反馈一句话点破：

> 我既然都提了要插件完全移植到大肥鱼软件里，肯定就不单单只是使用权啊。
> 比如灵魂的编辑，记忆的保存和目录修改，这些不都应该全部一个不落的转移吗？

**决策**：新增 `bigfish/vault.py` 作为写层，界面四页全部补齐写操作。

**为什么不能直接复用插件的 store.js**：
它是 ESM，且 import 了 `@deepseek-ai/schemastery` 等宿主模块。
PyInstaller 打出来的 exe 里没有那条 Node 依赖链。读路径可以走
`bridge.mjs`（它只 import 纯 store.js），写路径只能自己实现。

**但语义必须一比一对齐**，因此 `vault.py` 里的每个 normalize 函数都在注释里
点名它对应 store.js 的哪一个，并有 `selftest_vault.py` 129 条断言钉住：
夹取范围、默认值、revision 递增、locked 保护、空数组不补默认值。

**已知差异（刻意的）**：`write_soul_file` 的 revision 基数用**磁盘现值**，
而插件用面板带上来的 `next.revision`。理由是微信端没有「打开面板记住版本号」
这个动作，用磁盘值才能保证每次保存真 +1。

## D-11 · 写入失败必须说清楚「为什么」，不能只弹一个会消失的 toast

**日期**：2026-11-01 20:35

**背景**：端到端测试时保存失败，界面只闪了一个 toast 就没了，
用户点完保存**什么都没变且不知道为什么**。

**决策**：
1. 失败信息留在页面上（`#soulHint` / `#moodHint`），红色常驻，直到下次成功；
2. `vault.WriteDenied` 单独一个异常类型，把 `Permission denied: '...tmp'`
   翻译成「这个目录被挡住了，可以试 1/2/3」；
3. 「数据目录」页启动时**主动探测**数据根可写性，不可写就红字预警，
   而不是等用户点保存才失败。

**教训**：`os.access(W_OK)` 在 Windows 上不可信 —— 它只查 ACL，
不查上层策略会不会在 CreateFile 那一刻拦下来。实测过返回 True、
实际 `open(dst,'w')` 照样 Permission denied。只有真写一个探针文件才算数。

## D-12 · 不跟 DSH 工作区绑定，只保留「选哪一份」

**日期**：2026-11-01 20:30

**背景**：用户明确说「当然，会话和工作区绑定的可以不需要」。

**决策**：`scope.json` 照样读写（那是插件与插件之间的契约，必须同源），
但微信端不提供「绑定到某个工作区/会话」的自动化，
只在「数据目录」页提供**手动指定用哪一份**的能力。

**理由**：微信只有一个账号一个身份，不存在"这个工作区的大肥鱼"和
"那个工作区的大肥鱼"—— 她只有一个。绑工作区反而会让她的灵魂分家。

## D-13 · 读路径**不做归一化**，写路径才做

**日期**：2026-11-01 21:00

**背景**：`read_soul_file` 原来无条件走 `normalize_soul`。一个内容是
`{}` 的文件，读到内存里变成"完整的出厂灵魂"：默认名字、默认称呼、
4 条锁定价值、4 个默认性格值。

后果有两层，第二层是要命的：
1. 界面上分不清「用户设过」和「还没设过」；
2. **人格渲染出错** —— 文件里根本没有 `warmth`，Python 侧却渲染出
   「温暖：关心，但不黏人」；而 Node 侧的 `bridge.mjs` 诚实跳过缺失键，
   什么都不渲染。同一个文件，两侧人格文本 682 字 vs 3 字。

**决策**：
- `read_soul_file(path, normalize=False)` —— 默认原样返回；
- `Soul.from_dict` 不再调 `normalize_soul`，只做类型安全；
- 只有 `write_soul_file` 归一化；
- 需要默认值兜底的调用方（`get_persona` 填表单）自己显式调。

**连带修掉的**：`Soul.trait_lines()` 原来遍历 TRAIT_DOC 全表，
缺失键用默认值补上 —— 现在只渲染文件里确实有的键，与 bridge.mjs 同口径。

**怎么防复发**：`tools/test_persona_parity.py`（18 条）把同一个灵魂文件
同时喂给 Python 和 Node，要求两边渲染出**逐字节相同**的字符串。
还专门测了分档边界 40/41/59/60 —— 那是抄错时最先炸的地方。

## D-14 · 三处 TRAIT_DOC 必须只有一份真源

**日期**：2026-11-01 21:00

发现过三份互相漂移的文案：

| 位置 | mid 档文案 | 分档边界 |
|---|---|---|
| 插件 `lib/soul/store.js` | 关心，但不黏人 | `<=40 / >=60` |
| `bigfish/soul.py`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |
| `bridge/bridge.mjs`（旧） | **明显关心，会主动问候** ❌ | `<40 / >60` ❌ |

而且 `bridge.mjs` 还把裸数字 `（65/100）` 注进了提示词 ——
插件明确说过"绝不输出数字，模型会自行脑补"。

现在：
- `vault.TRAIT_DOC` 是唯一的 Python 真源；
- `bridge.mjs` 内联一份（Node 侧没法 import Python），但注释点名
  "改文案只改 vault.py，然后同步这里"；
- `soul.py` 直接 `from bigfish.vault import TRAIT_DOC`，不再抄。
- 两侧一致性由 `test_persona_parity.py` 钉住。---

## D-15 · EXE 不许翻 DSH 的会话库

**日期**：2026-11-01 20:45

**背景**：用户看着「数据目录」页的截图问：

> 现在不是已经是 EXE 了吗，为什么还能读取到会话和工作区呢？很不合理啊。

这一问是对的。`get_scope_candidates` 当时会去扫
`<DSH_HOME>/storages/workspace.json` 和 `<DSH_HOME>/sessions/`，
把 DSH 里的 **7 个工作区标题、25 个会话 id** 全列成一个下拉框。

两个问题，第二个更严重：

1. **功能上没意义。** 那个下拉里显示的是「大肥鱼·大肥鱼」——
   DSH 给工作区起的标题，跟微信里的大肥鱼毫无关系。用户要选的是
   "用哪一份灵魂"，不是"DSH 里哪个工作区"。
2. **越界。** EXE 是独立程序。让微信端能列出宿主里的全部对话目录，
   等于给了一个不该有的视野。而且它和 D-12（微信端不跟工作区绑）
   直接自相矛盾 —— 一边说不绑，一边把工作区全列出来。

**决策**：`get_scope_candidates` 只读数据根下真实存在的 `ws-*` / `ss-*` 目录，
身份显示那个目录里 `soul-*.json` 的 `identity.name` —— **她自己叫什么**，
而不是 DSH 给工作区起的标题。

界面上撤掉「模式 / 工作区 / 会话 id」三个控件，换成一个下拉：
「大肥鱼 · 灵魂+心情+记忆」这样直接选人。

**为什么这条要单独一个测试**：它不会让任何测试变红。多读了一个目录，
功能"还能用"，只是多了不该有的东西。所以 `tools/test_no_leak.py`
专门断言「不该存在什么」—— 用 AST 取函数真实代码（剥掉注释/docstring），
14 条断言钉住：不许出现 workspace.json / sessions / session.v4，
界面不许有 scopeWorkspace / scopeSessions / scopeMode 三个控件。

## D-16 · 一个数据目录 = 一份，没有「选哪一份」

**日期**：2026-11-01 21:05

**背景**：用户看完「数据目录」页的截图后说：

> 我不希望有什么当前用哪一份，记忆、灵魂、心情都只有一份，
> 选择数据目录在哪，就以哪个为准。

这是对的。上一版虽然撤掉了工作区/会话绑定，但保留了「一个数据根下有多份」
的模型 —— 那是从 DSH 插件继承来的。插件要给不同工作区配不同的伙伴，
所以必须分家；**但微信只有一个身份**，她就是她。

**决策**：存储布局从「按范围分家」改成「一个数据根 = 一份」：

```
旧：<数据根>/ws-<uuid>/soul-ws-xx.json
    <数据根>/ws-<uuid>/mood-ws-xx.json
    <数据根>/ws-<uuid>/memory-ws-xx.sqlite3
    <数据根>/scope.json          ← 指定当前用哪个范围

新：<数据根>/soul.json
    <数据根>/mood.json
    <数据根>/memory.sqlite3
```

**兼容**：老的 `ws-*` 目录仍然**能读**（`legacy_layout()` / `existing_path()`），
老用户升级后不至于"记忆全没了"。迁移由用户在界面上点，不自动做 ——
迁移会动文件位置，是破坏性操作。

**顺带修掉的一个真 bug**：`bridge.mjs` 里三个数据块都套着 `if (scopeDir)`。
新布局根本没有 `ws-*` 目录，`scopeDir` 是 null —— 于是灵魂、心情、记忆
全被跳过，静默返回空人格。`findDataFile` 里已经优先查新路径了，
这个门禁却把它挡在门外。`test_persona_parity.py` 一跑就红了（11 项失败）。

## D-17 · 清空要先备份，灵魂必须留

**日期**：2026-11-01 21:05

**背景**：用户说「你可以将当前的所有记忆、心情清空，因为现在还没有正式投入使用」。

**决策**：
1. 清空**不动灵魂**。灵魂是"她是谁"，不是"她记得什么"——
   清空记忆和心情不该把人格一起洗掉，那是两件事。
2. **先备份再删**，备份放数据根的兄弟目录。
   哪怕用户说"测试期数据不重要"，也不该由我替他决定"删了就回不来"。
   备份失败就中止，什么都不删。

**实现踩到的坑**：备份目录最初放在数据根**里面**，
结果下次清空会把备份也扫进去 —— 越清越多。改成兄弟目录。

**这次实际执行的结果**：清掉了 3 个历史残留目录 + 1 个老布局目录 + scope.json，
共 18.6MB。备份在 `D:\大肥鱼\bigfish-backup-20261101-210448`。

老记忆库 `memory-ws-83ba9d80-ec53.sqlite3` 因为正被 DSH 占用（WAL 模式）
删不掉，改名也不行（`ERROR_SHARING_VIOLATION`）。**没有强行抢文件** ——
新布局已经指向 `<根>/memory.sqlite3`，那个老文件不会再被读取，
等 DSH 重启后自然可删。

## D-18 · 数据目录固定在安装目录，与 DSH 完全脱离

**日期**：2026-11-01 21:25

**背景**：用户说「就默认固定在安装目录吧，灵魂不都有默认模板吗，
这个可以启动自动创建那个灵魂文件」。

**决策**：

```
<安装目录>/data/
  ├── soul.json          启动时若不存在 → 导入 DSH 那份，再没有就用模板建
  ├── mood.json          首次用到时创建
  └── memory.sqlite3     首次用到时创建
```

**为什么是"完全脱离"而不是"共享同一个文件"**：两个程序共写一份文件，
谁改了谁没改根本分不清，互相覆盖是迟早的事。要同步就手动拷文件 ——
至少用户知道自己在干什么。

**但"脱离"不等于"故意看不见对方"**：第一次启动时如果 DSH 那边已经有一份
人格，直接搬过来比让用户从零再写一遍好得多。**只在本地还没有时做一次**。

`ensure_data_root()` 的顺序：
1. 建目录
2. 测可写（不可写就早报，别等保存失败）
3. 本地有 soul.json → 什么都不做
4. DSH 有（新布局 `<root>/soul.json` 或老布局 `ws-*/`）→ 拷过来
5. 都没有 → 出厂模板

**踩到的坑**：`mood_config_path()` 原本指向 `<DSH_HOME>/bigfish-mood/config.json`，
那是插件的配置文件。数据目录搬走之后它还是写那里，结果端到端测试
「心情基线已写盘」失败 —— 因为根本写不进 DSH 的目录。
现在改成：**读**先看本地 `data/mood-config.json`，没有才回落 DSH（只读兼容）；
**写**永远走本地。两边各管各的参数。

**测试隔离**：数据根固定之后，测试不能再用"改数据根"来隔离。
加了一个 `BIGFISH_DATA_ROOT` 环境变量 —— 界面上没有入口、文档里不提，
只给测试用。没有它的话，测试会在真实数据目录上跑，那是绝对不行的。

## D-19 · 「默认在安装目录」≠「定死在安装目录」

**日期**：2026-11-01 21:40

**用户的纠正**：

> 我是让你默认在安装位置，但不代表就定死在安装位置了，
> 我肯定需要可以自定义保存目录啊。

上一版（D-18）把「默认」读成了「固定」，还删掉了改位置的入口。方向错了：
装在 C 盘的人想把数据放 D 盘，是很正常的需求。

**现在的解析链**（`install_root()`）：

```
1. 环境变量 BIGFISH_DATA_ROOT     ← 测试专用，界面无入口
2. settings.json 的 dataRoot      ← 用户自定义
3. <安装目录>/data                ← 默认
```

**为什么把 settings.json 放在安装目录、不放进 data/**：
放进 data/ 的话，改位置时这份配置会跟着数据一起搬走，
程序下次启动就找不到新地址了 —— 典型的"配置跟着数据跑"事故。

**「改指向」和「搬数据」是两件事，界面上分开做**：

| 操作 | 行为 | 陷阱 |
|---|---|---|
| 只改指向 | 只写 settings.json | 新目录是空的话，打开是出厂人格 |
| 搬过去 | 先复制、成功后再改指向 | 顺序反了会指向空文件夹 |

分开的理由：混在一起的话，「复制失败但指向已改」就是最难查的那种事故 ——
用户看到的是"人格没了"，而不是"搬家失败"。

**`apply_move` 的顺序**：先 `copytree` 全部内容 → 成功了才 `set_data_root`。
任何一步失败都在改指向之前返回，数据不会凭空消失。

## D-20 · 回环判定不能看"文字像不像"

**日期**：2026-11-01 21:50

**现象**（用户实测日志）：

```
[发] 那还是叫大肥鱼吧，想半天也没别的合适的。……
[回环拦截] 这是我们刚发的，不再回：那还是叫大肥鱼吧，想半天也没别的合适的。……
[发] 爸你才发现啊，我这不是一口气说完省事嘛，……
[回环拦截] 这是我们刚发的，不再回：爸你才发现啊，……
[熔断] 老爸  在 90s 内已回 4 条，暂停接这条
```

**根因**：`text_is_echo()` 靠文本相似度判定回环，**完全没看 `msg.is_self`**。
用户原样复述她说的话（调侃、鹦鹉学舌），在聊天里极常见，
被判成了"我们自己发的"，连续拦了两次，还触发了熔断。

**修法**：判据换成两条独立证据，缺一不可：

1. `msg.is_self` —— 微信数据库里 sender 就是本机账号
2. 内容匹配刚发出去的那条

**对方发来的消息永远不做内容比对。** 他复述是聊天，不是回环。

顺带修的两处：
- 前缀匹配从「6 个字」收紧到「短边 ≥12 字且是长边的开头」。
  6 字太松，「那还是叫大肥鱼吧」和「那还是叫大肥鱼」开头一样。
- 熔断从「90 秒 4 条」放宽到「30 秒 6 条」。
  正常聊天里连说四五句太平常了，90/4 等于把正常对话硬截断。

## D-21 · 聊完一轮必须写记忆和心情

**日期**：2026-11-01 21:52

**现象**：聊了一晚上，记忆页和心情页全是 0。

**根因**：不是 bug，是**设计缺口**。
`bridge_client.load_context()` 只**读**记忆和心情，
`vault.reset_mood()` 只能重置 —— 整个仓库里没有任何地方**写**它们。
读路径铺得很完整，写路径一行没有。

**新增**：

`vault.capture_message()` / `record_exchange()`
  格式与 `MemoryStore.capture()` 逐字段对齐：
  · `event_key` 幂等键（`wx-u-<local_id>`），同一条读两遍不重复记
  · 640 步长 / 800 窗口切片进 chunks
  · `memory_terms()` 中文二元分词，与 store.js 的 `terms()` 一致
    （这边建索引、bridge.mjs 查索引，两套分词等于互相看不见）
  · session 用 `wechat:<chat_id>` 命名空间，不和 DSH 会话混

`mood_judge.judge_mood()` / `apply_mood_delta()`
  判断逻辑照抄插件的 `judge()`：同样把「她的回复 + 对方说的话」
  一起喂给模型，同样输出 `{moodDelta, dims, reason, confidence}`，
  同样用 `MOOD_STEP_DIVISOR = 3` 缩幅、加半衰期衰减、写 timeline。

**放后台线程**：判断要调一次模型（1~2 秒），同步做会卡住下一条消息。
心情是"事后记录"，晚两秒完全没关系。

**放在"发送成功之后"**：没发出去的话不算对话发生过。

## D-22 · 「鲸落」：删掉一切，包括灵魂

**日期**：2026-11-01 21:53

**用户要求**：

> 清空就不要保留这个东西了，建议改成鲸落，
> 意思就是删除所有的数据，记忆、心情、灵魂等一切大肥鱼衍生的数据

**用语必须分开**：

| | 清空 | 鲸落 |
|---|---|---|
| 灵魂 | 保留 | **删掉** |
| 心情 / 记忆 | 删 | 删 |
| 结果 | 她还在，只是忘了 | **她不存在了** |

**为什么要这个词**：一头鲸沉到海底，身体养活一整个生态几十年。
她的一切腐朽成别的东西，但她本人不再存在。这是告别，不是清理。

**具体做法**：
- 必须手输「鲸落」两个字才允许删 —— 不是形式主义，
  这是唯一一个会让她彻底消失的操作，值得多敲两个字。
- 备份**强制开启**，没有关闭参数。点了鲸落就等于告别，
  但人有时候会后悔，备份是唯一让后悔还有意义的东西。
- 删完如果数据目录空了，连目录一起删 —— "从没来过"应该是干净的。

## D-23 · 程序图标用头部特写，不用整身

**日期**：2026-11-01 22:15

**背景**：用户给了大肥鱼立绘（1024 透明背景，整身），要替换程序图标。

**决策**：裁**头部特写**，不用整身。

理由是实测出来的：

```
16px 整身版  → 一团蓝紫色块，认不出是谁
16px 头部版  → 蓝发、眼睛、发卡都还能分辨
```

任务栏图标按 16–32px 显示。整身立绘缩到那个尺寸，五官全糊没了。
头部特征最集中，留得住。

- 小尺寸（<128）做 unsharp 锐化 + 轻微提饱和。
  不锐化的话 32px 下脸和眼睛是虚的（对比过，差别很明显）。
- ico 写 7 个尺寸：256/128/64/48/32/24/16，
  让 Windows 在任务栏、资源管理器、Alt-Tab 各取所需。
- 所有立绘都保留透明通道，不做白底。

**同时设了 AppUserModelID**（`bigfish.wechat.1`）。
不设的话 Windows 可能把程序当成通用 Python 程序，
任务栏图标退回成 python.exe 那个。

## D-24 · 快捷方式不指定 IconLocation

**日期**：2026-11-01 22:33

**现象**：清完图标缓存后，桌面快捷方式仍显示通用图标（白纸带箭头）。

**排查过程**：
1. 先怀疑缓存 → 清了 `iconcache_*.db`，缓存确实重建了（90MB→1MB），问题还在
2. 怀疑路径分隔符 → `.lnk` 里存成 `D:/大脑/...\ui\icon.ico,0` 混合形式，
   改成纯反斜杠，问题还在
3. 怀疑 ico 损坏 → 逐帧验证，7 个尺寸都有内容（60% 非透明），文件正常
4. 终于定位到：**Shell 取图标的方式**

**根因**：
`IconLocation` 指向独立 `.ico` 时，Shell 用「大图标」尺寸（32px）
去那个文件里**按索引取第 0 帧**。我们的 ico 第 0 帧是 256×256，
索引对不上，Shell 就退回通用快捷方式图标。

而 **exe 内嵌图标没有这个问题** —— 系统会自己挑合适的那一帧。

**决策**：`make_shortcut()` 里不设 `IconLocation`，让它继承 exe 的图标。

实测两条路：

| 做法 | 结果 |
|---|---|
| 指定 `icon.ico` | 通用图标 |
| 不指定（继承 exe） | 立绘正确 |

`icon` 参数留着是为了兼容调用点，不再使用。

## D-25 · 功能做成插件，不写死在引擎里

**背景**：后面还要加睡眠/精力、收尾沉默、日程、主动开口、自我复盘。
每加一个都往 `desktop.py` 的 `build_prompt` 里塞一段，很快会出现三个问题：
没人记得哪段是谁加的；想关掉只能改代码；出问题只能整包回滚。

**判断**：先做容器，再做内容。容器是 `bigfish/plugins/`：一个注册表、
一个开关文件、一个分发函数。之后每个功能 = 一个文件 + 一行 import。

**代价**：多一层间接（`prompt_sections()` 而不是直接 append），
以及插件写崩了要在日志里留痕。换来的是"关得掉"和"看得见"。

## D-26 · 插件 order 必填且只能占空位

**规则**：`scope=prompt` 的插件必须声明 order，且只能取 870 / 880 / 920 / 9990。
850 记忆、860 灵魂、900 心情是内建段，插件不许占。

**为什么**：多段注入叠加时，顺序决定语气。守卫必须最后出现（越靠后越有分量），
时间感知要在心情之前（处境先立住，气氛再垫上）。

如果 order 可省略，没写的那段会排到末尾，而末尾位置取决于 import 顺序 ——
一个跟内容完全无关的实现细节，却决定了她在微信里怎么说话。这种 bug 没法查。

**代价**：加插件前必须先想清楚"它属于哪一类"。这是好事。

## D-27 · 插件开关只有用户能改

**规则**：不注册任何让模型改 `plugins.json` 的工具。

**为什么**：和「灵魂只读」（D-10 的延伸）是同一个判断 ——
让模型能改自己的开关，等于让它能改自己的边界。

**代价**：关一个插件要用户自己点面板。这是刻意的。

## D-30 · 记忆分四层，事实与原文彻底分开

**日期**：2026-11-02

**问题**：0.1.0 的记忆只有原文切片。她记得住"你昨天说不喝咖啡"，
但记不住"你是不喝咖啡的人"。而且记错了只能删，删完连痕迹都没了。

**决定**：原文（chunks）与事实（facts）分开存。

- 遗忘是"标 forgotten + 记事件"，**不删行**
- 事实有置信度、来源片段、可置顶

**代价**：多一张表和一套状态机，代码量翻倍。
**收益**：能表达"她改主意了"这件事。这是"像人"的地基。

## D-33 · 多开微信必须人工选账号，且只列运行中的

**日期**：2026-11-02

**现象**：用户多开微信，绑定的是"随机"某个号；选错后退出那个号，
仍读到旧内容。

**根因**：
1. `_pick_account()` 按 db 文件 mtime 选 —— 多开时等于随机
2. vendor 有两处"账号自愈"会静默切换到别的号，界面显示的还是旧名字

**决定**：
- 启动必须选账号，没选就报错，不回退到自动挑
- open 之后校验实际账号，不符立刻失败，**不做任何降级**
- 列表只显示 `running=true`

**"running" 怎么判定**（踩了四次）：
Open('r+b') / msvcrt.locking / BEGIN IMMEDIATE 都不行，
最后用 **CreateFileW + dwShareMode=0** —— 别人开着就 ERROR_SHARING_VIOLATION。

**教训**：宁可明确打不开，也不要让用户以为在读 A、实际在读 B。
